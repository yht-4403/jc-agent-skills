# JC Daily Thought Social Publisher V5

**一句话定位**：把知识库长文拆成内容原子，再自动判断是否需要升级调用 DBS 方法，最后只围绕一个小红书问题成稿。

v5 = v4 的「原子拆分 + 单问题成稿」+ 自动路由层。

## 版本差异

- v3：保留完整叙事，适合飞书、知乎、Uplog。
- v4：先拆原子，只选一个问题，适合小红书。
- v5：在 v4 基础上增加自动判断：问题不清走 `dbs-good-question`，概念不清走 `dbs-deconstruct`，角度不稳走 Mini Chatroom。

## 关键边界

「问题 → 常见误区 → 机制 → 例子 → 动作」不是 DBS 原 skill 明文规定的固定模板。

这是本 skill 为小红书平台定制的成稿骨架，来源于 DBS 的 `dbs-good-question`、`dbs-deconstruct`、`dbs-content-system`、`dbs-hook`、`dbs-content` 的组合方法。

v5 不默认完整调用所有 DBS skill。它先用轻量规则判断，只有踩到阈值才升级调用。

## 成稿边界

v5 不判断内容适合哪个账号，也不为了匹配作者身份、账号定位或发布渠道去改写材料。

成稿必须就事论事，服务这个主题本身和目标读者。禁止为了贴合作者身份或商业身份，额外加入原文没有的跨领域例子、个人经历或个人复盘。

例子优先来自原文。原文没有足够例子时，只能使用中性、贴合主题的补充场景，并标注为「补充场景」，不能把作者本人塞进正文。

## 前置条件

用户提供原文全文或知识库文件路径。主 agent 必须完整读取原文，不跳读。

如果用户提供的是文件路径，最终发布稿保存到：

```text

```

文件名遵循：


同名文件已存在时，在文件名末尾追加 `-2`、`-3`。

## DBS 调用说明

v5 里的「调用 DBS」指：主 agent 根据阈值读取对应 DBS skill 的 `SKILL.md`，按它的方法对当前问题/概念/角度做专项校准，再把校准结果合并回 v5 成稿流程。

默认可用路径：

- `dbs-good-question`：`/Users/codemao/.cc-switch/skills/dontbesilent2025-dbskill-dbs-good-question/SKILL.md`
- `dbs-deconstruct`：`/Users/codemao/.cc-switch/skills/dontbesilent2025-dbskill-dbs-deconstruct/SKILL.md`
- `dbs-chatroom`：`/Users/codemao/.cc-switch/skills/dontbesilent2025-dbskill-dbs-chatroom/SKILL.md`

注意：不要把 `dbs-chatroom` 原版推荐专家流程作为默认流程。v5 默认使用 Mini Chatroom；只有用户明确要求完整聊天室时，才使用原版 `dbs-chatroom`。

## 执行流程

### Phase 0：读取原文

完整读取原文，识别：

1. 原文主题
2. 原文材料类型：读书笔记 / 个人思考 / 案例复盘 / 方法论 / 销售拆解 / 职场观察
3. 原文中的事实、作者观点、AI 推断、个人应用建议
4. 哪些内容适合公开发布，哪些只适合留在知识库决策记录里

正文里不要保留「作者观点」「AI 推断」「个人应用建议」这类知识库标签。发布稿要像一个人在说话。

### Phase 1：原子拆分

按 DBS 内容工程的五类单元拆原文：

1. **问题单元 Q**：这段材料真正能回答什么问题
2. **概念单元 C**：承担论证重量、容易误解的大词
3. **观点单元 O**：作者真正想表达的判断
4. **案例单元 E**：能证明判断的具体场景、对话、数字、行为
5. **方案单元 S**：读者看完能做的动作

拆分规则见 `references/atomization-guide.md`。

### Phase 2：选择本次成稿问题

只选一个问题单元成稿。

按 5 项评分：

1. 痛点即时性
2. 冲突强度
3. 场景具体度
4. 材料可支撑度
5. 主题通用性

如果最高分问题仍然不够清楚，不要直接成稿，进入 Phase 3 自动路由。

### Phase 3：自动路由

读取 `references/auto-routing-guide.md`，按顺序判断：

1. **问题门**：是否需要 `dbs-good-question`
2. **概念门**：是否需要 `dbs-deconstruct`
3. **角度门**：是否需要 Mini Chatroom

调用顺序固定：

```text
原子拆分 → 问题门 → 概念门 → 角度门 → 成稿
```

不要反过来先 Chatroom。没有一个清楚的问题，多视角讨论只会把文章变散。

升级调用上限：

- 默认最多升级 2 个环节。
- 如果已经调用了 `dbs-good-question` 和 `dbs-deconstruct`，只有在角度仍明显不稳时才进入 Mini Chatroom。
- 用户明确要求「完整压测」时，可以三者都走。

把每次调用或跳过的理由写入最终文档的「自动路由记录」。

### Phase 4：问题校准

对最终选题做 7 项校准：

1. **目标读者**：这篇只写给哪一种人
2. **现象**：他们正在经历什么具体场景
3. **常见误区**：他们通常会怎么理解错
4. **本文问题**：这篇真正要回答什么
5. **核心冲突**：为什么这个问题值得点开
6. **可观察信号**：如果判断成立，现实中应该看到什么
7. **不确定项**：哪些只能写成个人观察，不能写成普遍规律

「本文问题」必须是一句话。不能写成大词，必须包含人、场景或动作。

### Phase 5：成稿

按以下顺序生成：

1. 标题候选 5 个
2. 开头候选 3 个
3. 正文

正文默认骨架：

1. **问题**：这篇解决谁的哪个具体问题
2. **常见误区**：多数人会怎么想错、做错
3. **机制**：为什么会这样，因果链是什么
4. **例子**：原文里最能支撑判断的一个场景
5. **动作**：读者下一次遇到这个场景时怎么做
6. **收束**：一句边界判断，不升华

成稿要求见 `references/dbs-xhs-writing-rules.md`。

### Phase 6：自检 + 自改

按 10 项检查，发现问题直接改：

| 项目 | 通过标准 |
|---|---|
| 单问题 | 正文只回答一个问题 |
| 路由合理 | 该调用的已调用，不该调用的没硬套 |
| 原子支撑 | 正文每个关键判断能回到某个原子 |
| 问题清楚 | 有目标读者、场景、冲突、反馈入口 |
| 首屏筛选 | 前 3 句能筛出目标读者 |
| 冲突清晰 | 读者知道为什么常见做法有问题 |
| 概念干净 | 大词被替换成动作、场景、反馈 |
| 例子有效 | 至少有一个具体场景支撑机制 |
| 动作具体 | 读者知道下一次怎么做 |
| AI 味 | 无空泛排比、无过度升华、无连续口号 |
| 无身份迁移 | 没有为了匹配作者身份、账号定位或发布渠道新增例子 |

如果正文仍像飞书/知乎文章，重写开头和正文结构。

## 迭代方式

| 用户反馈 | 执行 |
|---|---|
| 「换一个问题」 | 从原子拆分记录里重新选 Q 单元，重跑 Phase 2-7 |
| 「问题没钉住」 | 强制走 `dbs-good-question`，重写问题校准和开头 |
| 「概念没拆清」 | 强制走 `dbs-deconstruct`，重写相关正文段落 |
| 「角度不稳」 | 强制走 Mini Chatroom，重选角度 |
| 「太像长文」 | 压缩到 500-800 字，保留问题、误区、机制、例子、动作 |
| 「不够 DBS」 | 检查是否缺少冲突、现实信号、大白话概念拆解 |
| 「开头不筛人」 | 重写 3 个开头，只保留读者筛选器结构 |
| 「动作不具体」 | 重写正文最后 1/3，只保留下一步行为 |
| 「想发知乎/飞书」 | 切回 v3 或输出长文版，不用 v5 单问题约束 |
