# v5 自动路由指南

## 路由总原则

先拆原子，再判断是否升级。

不要把流程设计成：

```text
原文 → good-question → deconstruct → chatroom → 成稿
```

正确流程是：

```text
原文 → 原子拆分 → 自动诊断 → 需要哪个才调用哪个 → 成稿
```

默认最多升级 2 个环节，避免流程过重。

## 路由顺序

固定顺序：

1. 问题门：`dbs-good-question`
2. 概念门：`dbs-deconstruct`
3. 角度门：Mini Chatroom

原因：

- 问题不清时，概念拆解和 Chatroom 都会发散。
- 概念不清时，成稿会出现大词撑文章。
- 角度不稳时，才需要多视角压测。

## 问题门：是否调用 dbs-good-question

### 触发条件

满足任意一条，就调用：

1. 本次选题没有具体人群。
2. 本次选题没有具体场景。
3. 本次选题没有核心冲突。
4. 本次选题没有可观察信号。
5. 选题写成「为什么 X 很重要」「如何提升 X 能力」「怎么做好 X」。
6. 问题评分中「场景具体度」或「冲突强度」低于 3 分。
7. 最高分问题总分低于 18 分。

### 调用方式

读取：

```text
/Users/codemao/.cc-switch/skills/dontbesilent2025-dbskill-dbs-good-question/SKILL.md
```

只做与成稿有关的部分：

1. 钉现象
2. 暴露冲突
3. 明确对象、目标、约束、反馈
4. 生成一句话「本文问题」
5. 生成 1-2 个低置信候选解释和可观察信号

不需要输出完整评分表，除非问题特别松。

### 合并规则

把 `dbs-good-question` 的结果合并回 v5：

- 更新「本文问题」
- 更新「核心冲突」
- 更新「可观察信号」
- 必要时重新选择问题单元

## 概念门：是否调用 dbs-deconstruct

### 触发条件

满足任意一条，就调用：

1. 核心判断依赖 1-3 个高风险概念。
2. 去掉某个概念后，正文主线说不清。
3. 同一个词在原文里可能有多个意思。
4. 概念是商业/职场/内容领域的大词：解决方案、闭环、壁垒、平台光环、个人 IP、商业模式、私域、流量、定位、背书、资源、人脉、转化。
5. 正文草稿里出现连续抽象词，缺少动作、场景、反馈。

### 调用方式

读取：

```text
/Users/codemao/.cc-switch/skills/dontbesilent2025-dbskill-dbs-deconstruct/SKILL.md
```

只拆承担论证重量的 1-2 个概念。

默认不要做 7 张表，除非用户明确要求深度拆解。

必做四项：

1. 它在原文里是什么意思
2. 读者可能误解成什么
3. 用大白话怎么说
4. 成稿里保留 / 替换 / 首次解释 / 删除

### 合并规则

把拆解结果合并回 v5：

- 更新概念单元
- 改写正文里的大词
- 如果概念本身被判定为伪概念，正文不要围绕这个词写标题

## 角度门：是否进入 Mini Chatroom

### 默认使用 Mini Chatroom，不默认使用原版 dbs-chatroom

原版 `dbs-chatroom` 会推荐专家并等待用户确认。它适合做深度讨论，不适合每篇小红书稿默认调用。

v5 默认使用内置 Mini Chatroom：

1. **严苛小红书读者**：哪里想划走，哪里像说教
2. **同频从业者**：哪里有共鸣，哪里值得收藏或转发
3. **DBS 编辑**：哪里太散、太像 AI、太像飞书/知乎

如果可用 sub-agent 工具，就并行调用三个子 agent。没有 sub-agent 工具时，由主 agent 在内部模拟三个视角，但必须分开写诊断。

### 触发条件

满足任意一条，就进入 Mini Chatroom：

1. 最高分问题和第二名问题分差小于等于 2 分。
2. 目标读者不清楚。
3. 开头候选连续 2 次都像文章说明，不像读者筛选器。
4. 原文很长，原子超过 15 个，主线容易散。
5. 选题有争议，容易从分享者变成教育者。
6. 用户明确说「帮我多视角讨论」「压一下角度」「怕不够小红书」。

### Mini Chatroom Prompt

#### A：严苛小红书读者

```text
你是一个很挑剔的小红书读者。读下面的选题、开头和正文草稿，只回答：

1. 前 3 句能不能让我觉得这篇和我有关？
2. 哪里像说教、像飞书、像知乎？
3. 我最可能在哪里划走？
4. 哪一句最像「说的就是我」？

直接说，不客套。150 字以内。
```

#### B：同频从业者

```text
你是一个处境相近的从业者。读下面的选题、开头和正文草稿，只回答：

1. 哪个场景最真实？
2. 哪个判断你会收藏或转发？
3. 作者最有资格说哪一句？
4. 哪个动作建议真的能用？

直接说。150 字以内。
```

#### C：DBS 编辑

```text
你是 DBS dontbesilent 风格的内容编辑。读下面的选题、开头和正文草稿，只诊断：

1. 核心问题有没有钉住？
2. 有没有被并列观点稀释？
3. 大词有没有替换成动作、场景、反馈？
4. 开头有没有独立工作？
5. 哪一段最像 AI？

直接诊断。220 字以内。
```

### 合并规则

Mini Chatroom 后，主 agent 必须形成四个结论：

1. 保留哪个角度
2. 强化哪个场景
3. 删除或压缩哪些内容
4. 重写开头还是重写正文主线

## 完整 dbs-chatroom 触发

只有以下情况使用原版 `dbs-chatroom`：

1. 用户明确说「用完整 dbs-chatroom」。
2. 这篇不是为了快速成稿，而是为了做深度选题讨论。
3. 用户愿意先确认专家人选。

读取：

```text
/Users/codemao/.cc-switch/skills/dontbesilent2025-dbskill-dbs-chatroom/SKILL.md
```

遵循它的原流程，不要绕过确认步骤。

## 自动路由记录格式

最终文档写：

```markdown
## 自动路由记录

| 路由门 | 结果 | 理由 | 处理 |
|---|---|---|---|
| 问题门 | 调用 dbs-good-question / 跳过 |  |  |
| 概念门 | 调用 dbs-deconstruct / 跳过 |  |  |
| 角度门 | 进入 Mini Chatroom / 跳过 |  |  |
```

理由要具体，不要写「不需要」。写成：

- 「本文问题已有具体人群、场景、冲突和反馈，跳过。」
- 「解决方案承担论证重量，且容易被理解成 PPT，调用概念拆解。」
- 「Q1 和 Q2 分差 1 分，目标读者不同，进入 Mini Chatroom。」
