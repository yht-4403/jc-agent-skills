# v5 小红书 DBS 风格写作规则

## 明文规则和推导规则

DBS 明文规则包括：

- 内容要先有明确选题。
- 知识博主要把事情搞清楚、说清楚。
- 好问题要先钉现象、暴露冲突、给反馈入口。
- 概念要拆到使用场景，能用大白话说清楚。
- 开头要独立工作，有话题、Hook、可信度，不直接把答案说完。

v5 推导规则包括：

- 正文默认使用「问题 → 常见误区 → 机制 → 例子 → 动作」。
- 一篇只选一个问题原子。
- 不把知识库结构直接搬到小红书正文。
- 如果问题、概念、角度不稳，就先自动路由校准，再成稿。
- 不为了匹配作者身份、账号定位或发布渠道新增例子。

推导规则不是 DBS 原作者原话，是为了让知识库材料适配小红书首屏和阅读行为。

## 核心文风

### 1. 先筛人

开头不是解释文章，而是筛选目标读者。

弱：

```text
这篇文章主要讨论销售解决方案的重要性。
```

强：

```text
这篇只写给一种销售新人：客户说「发我看看」以后，你就真的回去做资料了。
```

### 2. 先钉场景，不先讲道理

弱：

```text
销售新人要具备方案能力。
```

强：

```text
客户问你「你们和另一家有什么区别」时，你以为他要技术说明，其实他可能在找下一次沟通的理由。
```

### 3. 大词改成动作

弱：

```text
解决方案型销售的核心是连接资源和客户需求。
```

强：

```text
你要做的不是把产品讲完，而是把客户下一步要判断什么问出来。
```

### 4. 判断必须有信号

弱：

```text
客户认可你的方案。
```

强：

```text
客户愿意再约一次、愿意给材料、愿意让关键人一起听，才说明你的方案进入了他的真实决策。
```

### 5. 结尾落到下一步

弱：

```text
所以我们要不断提升自己的销售能力，成为更专业的人。
```

强：

```text
下次客户再说「发我看看」，先别急着做资料。先问一句：你这次主要想判断哪一点？
```

## 正文骨架

### 第一段：问题筛选

目标：让目标读者马上知道这篇是不是写给自己。

可用句式：

```text
这篇只写给一种人：...
如果你也经常卡在这里，问题通常不是...
真正麻烦的是...
```

### 第二段：常见误区

目标：指出读者的默认动作为什么有问题。

可用句式：

```text
很多人会把这句话理解成...
所以第一反应是...
但这个动作最大的问题是...
```

### 第三段：机制

目标：解释为什么误区会导致结果变差。

可用句式：

```text
因为在这个场景里，客户真正要判断的不是...
而是...
如果你只做了前者，就会失去...
```

避免连续使用「不是 X，而是 Y」。最多出现 1-2 次，后面换成因果链。

### 第四段：例子

目标：用一个场景把机制钉实。

可用句式：

```text
比如客户问...
新人最容易...
更好的处理方式是...
```

例子只选一个。不要为了完整把多个案例都放进去。

### 第五段：动作

目标：给读者下一次可执行的动作。

可用句式：

```text
下次遇到这个场景，可以先问三个问题：
1. ...
2. ...
3. ...
```

动作必须能在现实沟通中说出口。

### 第六段：收束

目标：用一句边界判断结束，不升华。

可用句式：

```text
所以这件事不是让你少准备，而是让你先确认客户到底要判断什么。
```

## 小红书首屏规则

前 3 句必须完成三件事：

1. 圈出人群。
2. 点出场景。
3. 暗示常见做法有问题。

不要在前 3 句做：

- 背景铺垫
- 概念定义
- 作者自我介绍
- 长篇价值宣言
- 完整答案

## 标题规则

每次给 5 个标题候选。

要求：

- 不超过 20 字，含标点。
- 至少覆盖 3 种触发器：认知冲突、好奇缺口、身份代入、场景条件、恐惧损失、争议挑衅。
- 标题不说完答案。
- 标题围绕问题、场景、冲突，不围绕抽象概念。

## 禁用表达

正文尽量删除：

- 「本文将」
- 「我们需要」
- 「至关重要」
- 「赋能」
- 「闭环」
- 「底层逻辑」
- 「核心抓手」
- 「本质上」
- 「归根结底」
- 「认知升级」
- 「打造能力」
- 「持续迭代」
- 「你值得」
- 「希望对你有帮助」

不是完全不能用，而是用了就要检查：能不能换成动作、场景、反馈。

## 知识库痕迹清理

发布稿正文不要出现：

- 作者观点：
- AI 推断：
- 个人应用建议：
- 风险提醒：
- 和其他资料的联动：
- 今日练习：
- 下次任务建议：

这些可以放在决策记录，不放正文。

## 禁止额外迁移

成稿只服务主题本身，不服务作者身份、账号定位或发布渠道。

禁止：

- 判断这篇适合哪个发布渠道。
- 为了贴合作者身份或商业身份额外加例子。
- 把原文主题强行转成作者个人反思或个人复盘。
- 在正文中写作者身份、账号定位或发布渠道适配建议。

允许：

- 原文已经有的行业、案例和应用场景。
- 为了让机制更清楚而补一个中性场景，但必须贴合主题本身，不能迁移到作者身份。

## 质检问题

成稿后逐条问：

1. 如果只看前 3 句，目标读者会不会觉得「这说的是我」？
2. 这篇是不是只解决一个问题？
3. 有没有一个具体场景支撑全文？
4. 有没有把大词换成动作？
5. 有没有告诉读者下一次具体怎么做？
6. 有没有把个人观察写成普遍规律？
7. 有没有为了完整性塞进知识库材料？
8. 结尾是不是在行动上停住，而不是升华？
9. 自动路由有没有真的改善问题、概念或角度？
10. 有没有为了调用 DBS 而调用 DBS？
11. 有没有为了适配作者身份、账号定位或发布渠道而添加额外例子？
