# 原始制品优先的“理解感”讲解

当任务重点是帮助读者理解一个复杂技术或系统机制，并且存在可安全读取的代码、报文、日志、截图或运行结果时，默认读取本文件，不等待用户主动说“小白”“真实体感”或点名某个 Skill。用户明确要求真实代码、接口输入输出、日志、截图或抓包时，只是进一步提高原始制品的优先级。

这是一套 JC 偏好的讲解协议，不是宣称对所有读者都成立的教学定律。目标是让读者同时获得三种感觉：我看见它真实存在、我能沿着过程走一遍、我能自己说出其中的关系。

## 默认节奏

```text
一句待验证的判断
→ 一份原始制品
→ 只高亮 1～2 个关键点
→ 一张抽象图或最小关系说明
→ 回到原始制品重新认一次
→ 留一个动作、代价、判断题或仍未解决的问题
```

长文大约每 300～500 字重新落地一次，让读者再次接触代码、报文、日志、截图或可执行动作；这是节奏参考，不机械计数。简单问题可以只走一个缩短循环。

以下场景不强制走完整循环：一句话定义、用户只要结论、纯执行或修复任务、只优化一张既有图，以及面向负责人快速拍板而非教学的验收报告。它们仍要保持事实与模拟标注，但不要为了展示方法增加无关篇幅。

## 什么算原始制品

优先级通常是：

1. 用户提供或仓库中真实存在的源码片段，并附文件与行号；
2. 实际运行命令得到的终端输出、日志、测试失败或状态变化；
3. 真实接口的请求、响应、响应头或流式事件；
4. 经过授权和脱敏的截图、网络记录或监控片段；
5. 无法安全实测时构造的最小演示数据，但必须明确写“模拟响应”“假设案例”或“仅展示数据形状”。

不要把依据真实接口格式手写的 JSON 说成“真实调用结果”。如果只运行了翻译器而没有请求上游，要分别说明“转换过程已实跑”和“上游响应为模拟”。

## 圈选和高亮

原始制品不能整块扔给新手。第一次保留足够上下文，第二次只指出真正改变理解的 1～2 处。

- 源码：先给连续的短片段，再用行号、箭头或片段下方说明指出入口、状态变化或跨文件交接；不要在声称“原始代码”的块里插入并不存在的注释。
- JSON/HTTP：先给合法、可复制的原始报文，再单独摘出关键字段；不要为了高亮把第一份 JSON 改成不可执行格式。
- 日志：保留必要时间戳、级别、requestId 和前后事件；高亮导致判断变化的那一行，不只截最终 `success`。
- 截图：保留窗口、路径、时间或环境等证据上下文；每张图圈 1～2 处。敏感信息必须不可逆遮盖，不能使用可还原的半透明色块。
- 命令：同时给可复制文本和预期观察点，让读者能在自己的环境复现。

## 抽象图放在中间

图的职责是压缩刚刚看见的关系，不是替代证据。先让读者在原始制品里撞见字段、分支或错误，再用流程图、时序图、状态图或三列表解释它们怎样连接。

图后必须回到同一份制品，重新指认：

- 图里的账号调度器，对应哪段选择代码；
- 图里的 429 冷却，对应哪条响应头和哪次状态变化；
- 图里的“反向翻译”，对应响应 JSON 的哪些字段；
- 图里的前后端交接，对应哪个真实路由和参数。

读者能把图中节点重新映射回代码或报文，才算这一轮完成。

## 真实体感来自“不那么干净”的地方

在安全、授权和篇幅允许时，优先保留一个有解释价值的意外：多出来的字段、一次 429、一次重试、一个缓存命中、半成功状态或失败日志。它比只有成功终态更容易暴露设计为什么存在。

“失败证据通常更有教学价值”是讲解偏好，不是“失败截图必然比成功截图贵十倍”的量化研究结论。不要为了制造戏剧性伪造失败，也不要对生产系统故意触发高风险错误。

## 不替读者关门

可以在开头给一句待验证的判断，但深度讲解的结尾不再重复宣布“所以本质上就是……”“归根结底……”“一句话总结……”。这些句式容易替读者完成最后一次抽象。

优先用以下方式结束：

- 动作：让读者改一个参数、发一次请求或在源码中继续找下一跳；
- 代价：指出删掉某一步后会出现的具体后果；
- 判断：给一个相邻场景，让读者判断同一机制是否仍成立；
- 未解：保留一个真实存在、需要更多证据才能回答的问题。

不是所有内容都必须开放式收尾。操作手册、安全指令、故障处置和需要明确拍板的材料仍要给清楚结论，不能为了“不关门”牺牲可执行性。

## 交付前检查

- 是否至少有一个可核对的真实代码、报文、日志、截图或实际运行结果？
- 实测、来源事实、合理推断和模拟数据是否明确区分？
- 是否只高亮了真正改变理解的 1～2 处，而不是满屏标注？
- 抽象图能否逐点映射回原始制品？
- 是否给了复制命令、文件行号或其他复现入口？
- Token、Cookie、邮箱、手机号、内部地址和个人标识是否完成不可逆脱敏？
- 结尾是否给读者留下了一次自己的判断或动作，而不是重复喂结论？

## 最小回归案例

请求：“解释一个 CLI/OAuth 网关怎么包装成兼容 API，画图，也拿真实接口输入输出举例。”

合格表现：读取实际路由或转换代码；展示一份实际执行过的输入与转换结果；如果没有调用真实上游，明确标记上游响应为模拟；高亮少量关键字段；画图后重新指出图中节点对应哪段代码或报文；最后给一个可复现动作或仍需验证的问题。

失败表现：只画一张整洁架构图；手写一份看似真实的 JSON 却不说明来源；罗列很多代码但不指出读者该看哪两行；结尾再次用“所以本质上是”替读者重复结论。

负向案例：“一句话告诉我什么是幂等。”这种短问题不强制抓包、截图和完整循环，按快速解释处理，避免为了展示方法把简单问题写成长文。

## 默认触发与相邻路由

- 应自动触发且不依赖关键词：“这个开源项目为什么能把 OAuth 账号包装成 API？”“429 之后为什么会切换账号？”
- 应由 `code-chain-study-comments` 主导并带入本协议：“从前端按钮一路追到数据库，带我读懂这条代码链路。”
- 应由 `jc-learning-map` 主导：“先帮我画出学习 Kubernetes 的全貌和当前卡点。”
- 不应抢路由：“修复这个空指针”“把这张 Mermaid 调整得更清楚”“一句话解释幂等”“把这段对话原样保存成文档。”
- 面向发布验收或决策的报告，可以引用原始证据，但不把整篇报告改造成教学课；只有解释难点的局部段落使用完整循环。
