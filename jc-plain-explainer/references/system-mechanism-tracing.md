# 企业与系统机制追踪

适用于 SaaS、供应链、电商、支付、权限、后端、数据处理、并发、幂等、异步任务和多系统协作。

## 选择有冲突的业务切片

不要只讲“下单→发货→收货”这类人人已经知道的主线。选择能暴露隐藏机制的一次事件：

- 用户取消订单时，仓库刚好完成拣货。
- 员工被停用时，浏览器会话和 API Token 仍然有效。
- 两个人同时编辑同一份配置并提交。
- 支付成功消息重复到达三次。
- 文件上传成功，但数据库记录写入失败。
- 审批人在审批途中被移出组织。

## 固定初始条件

至少给出：

- 具体对象：订单号、账号、配置版本、文件名或任务编号。
- 参与角色：用户、运营、仓库、支付平台、系统模块或管理员。
- 事件时间：按秒或先后顺序说明。
- 开始状态：已经支付、等待拣货、仍在登录或版本为 v3。
- 关键限制：最后一件库存、只能退款一次、离职后必须立即失去权限。

## 状态追踪表

| 时刻/事件 | 外部可见结果 | 状态变化 | 内部动作 | 保护的约束 |
| --- | --- | --- | --- | --- |
| 事件发生 | 用户看到什么 | 从 A 到 B | 校验、写入、通知等 | 防止什么错误 |

先用业务语言写清状态，再在需要时补数据库字段或枚举值。

## 反事实解释

用下面四种测试解释工程复杂度：

1. **删除一步**：如果不校验、不记录、不撤销，会发生什么？
2. **重复一次**：用户连点、消息重放或任务重试会怎样？
3. **同时发生**：两个角色同时修改同一对象，谁成功？
4. **只成功一半**：钱退了但库存没释放，下一步怎么办？

先展示具体错误，再命名机制：

| 真实问题 | 之后再引入的术语 |
| --- | --- |
| 连点三次不能退三次钱 | 幂等 |
| 取消与出库不能都成功 | 并发控制、状态机 |
| 钱退了但库存没释放，需要补做 | 补偿、最终一致性 |
| 能查出谁何时改了什么 | 审计日志 |

## 演示案例：取消订单撞上仓库拣货

明确标注这是演示案例：

```text
订单 O-240618-031，商品只剩 1 件。
10:00 用户支付成功。
10:02 仓库收到拣货任务。
10:03 用户点击取消。
10:03:01 仓库员工扫码确认拣货。
```

表面问题只有“能不能取消”，内部需要处理：

1. 检查订单当前状态是否仍允许取消。
2. 确保取消和拣货只有一个状态变更成功。
3. 把重复点击识别为同一次取消，避免重复退款。
4. 如果仓库已拣货，改走撤回或物流拦截。
5. 如果退款成功但库存释放失败，记录并重试补偿。
6. 保存状态变化和操作者，供投诉、资金和库存对账。

讲解重点不是罗列六个专业名词，而是让读者看到：用户的一次点击同时改变资金、库存、仓库任务和订单状态，因此不能用一次普通更新安全完成。

## 解释“为什么开发需要这么久”

把工作拆成可验证责任，而不是强调代码量：

- 正常路径是否正确。
- 所有允许和禁止的状态变化是否明确。
- 重复请求是否只产生一次效果。
- 并发冲突是否有唯一结果。
- 跨系统部分失败后能否恢复。
- 权限、审计、告警和人工处理是否完整。
- 历史数据和旧客户端是否兼容。
- 每条关键路径是否有测试和观测手段。
