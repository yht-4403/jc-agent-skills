# 真实案例驱动讲解

适用于陌生行业、专业知识、抽象概念和需要从零建立整体认识的内容。

## 核心方法：一件事走到底

不要先罗列行业术语。选择一个最小但完整的业务对象，让它从开始走到结果：

- 招聘：一个候选人从看到职位到收到结果。
- 电商：一笔存在退款或缺货问题的订单。
- SaaS：一个企业成员从被邀请到离职停用。
- 内容运营：一篇内容从选题到发布再到复盘。
- 开发：一次请求从进入系统到返回结果。

案例应包含：

- 明确对象，而不是泛称“用户”或“数据”。
- 初始条件，例如时间、状态、数量、角色和限制。
- 一个真正需要解释的矛盾，而不是毫无阻力的流水账。
- 最终结果，以及读者能观察到的证据。

## 渐进放大

### 第一层：30 秒主线

只回答：

```text
谁遇到什么事
→ 做了什么
→ 中间最大的变化或冲突
→ 最后得到什么结果
```

### 第二层：关键机制

只展开满足至少一个条件的隐藏步骤：

- 改变了业务对象的状态。
- 发生了责任或所有权交接。
- 保护了资金、库存、权限、质量、合规或证据。
- 失败后需要补偿、重试、撤销或人工介入。
- 省略后会让读者无法理解成本或设计理由。

### 第三层：专业实现

用户需要继续深入时，再解释具体工具、数据结构、接口、算法、规则或专业术语。

## 双轨表达

复杂企业逻辑优先并排说明：

| 用户/业务能看到什么 | 内部角色或系统实际处理什么 |
| --- | --- |
| 发起操作、等待、看到结果 | 校验、占用、交接、记录、重试、补偿 |

双轨不是为了把所有后台细节都列出来，而是把“看起来只有一步”与“实际为什么需要多步”对应起来。

## 每个关键步骤的六问

1. 谁或什么事件触发？
2. 触发前是什么状态？
3. 这一步具体改变什么？
4. 完成后是什么状态？
5. 为什么不能省略？
6. 省略、重复或失败会出现什么可观察后果？

避免回答成“提高稳定性”“方便维护”“支持扩展”。必须指出具体后果，例如重复退款、库存仍被占用、离职员工继续访问客户资料、招聘方无法判断候选人是否真正负责过项目。

## 讲解顺序

```text
真实问题
→ 完整案例
→ 关键机制
→ 失败或反事实
→ 专业术语
→ 换场景应用
```

不要先给一页概念定义，再在末尾补一个例子。

## 类比使用门槛

优先顺序：

```text
用户自己的材料
→ 当前行业的典型事件
→ 相邻的熟悉场景
→ 跨行业类比
→ 库存式万能比喻
```

只有当前场景仍然无法说明抽象关系时才使用类比。类比最多承担一个核心关系，理解后立即回到真实对象；可能误导时说明边界。
