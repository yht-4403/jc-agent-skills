# 通俗机制讲解

把抽象结论改写成可跟随、可验证的真实过程。不要只告诉读者“应该做什么”，要让一个具体对象完整经历一次事件，并解释关键步骤为什么存在。

## 选择讲解模式

先判断问题属于哪一类，只读取对应参考文件：

- 简单知识点或短问题：使用本文件的“快速解释”，不强行展开完整流程。
- 陌生行业、抽象概念或需要完整入门：读取 `references/case-driven-explanation.md`。
- SaaS、供应链、电商、支付、权限、后端、数据、并发、状态或企业隐藏流程：读取 `references/system-mechanism-tracing.md`。
- 简历、面试、项目经历、工作成果或“具体怎么写”：读取 `references/experience-evidence-reconstruction.md`。
- 制度、政策、业务规则、审批、资格判断或例外处理：读取 `references/policy-and-rule-explanation.md`。
- 长文、对外材料、类比较多或用户强调自然中文：读取 `references/natural-chinese-style.md`。
- 对技术或系统机制做深度解释时，只要有可检查的代码、报文、日志、截图或运行结果，就默认读取 `references/artifact-first-understanding.md`，不等待用户说“真实体感”或其他触发词；简单短问答按“快速解释”缩短处理。
- 只有在维护本 Skill、解释设计依据或用户要求论文来源时，读取 `references/learning-science-evidence.md`。

如果问题横跨多类，选择一个主模式，其他参考文件只补充必要部分。不要把所有模板机械拼在一起。

## 与相邻 Skill 的默认分工

- 主要任务是跨文件追踪调用链或添加学习注释：由 `code-chain-study-comments` 主导，并默认带入本 Skill 的原始制品协议。
- 主要任务是先看领域全貌、定位卡点：由 `jc-learning-map` 主导；只有展开当前卡点时进入本 Skill。
- 主要任务是沉淀、保存、发布或形成评审文档：由 `jc-knowledge-capture` 主导；解释性章节按本 Skill 组织。
- 主要任务只是新增或优化 Mermaid、表格和清单：由 `jc-markdown-visual-writer-latest` 主导，不强制补一篇机制讲解。
- 主要任务是修代码、执行操作、排查故障或给出明确决策：先完成任务；用户同时要求理解原因时，再用本 Skill 补充解释。

## 真实体感优先

当原始代码、接口报文、日志、截图或实际运行结果可获得时，不要只给加工后的架构图和口头案例。默认走一次短循环：

```text
一句待验证的判断
→ 原始制品
→ 高亮 1～2 处
→ 抽象图
→ 回到原始制品重新指认
→ 一个动作、代价、判断题或未解问题
```

图用于压缩关系，不能代替原始证据。真实材料无法安全取得时，使用明确标注的模拟数据，并分别说明哪些步骤实际运行过、哪些结果只是演示。

## 核心工作流

1. **确定真正要讲懂的问题**
   - 判断读者已经知道什么、卡在哪里、理解后准备做什么。
   - 信息不足但不影响主线时，用明确假设继续；会改变结论时再询问。

2. **选择一个贯穿案例**
   - 优先使用用户提供的真实材料。
   - 其次选择当前行业里最典型的一次任务，例如一笔退款、一次员工离职、一条简历经历、一次审批。
   - 不要为了通俗而优先跨行业比喻。
   - 构造案例时标注“假设案例”或“演示数据”，不得冒充真实事实。

3. **先走用户能感受到的主线**
   - 用 3–7 步说明从哪里开始、发生什么、最后得到什么。
   - 只保留第一遍理解必需的角色和动作。

4. **逐点展开隐藏机制**
   - 只展开会改变结果、保护约束、造成成本或引发误解的步骤。
   - 每个关键步骤回答：谁触发、之前是什么状态、具体做什么、之后如何变化、为什么必须有、不做会出现什么具体结果。

5. **加入一次冲突或失败模拟**
   - 优先选择最能解释设计必要性的情况：重复操作、同时发生、部分成功、权限变化、超时、撤销、数据不一致。
   - 用时间、人物、对象、数量和状态讲故事，不只列抽象异常名词。

6. **最后再引入术语**
   - 先让读者看到问题和处理方式，再说明它叫幂等、状态机、责任边界、证据链或其他专业名称。
   - 第一次出现术语时用一句人话解释，后面正常使用术语，不持续幼化表达。

7. **按需选择视觉表达**
   - 图能减少读者在角色、时间、状态或分支之间来回对照时，读取 `../jc-markdown-visual-writer-latest/SKILL.md`。
   - 图只负责呈现已经想清楚的关系，不能代替机制解释。

8. **用可检验的方式收束**
   - 点出最容易混淆的地方。
   - 给出一个换场景判断、复述问题、检查清单或下一步动作；不要只问“懂了吗”。
   - 深度讲解不在结尾重复“所以本质上是”“归根结底”“一句话总结”。需要明确结论的操作、安全和决策材料除外。

## 快速解释

简单问题默认使用以下最小结构，按需删减：

1. 一句话说明它解决什么问题。
2. 用一个具体场景展示它何时出现。
3. 说明关键机制和一个“不这样会怎样”。
4. 给出准确术语或行动建议。

不要为了展示方法而把简单问题写成长文。

## 真实性与精度

- 不编造用户经历、业务数据、指标、公司规则或系统行为。
- 缺少关键事实时，使用 `[待补充]`、范围表达或追问，不擅自补成漂亮成果。
- 区分“材料已经证明”“基于材料推断”“为了讲解构造的假设案例”。
- 通俗不是删除关键约束。权限、资金、库存、合规、并发和失败补偿不能被一句“系统处理”带过。
- 完整链路不等于穷举全部实现，只展开对当前问题有解释价值的细节。

## 输出风格

- 优先使用当前行业真实的人、对象、动作和结果。
- 少用“你可以把它想象成”“本质上”“赋能”“抓手”“闭环”“承载”等模板化表达。
- 多写“谁做了什么、状态怎么变、为什么、少了会怎样”。
- 一次解释尽量只使用一个贯穿案例，不在多个类比之间跳转。
- 结论先行，但不要只给结论；用事实链把结论撑起来。
