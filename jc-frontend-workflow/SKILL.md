# JC Frontend Workflow

按 JC 确认的流程推进前端重设计：

**看现有页面和真实任务 → 拆参考站 → 确定设计方向 → 做独立原型 → 看截图和实际交互迭代 → 固定颜色、字体、间距与组件规则 → 分批替换正式页面。**

## 七步流程

1. **看现有页面和真实任务。** 运行页面，记录截图，确认谁在什么场景使用、最常完成什么任务；读清现有入口、状态与接口依赖。区分展示页面和工作工具页，保留有效功能。
2. **拆参考站。** 优先使用用户给出的参考，缺少参考时按任务寻找。按区块记录截图及布局、字体、间距、颜色、组件状态和关键交互；写清借什么、为什么适合，不复制品牌资产和业务承诺。已有可信拆解可复用并标注日期。
3. **确定设计方向。** 用一句话写出页面气质和核心视觉选择，明确内容主次、密度和主操作。用户已有明确偏好就沿用；只有会改变产品定位或核心功能的分歧才追问。实现前记录信息、层次和颜色预算，可用 `jc-frontend-uiux` 辅助。
4. **做独立原型。** 在项目允许的位置建立独立 HTML 或预览路由，验证代表性页面和关键状态。布局、排版和内容可以重构；把模拟数据标清，不把模拟状态说成接口已经接通。原型中的新增能力不自动变成正式开发范围。
5. **看截图和实际交互迭代。** 先看成品，再判断实现。检查构图、排版、真实素材、操作反馈、长内容和失败状态；默认迭代一到两轮，优先修影响最大的差距。浏览器验证默认无头，截图保存到文件；没有浏览器时明确未验证，不能用静态检查代替交互验证。
6. **固定颜色、字体、间距与组件规则。** 将原型中已验证的选择写入项目现行设计规范和统一 Token（设计变量）。固定基础值、语义角色和组件状态的对应关系，包括默认、悬停、按下、焦点、禁用、加载与错误；核对字体可用性、对比度和响应式。需要规范来源时读 [设计规则来源说明](references/design-system-notes.md)。已有规范优先，不强行引入新框架或算法。
7. **分批替换正式页面。** 按公共样式与组件、代表页面、同类页面的顺序迁移。每批对照原型检查视觉和真实主流程，运行项目要求的构建与检查；能通过真实接口完成任务后，才标记完成。外部发布与推送仍按用户授权范围执行。

## 最小记录

在项目已有文档位置维护一份简短记录，已有计划就续写：当前步骤、参考与截图、已选方向、已完成并验证的内容、尚未验证的内容、下一步。恢复任务先读这份记录，不从头重做。历史规范只解释背景，取值以项目现行规范为准。

用户只要求找流程、做方案或做原型时，交付到对应步骤即可。常规审美和实现选择自行推进，不为每个步骤重复请求确认。

## 可选配合

- `frontend-design-teardown`：需要深入拆解参考站时使用。
- `daring-design-iteration` / `impeccable`：需要探索视觉方向、评审或打磨时按需使用。
- `jc-frontend-uiux`：设计预算、信息精简和颜色量化检查。

这些工具可用时再调用；七步流程本身不依赖它们全部安装。不自动安装、更新或激活其他 Skill。
