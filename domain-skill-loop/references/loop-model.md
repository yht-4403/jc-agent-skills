# Loop 模型

## 本质

Loop 不是 `while true`，也不是反复把同一句提示发给模型。它是一个带证据门的状态机：每次只推进一个合法状态，并把状态写到对话之外。

```text
pending → in_progress → extracted → reviewed
               ↑            │
               └── fail ────┘
```

## 六个部件

1. **Goal**：可验证的终点。
2. **Queue**：下一项从哪里发现；本工程使用 chunk-status。
3. **Worker**：完成一次有边界的语义工作。
4. **Verifier**：机械校验 + 独立语义复核。
5. **Memory**：loop.json、batches.jsonl、loop-events.jsonl 与知识资产。
6. **Stop Rule**：质量门、预算、重试上限、无进展、权限或完成。

缺少任何一项都可能退化：没有 Queue 会重复工作；没有 Verifier 会扩大错误；没有 Memory 会在换上下文后失忆；没有 Stop Rule 会无限消耗。

## 三层循环

- **内层批次循环**：处理 4–8 个文本块，失败只返工该批。
- **阶段循环**：抽取 → 路线 → 场景 → Skill → 评测。
- **外层 Goal**：直到发布条件满足，或遇到必须由人决定的阻断。

## 为什么使用文件状态

聊天上下文会增长、压缩或切换，不能充当可靠账本。Loop 的事实来源必须是工程文件；对话只用于当前批次推理。重新进入时先读 `status`，不要试图从聊天历史恢复进度。

## 质量门

- `sample`：首个完整批次复核通过，确认粒度和协议。
- `80`：完整复核覆盖达到 80%，检查路线是否漏掉大环节。
- `100`：所有目标块 reviewed/skipped，确认跳过原因后进入合成。
- `release`：路线、场景、References、Skills、评测和引用链全部通过。

质量门是暂停点，不是成功文案。没有证据就不能确认。
