# JC Markdown Visual Writer

目标是把文档写得清楚，不是展示 Mermaid 全家桶。默认用简单、稳定、可读的结构。

## 修改已有 Mermaid 前先过门禁

优化已有 Mermaid 时，默认先判断“是否真的需要改”，不能把统一换色、降低饱和度或改成当前偏好的模板当成优化。

1. 已经使用 `classDef`、`style`、分组或多类颜色，而且颜色正在区分角色、系统、阶段、产出或技术层级时，默认**完全不改**；即使它与其他文档风格不同，也不能擅自柔化配色、减弱描边或重画结构。
2. 只有默认黑白样式、视觉上无法区分动作与判断的简单流程图，才考虑增加语义颜色；颜色必须帮助识别场景、动作、判断、边界或结果，不能只为“更好看”。
3. 用户只要求视觉优化时，保持节点、文案、顺序、方向、连线和拓扑不变。压短文案、拆图、合并节点、改变方向或重组信息属于结构优化，必须由用户明确要求，或有清楚的阅读障碍证据。
4. 如果现有图已经清楚，交付结论可以是“保持原样”。不为制造前后对比而强行生成优化版。
5. 新写的并列总结可以使用卡片式总结树；不要拿这种样式改造原本清楚的流程图、技术展开图或全景图。
6. 配色统一只统一“颜色代表什么”，不要求所有图使用同样数量、面积或强度的颜色。新图中，`flowchart TD` 和 `stateDiagram-v2` 优先使用语义色，`graph LR` 按需使用，`sequenceDiagram`、`pie`、`erDiagram` 保持克制；具体规则见 `references/mermaid-patterns.md`。

## 默认偏好

优先级从高到低：

1. `graph LR` + `subgraph`：主线从左到右，关键节点用细节盒子展开。
2. `graph LR` / `flowchart LR`：表达树状分支、左右展开的业务逻辑。
3. ASCII 树：表达同一份逻辑的纯文本兜底，尤其适合知识库和聊天输出。
4. `flowchart TD`：表达标准流程、开始结束、判断和处理步骤。
5. `sequenceDiagram`：表达用户、界面、逻辑层、后端、音频模块等角色交互。
6. `stateDiagram-v2`：表达对象或页面状态变化。
7. 正常 Markdown 无序列表、序号列表、表格、检查清单：承载细节、规则和任务。

只在材料明确需要时使用：

- `erDiagram`：数据库表、实体关系、字段关系。
- `pie`：占比数据，类目少于 6 个时使用。

默认不要主动使用：

- `mindmap`
- `classDiagram`
- `journey`
- `gantt`
- `quadrantChart`
- `requirementDiagram`
- `gitGraph`
- `architecture`
- `block`
- 其他高级 Mermaid 图种

除非用户明确点名，或者材料本身强烈需要。

## 资源路由

- 需要新增 Mermaid、修改已有 Mermaid 或进行配色优化时，读取 `references/mermaid-patterns.md`。
- 需要 ASCII 树、普通列表、表格、检查清单时，读取 `references/text-structures.md`。
- 如果任务来自 `jc-knowledge-capture`，先遵循 `../jc-knowledge-capture/SKILL.md` 的保存、命名和笔记类型规则，再用本 Skill 优化文档表达。
- 如果任务来自 `plain-explainer`，先遵循 `../plain-explainer/SKILL.md` 的案例选择、讲解顺序和真实性规则；本 Skill 只负责选择合适的视觉结构，不另行注入技术角色、状态或类比。
- 当图用于解释有可核对实现的复杂机制时，默认读取 `../plain-explainer/references/artifact-first-understanding.md`：图放在“原始制品 → 局部高亮”之后，并在图后回到同一制品完成映射，不等待用户主动索要真实代码或接口输入输出。只新增或优化既有图、以及以快速拍板为目标的评审任务，不强制套完整教学循环。

## 选型规则

- 有大量“是否、如果、缺少、成功、失败、兜底”：优先 `graph LR`，再给 ASCII 树。
- 有“宏观主线 + 底层细节/黑盒逻辑/硬核参数”：优先 `graph LR` + `subgraph` 细节盒子。
- 有严格先后顺序：用 `flowchart TD` 或序号列表。
- 有多个系统/角色来回调用：用 `sequenceDiagram`。
- 有 `Idle / Running / Success / Error` 这类状态：用 `stateDiagram-v2`。
- 有数据库表、实体、字段：用 `erDiagram`。
- 有占比：用 `pie` 或表格。
- 只是要沉淀清楚：用无序列表、序号列表、检查清单，不强行画图。

## 30 分钟评审文档

当文档目标包含“新人快速上手”“30 分钟内完成技术评审”“尽可能减少文字”或“降低首次阅读心智负担”时，默认在同一文档内使用双层结构：

1. 第一部分写“30 分钟技术评审”，以图为主，只保留目标与边界、当前流程、目标流程、旧新对比、核心 Key/数据关系、简化 ER、开发依赖、关键决策、风险和验收结论。
2. 使用明显的 `---` 分割线结束评审主文。
3. 第二部分写“开发查询附录”，收纳完整接口、JSON、SQL、表字段、错误码、代码位置和测试用例；附录开头提供按角色查询导航，并注明不要求顺序阅读全文。
4. 评审主文负责“看懂并决策”，开发附录负责“实施时查细节”；详细内容不能反向侵入第一阅读路径。
5. 删除重复目标、重复流程、重复结论和不影响技术决策的管理性内容。内容应移动到正确层级，不因追求短而丢失开发契约。

第一部分优先采用 5 张左右核心 Mermaid 图和少量短表。每张图只回答一个问题；不要用一张超大时序图承载现状、目标、数据库、异常和排期。完整请求/响应 JSON、SQL/DDL、逐字段表结构、全量错误码、大段代码路径和逐仓测试用例默认不进入第一部分。

### 中文业务语义与英文契约分层

- 评审图、Key 关联图和具体数据流转图先写中文业务对象，例如“作品唯一标识”“报告编号”“公开访问令牌”“录制顺序”，不要让读者先记 `bcmkrHash/reportId/shareToken/slotIndex`。
- 英文变量最多集中在一张紧邻图表的“中文含义 / 开发字段 / 用途”对照表中；完整字段、JSON、索引和 SQL 放到详细接口或数据库章节。
- “一条数据如何贯穿系统”优先画中文 Mermaid，不重复展示长 Hash、完整数据库行、字段赋值块和响应 JSON。图只讲关联关系，精确契约通过章节引用查询。
- 真实 HTTP 路由、数据库和表名继续保留在需要核对实现的技术图中；纯业务理解图不为了显得专业而堆这些标识。
- 开发附录先删除与评审正文重复的流程、范围、结论、架构和排期，再删除重复的代码依据和后续阶段预留；全新接口的完整契约最后才考虑压缩。

## 输出习惯

- 复杂逻辑优先给“一张 Mermaid + 一段 ASCII 树/列表兜底”。
- 涉及可核对实现时，Mermaid 不能替代原始代码、报文、日志或截图；先让读者看见证据，再用图压缩关系，最后指出图中节点分别对应原始制品的哪里。
- 主线节点保持 4 到 8 个字；细节节点可以稍长，但不要写成小作文。
- `graph`/`flowchart` 需要显式标注先后顺序时，默认使用圈号 `① ② ③ … ⑳` 作为视觉锚点，例如 `A -->|"①：申请预签名"| B`。不要再写“步骤 1”“步骤一”或“第 1 步”。超过 20 步时优先拆图，不继续堆叠冷僻圈号字符。
- `sequenceDiagram` 默认使用 `autonumber` 表达交互顺序，不同时手写圈号，避免出现两套编号；只有用户明确要求 sequence 也使用圈号时，才移除 `autonumber` 并手工编号。
- 用 `-.->` 从主线关键节点连到细节盒子，表示“展开查看”，不要打断主流程。
- `subgraph` 内部优先加 `direction TB`，让细节从上到下展开。
- 可以少量使用中文 emoji 作为视觉锚点，但不要每个节点都堆表情。
- 图前只写一句它解释什么，图后补关键规则。
- 节点文字短一点，细节放列表里。
- 分支边上写清材料中的真实条件，例如 `B -- 条件不满足 --> C[说明原因]`。
- 列表层级不要太深，超过 4 层就改 ASCII 树。
- Mermaid 代码块里只放 Mermaid，不混解释文字。
- `flowchart`/`graph` 里不要用小写 `end` 做节点 ID。
- Mermaid 节点或连线标签不要以 `1.`、`2.`、`- `、`* `、`+ ` 等 Markdown 列表语法开头；部分 Markdown-aware Mermaid 渲染器会把它解析成列表并显示 `Unsupported markdown: list`。需要编号时优先改写为 `① ② ③` 圈号。
- 输出 `graph`/`flowchart` 后，检查 `[...]`、`{...}`、`(...)` 和 `|...|` 中是否存在以 `数字+句点+空格` 或项目符号开头的文字；存在则先改写再交付。错误与正确示例见 `references/mermaid-patterns.md` 的“兼容性红线”。
- 优先沿用材料中的人物、对象、动作和术语。不要因为模板示例存在，就把招聘、运营、制度等非技术内容改写成系统架构语言。
