# 需求问题树

用本文件建立批量盘问的决策依赖、覆盖范围和推荐答案。先从根问题开始；只有前置决定清楚后，才展开下游分支。

## 目录

- 使用规则
- 根问题：项目与业务

## 使用规则

1. 先从用户材料中填入已知事实，不重复提问。
2. 当前批次只包含前置条件已经满足的问题。
3. 下方每个项目是内部覆盖检查点，不对应一道用户问题；把相关检查点合并为一个需要拍板的决策卡。
4. 当前依赖层过宽时拆成同层子批次，先保持可扫描，再根据回答进入下游；不设固定题数。
5. 每题给出基于当前材料的推荐答案、关键假设和影响。
6. 推荐默认选择最小够用、可验证、可撤销且复用现有能力的方案；高风险结果优先保证正确、可追踪和可回退。
7. 用户回答后重新构建问题层，不提前固化后续问卷。
8. 不因某个维度常见就强制提问；确认不适用并记录原因即可。

## 根问题：项目与业务

这些问题决定其余分支，应优先确认。

### 项目背景与触发

- 现在发生了什么，为什么会提出这个项目？
- 当前怎样处理，最明显的问题是什么？
- 为什么现在做，不做会造成什么影响？
- 谁提出、谁负责、谁最终拍板？
- 有哪些会议纪要、现有页面、流程文件或历史数据可作为事实来源？

### 所处阶段

结合材料推荐一种最接近的描述，不要要求用户理解产品术语：

- 还在确认有没有真实需求；
- 准备做小范围试点；
- 已经有人使用，要补齐完整流程；
- 已正式运行，要扩大规模或提高效率；
- 要替换旧系统或迁移历史数据。

阶段会决定首期范围、成功标准、数据质量、上线和回退要求。

### 业务目标与价值

- 项目最希望改变哪个业务结果？
- 谁直接得到价值：用户、运营、销售、管理者还是合作方？
- 价值体现为增加收入、节省时间、减少错误、降低风险、改善体验或满足合规中的哪一种？
- 用什么现象判断值得继续投入？
- 有哪些结果不能为了主目标而被破坏？
- 不开发时，能否通过现有工具、人工流程或小试验验证核心假设？

推荐答案必须具体到可观察变化，避免“提升体验”“数字化”“提高效率”等无法验收的表述。

## 用户与体验流程

完成根问题后展开。

### 用户与场景

- 主要使用者是谁？是否还有运营、管理员、审核人、客服或合作方？
- 用户在什么时间、地点和设备上使用？
- 使用是一次性的、偶尔发生、定期发生还是每天高频？
- 用户为什么愿意开始，又可能为什么放弃？
- 新用户和老用户的过程是否不同？

### 当前与目标体验

按实际场景走一遍：

```text
使用前怎样知道 → 从哪里进入 → 系统怎样认出他 → 核心操作
→ 用户看到什么结果 → 以后怎样回来 → 出错时找谁
```

每一步检查：

- 用户想完成什么；
- 用户做什么；
- 用户看到什么反馈；
- 背后谁或哪个现有系统提供结果；
- 走不下去、退出、取消或重复操作时怎样处理。

## 范围、阶段与依赖

体验主流程清楚后展开。

- 本期缺少哪些能力就无法完成核心目标？
- 哪些步骤可以沿用现有系统或人工方式？
- 哪些明确不在本期？
- 哪些属于后续阶段，它们被什么结果触发？
- 功能之间有什么先后依赖？
- 是否有固定日期、预算、人员、供应商或政策约束？
- 如果必须缩小范围，最小可验证闭环是什么？

推荐优先形成完整但最小的用户闭环，不推荐交付一组彼此断开的页面。

## 角色、权限与后台

只有存在身份差异、数据隔离、后台工作或高风险操作时展开。

- 有哪些角色？每个角色为什么需要存在？
- 谁能查看、创建、修改、删除、审批、导出或代替别人操作？
- 用户能否看到其他人的信息？组织之间是否隔离？
- 哪些操作需要二次确认、审批或限制范围？
- 修改错误后能否知道谁在什么时候改了什么？
- 管理员后台每天实际要完成哪些工作，而不是笼统地“管理全部数据”？
- 离职、角色变化或权限收回时怎样处理？

最终形成角色—动作—对象—范围的权限说明，不让业务人员设计鉴权实现。

## 数据与业务规则

用户流程和角色清楚后展开。

- 用户会输入什么，结果数据从哪里产生？
- 哪个系统或负责人是最终可信来源？
- 哪些信息下次回来仍要看见？需要保留多久？
- 以前已经存在的数据怎么办？
- 是否需要导入、导出、同步或人工修正？
- 哪些规则决定资格、数量、价格、积分、权益、状态变化或有效期？
- 规则变化后，历史记录按旧规则还是新规则处理？
- 数据错误时谁有权修正，是否需要原因和记录？

涉及余额、积分、权益或库存时，继续确认扣减、返还、过期、重复提交、对账和人工调整。

## 使用规模与体验要求

目标用户和使用方式清楚后展开。优先询问业务可估计的范围，不要求伪精确数字。

- 总共可能有多少用户？首期、半年后和成熟阶段大概处于什么量级？
- 日常有多少人会使用？最高峰通常发生在什么事件或时间窗口？
- 峰值时大概会有多少人同时操作？不知道时，给出基于活动规模的区间建议并标注假设。
- 用户能接受等待多久？哪些动作必须立即看到结果，哪些可以稍后处理？
- 系统需要全天可用，还是只在活动或工作时间使用？
- 是否存在批量导入、集中发放、消息群发或活动开场等突发高峰？
- 用户量未来扩大多少时需要重新评估？
- 是否有弱网、手机扫码、老旧设备、无障碍、多语言或跨地区使用要求？

把答案写成业务场景，例如“活动开场后的十分钟会集中扫码”，不要只有脱离场景的并发数字。

## 异常、安全与合规

根据用户结果和数据类型选择分支。

- 用户连续点击、刷新、返回或重复扫码会发生什么？
- 操作进行到一半断网或失败，用户看到什么，业务结果是否改变？
- 用户取消、过期、退款、撤回或重新提交时怎样处理？
- 外部系统不可用时，是阻止操作、稍后重试还是人工处理？
- 是否可能被冒用、刷取、重复领取或越权查看？
- 是否涉及身份、联系方式、医疗、财务或其他敏感信息？
- 收集这些信息是否真的必要，谁能看，保留多久，怎样删除？
- 是否需要法务、隐私、安全、财务或业务合规负责人确认？
- 出现错误时，怎样追踪影响范围并修复用户结果？

## 运营、上线与验收

核心流程、规则和风险清楚后展开。

### 日常运营

- 谁维护内容、规则、名单、库存或权益？多久调整一次？
- 谁处理失败记录、投诉和人工修正？
- 运营人员需要查看什么数据，导出用于什么动作？
- 用户遇到问题从哪里获得帮助？

### 上线与变化

- 是试点、分批开放还是一次上线？
- 是否需要导入历史数据或兼容旧入口？
- 上线后看哪些信号判断正常？谁负责查看？
- 发现严重问题时，怎样暂停入口或回到原来的处理方式？
- 是否需要培训、通知、操作说明或客服准备？

### 验收与效果

- 主流程怎样算完成？
- 每个真实高风险失败场景应该看到什么结果？
- 哪些指标用于判断业务目标是否实现？多久复盘？
- 哪些开放问题必须在开发估时前确认，哪些可以在技术方案阶段确认？

## 完整性状态表

在每轮和最终文档中维护内部覆盖状态：

| 维度 | 允许状态 |
| --- | --- |
| 背景、阶段、目标、价值 | 已确认 / 需业务确认 |
| 用户、场景、体验流程 | 已确认 / 需业务确认 |
| 范围、分期、依赖 | 已确认 / 暂缓 / 需业务确认 |
| 角色、权限、后台 | 已确认 / 不适用 / 需业务或安全确认 |
| 数据、规则、历史处理 | 已确认 / 不适用 / 需业务或开发确认 |
| 用户量、峰值、体验要求 | 已确认 / 不适用 / 区间假设 / 需开发确认 |
| 异常、安全、合规 | 已确认 / 不适用 / 需专项负责人确认 |
| 运营、上线、回退、验收 | 已确认 / 暂缓 / 需业务或开发确认 |

禁止使用“未提及”作为最终状态；必须判断是不适用、暂缓还是需要某个负责人确认。
