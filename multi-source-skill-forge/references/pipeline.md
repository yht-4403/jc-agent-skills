# 八阶熔炼法 — 完整执行规范

本文件是 `SKILL.md` 的执行细则。**每一阶都有质量门，没过门不要进下一阶。**

---

## 阶 0 — 定盘（Charter）

**目标**：在读懂材料之前，先定清楚"为谁、为什么、要几个入口"。跳过这一步的后果是：拆出一堆漂亮的、但使用者永远不会调用的 skill。

**输入**：用户的材料 + 三个问题（见 SKILL.md §二）。

**产物**：`CHARTER.md`（模板 `templates/CHARTER.md`），必须包含：

```yaml
sources:                     # 来源清单，一条一个
  - source_id: src-a
    kind: book               # book|video|podcast|course|interview|article-set|docs
    title:
    author:
    year:
    uri_or_path:
    rights: user-provided    # user-provided|public-domain|licensed|unknown
    trust: primary           # primary|secondary|tertiary
    word_count:
    language:
profile:
  role:                      # 使用者是谁
  daily_tasks:               # 每天在做什么
  target_problem:            # 最想解决的那一个问题
  materials:                 # 最常处理的材料类型
  out_of_scope: []           # 明确不要的领域
entry_budget: 6              # 可发现入口总数上限（含 1 个 hub）
depth: full                  # fast | full
output_preference: mix       # hub | split | mix
```

**trust 分级口径**：
- `primary` — 作者本人的一手表达（原著、作者本人的访谈/课程）
- `secondary` — 整理、汇编、他人转述（别人的读书笔记、二手解读）
- `tertiary` — 聚合站、AI 转写稿、无法确认来源的转发

> 三级来源不是不能用，但**不能单独支撑一张能力卡**（见阶 3）。

**质量门**
- [ ] 至少 1 个来源，且每个来源都有可定位的原文（路径或链接 + 字数）
- [ ] 使用者画像四个字段（role / daily_tasks / target_problem / materials）都有实质内容，不是"普通人"
- [ ] 明确了入口预算与深度档位
- [ ] 若来源数 ≥ 2，已确认它们是**同一主题**（否则应当拆成两个独立项目，不要硬做三角）

---

## 阶 1 — 通读（Adler 分析阅读）

**目标**：真正读懂材料，尤其是**材料自身的局限**。没有这一步，拆出来的 skill 会把作者的盲点当真理一起打包。

**产物**：`OVERVIEW.md`（模板 `templates/OVERVIEW.md`）。

### 四步

**第 1 步 · 结构（Structural）**
- 这份材料属于什么类型？（方法论 / 实操手册 / 哲学 / 传记 / 访谈漫谈）
- 主旨用**一句话**说清 —— 必须真的能压缩到一句
- 若来源 ≥2：它们共同在回答哪个问题？各自从哪个角度切入？
- 主要部分如何构成整体？列出 3–7 个一级论点，标出关系（并列 / 递进 / 对比 / 反驳）

**第 2 步 · 解释（Interpretive）**
- **关键术语**：作者反复使用且有特定含义的词，给"作者本人的用法"定义，不是字典义
- **核心命题**：用你自己的话重述 5–15 条核心主张
- **论证链**：这些主张之间如何推导，作者用什么证据支撑

**第 3 步 · 批判（Critical）★ 最容易被跳过也最重要**

> Adler 原话：在没有找出论证中的错误之前，你不能不同意作者。反过来——**在找出作者的局限之前，你也不能完全同意。**

必须回答：
- **时代局限**：写于什么时期？哪些前提可能已经不成立？
- **立场盲点**：作者的身份 / 行业 / 文化背景让他忽略了什么？
- **未证明的假设**：作者把什么当成了不言自明、其实需要论证的东西？
- **最强反驳**：如果要用一句话反驳这份材料，最有杀伤力的论点是什么？

**这一步的产出直接成为每张能力卡 B（Boundary）段的来源。**

**第 4 步 · 应用潜力（Applicability）**
- 哪些内容可以卡化？（框架 / 清单 / 原则 / 决策程序）
- 哪些不适合卡化？（纯史料 / 纯故事 / 纯情绪 —— 但可作为其他卡的 example）
- 预估能力卡数量区间（不要硬凑）
- 从"最能赋能这个使用者"的角度给候选排序

**质量门**
- [ ] 主旨一句话说清
- [ ] 骨架列出 3–7 个一级论点
- [ ] 关键术语词典 ≥5 条
- [ ] **批判段至少列出 3 条作者局限**（做不到位不得进下一阶）
- [ ] 已向用户展示骨架并获确认

**常见翻车**
1. 跳过批判段 → skill 把作者偏见当真理
2. 写的是读后感而不是作者的骨架 → 自检"我在复述作者，还是在表达自己"
3. 术语用字典义 → 作者说"能力圈"和字典说"能力范围"不是一回事

## 阶 2 — 抽丝（5 路并行提取）

**目标**：不只用单一视角读一遍，而是**同时从 5 个角度扫描**，最大化候选覆盖率。

**为什么并行**：单一视角一定有盲区 —— 框架提取器找不到的"反例"，反例提取器会找到。且各提取器**必须独立判断**，否则阶 3 的"独立佐证"就是自欺。

**产物**：`candidates/frameworks.md`、`principles.md`、`cases.md`、`counter-examples.md`、`glossary.md`

**执行方式**（按宿主能力降级，三档均可，但产出格式不变）：

| 宿主能力 | 做法 |
|---|---|
| 支持并行 sub-agent | **同时** spawn 5 个，各给一份 `OVERVIEW.md` + 源文本 + 对应 extractor prompt |
| 只能串行 | 一次跑一个 extractor，**每跑一个前清空上一轮的判断视角**，只执行本轮职责 |
| 单会话单模型 | 逐 extractor 在独立段落中执行，明确写出"现在是第 N 路的职责，不受前几路影响" |

**长材料分块**（
超出单次可读时）：
1. 按自然边界切块（章节 / 卷 / 分 P / 讲次），单块 ≤5 万字
2. 每块都必须附带 `OVERVIEW.md` —— 它是判断"这段在全文中扮演什么角色"的锚点，不能省
3. 逐块提取，每条候选标注 `source_id` + `source_chapter`（有 chunk_id 一并发记录）
4. **块间汇总**：同一方法论在多块出现的合并成一条并保留**全部出处** —— 这些多出处恰好是阶 3 跨域验证的证据
5. 汇总后才写入 candidates

**上下文策略**（覆盖优先，不许牺牲覆盖率）：

| extractor | 分布特性 | 策略 |
|---|---|---|
| framework | 常跨章节隐性分布，需要全局视野 | **全量扫描** |
| principle | 散落全书，且需判断"是否反复出现" | **全量扫描** |
| case | 局部命中型，有明确文本锚点 | 可用检索式定位后取邻接块 |
| counter-example | 局部命中型，有警告性措辞 | 可用检索式定位后取邻接块 |
| glossary | 局部命中型 | 检索式 + 词频预筛 |

> 采用检索式时有一条硬门：**最终通过验证的候选相对全量扫描基线，漏检数必须为 0**。做不到就退回全量扫描。

**候选单元最小字段**
```yaml
- id: f01
  title: 逆向思维
  type: framework            # framework|principle|case|counter-example|term
  source_id: src-a
  source_chapter: 第三讲
  source_quote: |
    "反过来想，总是反过来想。"
  summary: |
    用自己的话 5–10 行
  tags: [decision, mental-model]
```

**质量门**
- [ ] 5 类 extractor 都跑过（速成档可只跑 framework + principle + counter-example，但必须在 STATE.md 注明）
- [ ] 每条候选都有 `source_id` + `source_chapter` + `source_quote`
- [ ] 引用 ≤150 字（英文 ≤100 词）
- [ ] 每条至少 1 个 tag
- [ ] **本阶不做筛选** —— 宁错杀，交给阶 3

**本阶不做**：不做筛选、不写 skill、不做跨单元链接。

## 阶 3 — 三角（验证 / 分级 / 争议 / 晋级）

全流程的质量枢纽。详细口径见 `references/verification.md`，此处只列流程：

1. 合并 5 个候选池为一个总池，去重（同一方法论被多路提取的合并并保留全部出处）
2. 对每条候选跑 **V1 跨源/跨域独立 → V2 预测力 → V3 独特性 → V4 时效与可执行**
3. 计算 **置信度等级**（A 跨源一致 / B 单源多域 / C 单源单域）
4. 读取 `CHARTER.md` 的画像，补 `profile_fit`：`core | merged | archived`
5. **源间分歧检查**：任一对来源在同一问题上立场不同 → 写一张 `conflicts/<id>.md` 争议卡
6. 分流写盘：
   - 四重通过 + profile 为 core/merged → `verified.md`
   - 四重未通过 → `rejected/<id>.md`，**必须写明挂在哪一项、为什么**
   - 四重通过但 profile 为 archived → `rejected/<id>-archived-for-profile.md`，标注"画像低相关归档，非知识失败"
   - 四重通过 → 跑**晋级门**，判定 `promoted`（独立入口）或 `router`（保留为 hub 内的能力卡）
7. 检查入口预算：`1 个 hub + promoted 数 ≤ entry_budget`
8. **用户轻确认**：展示 `A 级 N / B 级 M / C 级 K / 归档 J / 淘汰 R / 晋升 P` 与争议卡列表

**质量门**
- [ ] 每条候选都有明确的四重验证结果与硬证据（不是"看着挺有用"）
- [ ] 每条通过的候选都有置信度等级，且 A 级给出了 ≥2 个**独立**来源的证据
- [ ] 转引关系已识别（一方引用另一方的，合并为同一证据，不重复计数）
- [ ] 所有淘汰/归档项都写明了原因
- [ ] 源间分歧都已产出争议卡或明确记录"无实质分歧"
- [ ] 入口数未超预算，或有用户明确授权

## 阶 4 — 立卡（RIA++ 构造）

**目标**：把入选单元铸成一张可直接被 agent 加载的能力卡。

**产物**：
- 卡正文 `R / I / A1 / A2 / E / B` 六段 → `.forge/cards/<slug>.md`（**不带 frontmatter**）
- 元数据 → `.forge/bundle.yaml`（schema 见 `templates/BUNDLE.yaml`）

**六段定义与写法**见 `references/card-spec.md`。要点速记：

| 段 | 一句话要求 | 判断标准 |
|---|---|---|
| **R** 原文 | 直接引用 ≤150 字 + 出处 | 引用能在原文里检索到 |
| **I** 自述 | 用自己的话重写骨架，5–15 行 | 没读过原文的人读完能明白这个方法在做什么 |
| **A1** 案例 | 作者亲自用过的实例 1–3 条 | 每条写清：遇到什么问题 → 怎么用 → 得出什么 → 结果如何 |
| **A2** 触发 ★ | 用户在什么情境下会遇到 / 语言信号 / 与相邻卡的区别 | 写成了 `description` 后能被精准触发，不宽不窄 |
| **E** 执行 | 1–2–3 步骤，每步有**可判断的完成标准** | 每步都能回答"我怎么知道这步做完了" |
| **B** 边界 | 反场景 + 作者警告的失败模式 + 作者盲点 + 易混淆的邻近方法 | 能挡住至少一类不该触发的情况 |

**A2 的硬要求**：
- 场景 3–5 条，语言信号 3–5 条，且**中英双写关键 trigger 词**
- 与相邻卡的区分：本阶只写**初稿**（依据 verified 列表推测），阶 5 建立链接后回填定稿
- 好的 A2：`用户在纠结一个决策、列了正面理由却理不出头绪时；不适用于纯信息查询。`
- 坏的 A2：`用户需要思考时。` ← 太宽，必误触发

**质量门**
- [ ] 每张卡六段齐全，A2 与 B 尤其不能空
- [ ] E 段每一步都有完成标准，有判停点的显式写出
- [ ] bundle.yaml 中每张卡有稳定 `capability_id`、`one_liner`、`intents`、`keywords`、`source_evidence`
- [ ] `frontmatter.description` ≤300 字，写清"何时用 + 何时不用 + 关键 trigger"
- [ ] 卡正文里**没有** frontmatter（元数据只在 bundle 里，避免两处真相）

**常见翻车**：I 段写成书摘 / A2 太宽 / E 段只有哲学没有动作（"保持客观"不是步骤，"列出 3 个最不希望发生的结果"才是）/ 缺 B 段 / 从 I 直接跳到 E 跳过 A1（丢掉了"作者亲自用过"的权威性）。

## 阶 5 — 织网（Zettelkasten + 术语表）

**目标**：把原子卡之间的关系显式化，形成可导航的网络，而不是一堆孤立文件。

**三类关系**
1. **depends-on** — A 的前提是先理解 B
2. **contrasts-with** — A 与 B 是两种可选方案，看情境选一
3. **composes-with** — A 与 B 经常配合使用

**步骤**
1. 列出所有 active 能力，两两扫描识别上述关系
2. 写入 bundle 中各卡的 `also_read` 字段（编译时生成"补读"列）；语义说明写在卡末"相关能力"段
3. **回填 A2**：链接关系确定后，把阶 4 留下的"与相邻卡的区别"初稿改成定稿，同时同步 `frontmatter.description`
4. 把 `candidates/glossary.md` 提升为 `GLOSSARY.md`。**多源项目必须做术语对齐**：同一概念在不同来源中叫法不同 → 统一到一个主词条，别名全部列出

**节制原则 —— 不要硬造关系。**
经验值：10 张卡合理的关系数约 8–15 条。少于 5 条说明拆得太独立（可能单元选错了）；高于 25 条说明在硬凑。

**质量门**
- [ ] 每张卡都能说清它与至少 1 张卡的关系（或明确说明它确实孤立）
- [ ] GLOSSARY 覆盖了所有卡的 B 段提到的概念；多源项目已完成别名对齐
- [ ] A2 已回填定稿，与 bundle 中的 description 一致

## 阶 6 — 试炼（压力测试）

**目标**：在交付前验证每张卡**被调用的精准度**与**调用后的输出质量**。不通过的回炉重做阶 4 的 A2 / E / B，不是小修。

**产物**：每张晋级入口一份 `test-prompts.json` + `test-results.md`

**三类用例缺一不可**：

| 类型 | 数量 | 目的 |
|---|---|---|
| `should_trigger` | 3–5 | 该调用时是否调用 |
| `should_not_trigger`（诱饵） | 2–3 | 不该调用时是否忍住 |
| `edge_case` | 1–3 | 边界模糊场景判断是否合理 |

**三条硬规则**：
1. **没有诱饵用例的一律打回。** 只测正例，skill 永远"看起来很好"，部署后会乱激活。
2. **诱饵中至少 1 条必须是"该触发兄弟能力"的题。** 同一批材料拆出的多张卡互相抢调用，是部署后最常见的真实故障，只测"完全无关场景"发现不了它。盲测时把整包所有入口的 name + description 一起给评测者，让它做"该激活哪一个"的选择题，而不只是"要不要激活这一个"的判断题。
3. **诱饵中至少 1 条是边界反转题。** 把该卡 B 段写的反场景，直接改写成一个像正面请求的提问，验证边界守不守得住。
4. **多源项目额外要求**：至少 1 条用例来自**低置信度（C 级）内容所覆盖的话题**，验证 skill 不会把单源单域结论说得像跨源共识。

**独立盲测优先**：给评测者只看卡内容（或 `<name> + <description>` 列表）与用户 prompt，**不给** `type` / `expected_behavior` / `notes` / 通过标准。要求输出 `would_trigger` / `which_one` / `reason` / `if_triggered_action`。没有独立评测能力时退回自测，但必须在 `test-results.md` 里标明这是 fallback，可信度低于盲测。

**判分**
- 100% → 接受
- ≥80% → 分析失败用例，决定修卡还是修测试（修测试要警惕自我合理化，必须记录理由）
- <80% → **必须回炉重做阶 4**，不是小修

**判断"修卡还是修测试"**
- 失败暴露了 trigger 描述**有歧义** → 修卡
- 失败是一个你**之前没想到的合理场景** → 可能需要扩卡或明确排除
- 失败是**你为了凑诱饵设计过狠**的场景 → 修测试，但必须写理由

## 阶 7 — 出炉（编译 + DIGEST + 安装）

**目标**：把产出真正送到两类使用者手里 —— agent 能调用，人类能阅读。

### 第 1 步 · 编译

从 `bundle.yaml` 确定性生成：

| 形态 | 产物 | 何时用 |
|---|---|---|
| `hub` | 1 个入口目录，内含路由表 + 全部能力卡 | 能力数多、用户只想记一个名字 |
| `split` | N 个独立入口，无 hub | 能力数 ≤5、彼此独立、用户分场景调用 |
| `mix` | 1 个 hub + M 个高频能力晋级独立入口 | 默认；兼顾"一个总入口"与"高频直达" |

**编译规则**
- hub 的 SKILL.md 必须包含：触发与不触发 / 核心原则速览（3–7 条，概览类问题读到这里即可答）/ 意图→能力卡路由表 / 加载规则（一次只加载 1 张卡，跨域最多 2 张）/ 边界与判停
- 晋级入口的 `description` 直接取该卡 bundle 里的 `frontmatter.description`
- hub 的路由表中，已晋级的条目要注明"已晋级为独立入口，优先直接用；本卡仅作原文与背景补充"（避免同一请求双触发）
- **不要把同一批材料的 `hub` 与 `split` 同时安装** —— 两套 description 会重复覆盖意图

### 第 2 步 · DIGEST.md

面向人类读者的精华长文，**是"蒸馏后的再呈现"，不是"重新摘要"** —— 只写通过验证的内容，所以浓度天然高于普通书摘。

- 篇幅随体量伸缩（一本书 5000–10000 字；单期播客不必硬凑）
- 按**材料的骨架**组织章节，不按能力卡列表组织 —— 读者要的是"这讲的是什么"，不是产物清单
- 每个核心方法论一小节：解决什么问题 → 核心逻辑 → 最有代表性的案例 → 什么时候会失效
- **必须包含**"陷阱/反例"一节（来自 counter-examples）和"作者的局限"一节（来自阶 1 批判段）。只报喜不报忧的是软文，不是蒸馏
- **多源项目额外要求**：必须有"来源之间的一致与分歧"一节，把三角矩阵的结论写给读者看
- 每个方法论小节末尾指向对应的入口/卡，读者想深入时有路径

**自检**：一个没读过原文的人，读完 DIGEST 能否复述主旨、3 个以上核心方法、2 个以上陷阱？

### 第 3 步 · 安装

1. **一次性问清装哪里**（不要逐个卡问）：
   - 用户级 `<user home>/.workbuddy/skills/`（所有项目可用）
   - 项目级 `<project>/.workbuddy/skills/`
   - 只要仓库形态（准备发布到 GitHub），则跳过安装
2. 只安装通过阶 6 的产物；未通过的留在 `dist/` 里回炉
3. 安装后抽 1–2 个入口，用一条 `should_trigger` 的 prompt 实测宿主能否加载并触发
4. 把 `STATE.md` 标记为全部完成

## 迭代与增量更新

材料会更新（书出新版、播客出新一期、用户又给了一份新来源）。**不要直接改已发布的 skill**，走这条路径：

1. 新来源进 CHARTER，标 `trust` 与加入时间
2. 只对新增内容跑阶 1–2，产出增量候选
3. 与既有 `verified.md` 做 **chunk 级 diff**，分类为：完全重复 / 近似重复 / 新增 / 修正 / **矛盾** / 删除
4. **矛盾类必须人工确认**，产出或更新争议卡，不允许静默覆盖
5. 只对被影响的能力卡重跑阶 4，再整体重跑阶 6
6. 编译前保留旧产物快照，便于回滚
7. 重新编译默认**沿用上次的输出形态**，不因为新增材料就静默改变形态

## 演化路径：hub/split 不是单向门

`hub` 起步不等于永远 `hub`。当出现以下**证据**时，可把某张能力卡提升为独立入口：

1. 用户显式请求（"我希望 X 能单独触发"）
2. 用户自愿提供的调用记录（默认不采集；要采集必须说明并获授权）
3. 外部反馈聚合（issue / 反馈表里的重复诉求）

**拿不到证据就诚实保持现状，不要用猜测代替证据。** 任何情况下都不得在用户不知情时上报使用数据。
