# 阶 6 — 试炼（压力测试）

## 为什么必须做

A2（触发）是整条流水线里最难的一环。一张卡做得再漂亮，**触发不准就等于不存在**。压力测试是交付前唯一能发现触发问题的方法。

## 评测原则：独立盲测优先

压力测试要尽量模拟真实调用：一个**没有参与蒸馏、看不到预期答案**的评测者，面对用户 prompt 时会不会自然激活这张卡。

**优先做法**
- 每条 prompt 起一个干净的 sub-agent；资源有限时，同一张卡的一组 prompt 共用一个干净 sub-agent
- **只给**：卡内容（或整包所有入口的 `name + description` 列表）、用户 prompt
- **不给**：`type`、`expected_behavior`、`notes`、通过标准、主流程的任何判断
- 要求输出：`would_trigger` / `which_one`（多入口时）/ `reason` / `if_triggered_action`

**降级做法**：宿主无独立评测能力时退回主流程自测，但**必须在 `test-results.md` 里标明这是 fallback**，可信度低于盲测。

## 用例格式

```json
{
  "skill": "decision-heuristics",
  "version": "0.1.0",
  "sources": ["src-franklin", "src-barnum"],
  "darwin_compatible": true,
  "test_cases": [
    {
      "id": "should-trigger-01",
      "type": "should_trigger",
      "prompt": "我要决定要不要接这个新项目，列了一堆好处但还是没底",
      "expected_behavior": "激活 decision-heuristics，反问'最不希望发生什么'",
      "notes": "正面场景：决策纠结",
      "evidence_level": "A"
    },
    {
      "id": "should-not-trigger-01",
      "type": "should_not_trigger",
      "prompt": "我老婆有些习惯改不了，我该忍着还是怎么办？",
      "expected_behavior": "不应激活本卡，应由 acceptance 类能力处理",
      "notes": "跨能力混淆诱饵",
      "evidence_level": "—"
    },
    {
      "id": "should-not-trigger-02",
      "type": "should_not_trigger",
      "prompt": "帮我查一下这个 API 的参数",
      "expected_behavior": "纯信息查询，不调用任何决策能力",
      "notes": "无关诱饵"
    },
    {
      "id": "boundary-inversion-01",
      "type": "edge_case",
      "prompt": "我在想晚饭吃什么，帮我用决策框架分析一下",
      "expected_behavior": "守住边界：日常琐事不属于本卡的决策门，明确说明并给轻量建议",
      "notes": "边界反转题：把 B 段的反场景包装成正面请求"
    }
  ],
  "minimum_pass_rate": 0.8
}
```

## 三条硬规则

### 1. 没有诱饵用例的一律打回
只测正例，卡永远"看起来很好"，但部署后会乱激活。诱饵是**必要条件**，不是加分项。

### 2. 诱饵中至少 1 条必须是"该触发兄弟能力"的题
同一批材料拆出的多张卡互相抢调用，是部署后最常见的真实故障 —— 只测"完全无关的场景"发现不了它。

盲测时把**整包所有入口**的 `name + description` 一起给评测者，让它做"该激活哪一个"的**选择题**，而不只是"要不要激活这一个"的**判断题**。

### 3. 诱饵中至少 1 条是边界反转题
把该卡 B 段写明的反场景，**改写成一个看起来像正面请求的提问**，验证边界守不守得住。
例：B 段写"不适用于日常琐碎选择" → 诱饵写成"我在想晚饭吃什么，帮我用决策框架分析一下"。

## 多源项目额外要求

至少 1 条用例来自 **C 级（单源单域）** 内容覆盖的话题，验证这张卡不会把孤例说得像跨源共识。

例如：`"我听说理财就是要分散投资，是这样吗？"` —— 若该结论只有单一来源支持，正确行为是**明确标注证据强度不足**，而不是自信地回答。

## 判分

| 通过率 | 处理 |
|---|---|
| 100% | 接受 |
| ≥80% | 分析失败用例，决定修卡还是修测试 |
| <80% | **必须回炉重做阶 4**（A2 / E / B），不是小修 |

修卡还是修测试：
- 失败暴露了 trigger 描述**有歧义** → 修卡
- 失败是一个你**之前没想到的合理场景** → 扩卡或明确排除
- 失败是**你为了凑诱饵设计过狠**的场景 → 修测试，但必须记录理由（警惕自我合理化）

## 产物

- `<skill-dir>/test-prompts.json`
- `<skill-dir>/test-results.md` —— 通过率 + 逐条判定表 + 失败分析与回炉记录

# 阶 7 — 出炉（编译 + DIGEST + 安装）

## 第 1 步 · 从 bundle 编译

`bundle.yaml` 是唯一事实源，编译是**确定性**的。

| 形态 | 产物 | 何时用 |
|---|---|---|
| `hub` | 1 个入口目录：路由表 + 全部能力卡 + 术语表 + 概览 | 能力多、用户只想记一个名字 |
| `split` | N 个独立入口，无 hub | 能力 ≤5、彼此独立 |
| `mix`（默认） | 1 个 hub + M 个高频能力晋级为独立入口 | 兼顾总入口与高频直达 |

**hub 的 SKILL.md 必须包含**
1. **触发与不触发** —— 适用什么、不适用什么（含安全类兜底：涉及医疗/法律/人身安全时停止套用方法论）
2. **核心原则速览** —— 3–7 条 `one_liner`，概览类问题读到这里即可回答
3. **意图 → 能力卡路由表** —— 每行：用户意图 | 先读哪张卡 | 补读哪张卡
4. **加载规则** —— 每次先读 hub，再按路由表加载 **1** 张卡；任务明确跨域时最多 2 张；概览类问题不加载卡
5. **边界与判停** —— 路由表命中不了就明确告知"超出本包范围"，不要硬套

**晋级入口**
- `description` 直接取 bundle 中该卡的 `frontmatter.description`
- hub 路由表中对应行要注明"**已晋级为独立入口，优先直接用；本卡仅作原文与背景补充**" —— 否则同一请求会双触发

**编译自检**
- [ ] 每个 `active` 能力在 bundle 中恰好有一个去向（`promoted` 或 `router`）
- [ ] 所有 `promoted` 都有对应的独立入口目录
- [ ] hub 路由表覆盖了所有 `router` 能力
- [ ] **不要把同一批材料的 hub 与 split 同时安装** —— 两套 description 会重复覆盖意图
- [ ] 术语表 / 概览文件随 hub 一起分发

## 第 2 步 · DIGEST.md

面向人类读者的精华长文。**它是"蒸馏后的再呈现"，不是"重新摘要"** —— 只写通过验证的内容，浓度天然高于普通书摘。

**篇章结构**
- 篇幅随体量伸缩（一本书 5000–10000 字；单期播客不必硬凑）
- **按材料的骨架组织章节**，不按能力卡列表组织 —— 读者要的是"这讲的是什么"，不是产物清单
- 每个核心方法论一小节：它解决什么问题 → 核心逻辑 → 最有代表性的案例 → 什么时候会失效
- **必须包含**"陷阱 / 反例"一节（来自 counter-examples）和"作者的局限"一节（来自阶 1 批判段）。只报喜不报忧的是软文，不是蒸馏
- **多源项目必须加**"来源之间的一致与分歧"一节，把三角矩阵的结论讲给读者
- 每个小节末尾指向对应的能力卡，读者想深入时有路径
- 引用遵守 ≤150 字（英文 ≤100 词）

**自检**
- [ ] 没读过原文的人，读完能复述主旨、3 个以上核心方法论、2 个以上陷阱
- [ ] 没有把未通过验证的内容当核心方法论呈现
- [ ] 有批判/局限部分
- [ ] 每个小节都有指向能力卡的路径

## 第 3 步 · 安装

1. **一次性问清装哪里**（不要逐张卡问）：
   - 用户级 `<user home>/.workbuddy/skills/`（所有项目可用）
   - 项目级 `<project>/.workbuddy/skills/`
   - 只要仓库形态（准备发布到 GitHub）→ 跳过安装
2. 只安装通过阶 6 的产物；未通过的留在 `dist/` 回炉
3. 安装后抽 1–2 个入口，用一条 `should_trigger` 的 prompt **实测宿主能加载并触发**；`mix` 模式另抽 1 条意图验证 hub 路由
4. 把 `STATE.md` 标记为全部完成

## 第 4 步 · 收尾汇报模板

> 已完成。
> - 来源：<N 份>，其中 primary <n1> / secondary <n2>
> - 能力：<X> 张（A 级 <a> / B 级 <b> / C 级 <c>），晋级为独立入口 <M> 个，其余在 hub 内按需加载
> - 归档 <J> 条（画像低相关），淘汰 <R> 条（附原因）
> - 争议卡 <K> 张 —— **建议在真实决策前先读这几张**
> - 产出：<安装位置>、DIGEST.md（约 X 字）、GLOSSARY.md
> - 未解决：<列出你认为证据不足、需要更多材料才能定论的点>

**诚实报告未解决的部分**，比把包做得看起来完整更重要。
