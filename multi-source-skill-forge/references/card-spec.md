# 阶 4 细则 — RIA++ 能力卡写法规范

一张能力卡就是"**给 agent 用的一个方法论单元**"。它不是文章，不是笔记，不是摘要 —— 它的每一段都对应 agent 在真实调用时需要的一个信息位。

模板：`templates/CAPABILITY.md`

---

## 六段结构

### R — Reading（原文）

- 直接引用 ≤150 字（英文 ≤100 词）
- 必须标注出处（章节 / 页码 / 段落标识；视频填时间戳或分 P，播客填集数）
- 若原文是英文：**引用英文原文 + 你自己翻译的中文**，不要用现成译本（避免译本失真与译者版权问题）
- 多源项目：R 段可以列**多条**来源引用，每条带 `source_id`。这正是 A 级置信度的展现处

**作用**：让这张卡有据可查，也让 agent 在被追问"凭什么"时有话可说。

---

### I — Interpretation（自述）

- 用**你自己的话**重写方法论的核心骨架
- 5–15 行
- 检查标准：**读完这段，一个没读过原文的人能否理解这个方法在做什么？** 不能就重写

**禁止**：照搬原文句子、堆砌修辞、写成"作者在本章指出…"的复述腔。

> 反面示例（在抄书）：
> "作者认为，逆向思维是一种非常重要的思维方式，芒格在书中多次提到它，并引用了一句名言。"
>
> 正面示例（在解释）：
> "面对一个目标时，先别问'怎么达成'，先问'什么会让我失败'。把失败因素列出来后避开它们，反过来就得到了该做的事。它比正向推理更稳的原因很朴素：人对'不想要什么'的判断通常比'想要什么'更清晰，尤其在没有历史数据的新情境里。"

---

### A1 — Past Application（案例）

- 作者**亲自**用这个方法处理过的具体案例，至少 1 条、最多 3 条
- 每条写清四件事：**遇到什么问题 → 怎么用这个方法 → 得出什么结论 → 实际结果如何**

**作用**：让 agent 在调用这张卡时，手里有具体的类比素材可以讲，而不是只有抽象原则。

速成档可省略本段，但必须在 STATE.md 注明"本卡 A1 已省略（速成档）"。

---

### A2 — Future Trigger ★（最关键的一段）

**这一段决定了这张卡是否真的会被用起来。** 写得再好，触发不准就等于不存在。

必须明确三件事：

**1. 使用者会在什么情境下遇到这类问题？**（场景描述，3–5 条）
**2. 这些情境的语言信号是什么？**（用户会说什么样的话，3–5 条，**中英双写**关键 trigger 词）
**3. 和哪些相邻卡不同？**（避免互相抢调用）

A2 的浓缩版直接写进 bundle 中的 `frontmatter.description`，宿主据此决定是否激活。

> ✅ 好的 A2：
> 用户在纠结一个决策、列了正面理由却理不出头绪时；或在问"怎么做 X 才能成功"时。
> 不适用于：纯信息查询、日常琐事选择。
> Triggers: 纠结 / 拿不定主意 / 该不该 / 利弊 / 犹豫 | hesitate / should I / pros and cons

> ❌ 坏的 A2：
> 用户需要思考时。 ← 太宽泛，必然误触发

**与相邻卡的区分**：本阶只写**初稿**（依据 verified 列表推测），阶 5 建立链接关系后回填定稿。不要在本阶硬编相邻关系 —— 那时你还不知道最终有多少张卡活下来。

---

### E — Execution（可执行步骤）

- 把方法论转成 1–2–3 步骤
- **每一步都要有可判断的完成标准**
- 有判停点的（"step 2 之后若 X 则跳到 step 5"）显式写出

**作用**：让 agent 被调用时有明确执行路径，而不是"自由发挥"。

**唯一标准**：把"哲学"翻译成"动作"。

| ❌ 不是步骤 | ✅ 是步骤 |
|---|---|
| 保持客观 | 列出 3 个最不希望发生的结果 |
| 认真评估风险 | 为每个风险写一个"能否承受"的 yes/no |
| 多角度思考 | 换 3 个身份各写一句话：竞品 CEO / 五年后的我 / 最挑剔的客户 |

完成标准同理：不是"做完了"，而是"我能指出这一步的产出物是什么"。

---

### B — Boundary（边界）★

四类内容，尽量都写：

1. **什么时候不要用这张卡**（反场景）
2. **作者在原文中警告过的失败模式**
3. **作者的盲点 / 时代局限**（直接来自阶 1 批判段）
4. **容易混淆的邻近方法论**（和其他卡怎么分）

**作用**：**防止乱调用。** 没有 B 段的卡，会在不该用的时候被用，反而帮倒忙 —— 这比不触发更糟，因为它会给用户一个错误的、看起来很有权威的建议。

多源项目中，若某来源与另一来源在边界上不同（例如都反对负债，但一个允许经营杠杆），**B 段必须明确写出这个边界差异，并指向争议卡**。这是本 skill 相对单源蒸馏最重要的差异点之一。

---

## 元数据（写进 bundle.yaml，不写在卡里）

卡正文只放 R/I/A1/A2/E/B 六段，**不带 frontmatter**。所有元数据集中在 `.forge/bundle.yaml`：

```yaml
- capability_id: cap.<slug>.<name>   # 稳定 ID：文案润色只加 revision，语义拆分/合并才换 ID
  revision: 1
  status: active                     # active | merged-into-other | retired
  slug: <kebab-case>
  title: <中文标题>
  confidence: A                      # A | B | C
  freshness: evergreen               # evergreen | decade | volatile
  importance: critical|high|medium|low
  importance_rationale: "<为什么重要：入度 / 篇幅占比 / 命中使用者目标任务>"
  destination: promoted              # promoted | router
  one_liner: <一句话决策规则>          # 进入 hub 的核心原则速览
  intents: [<用户意图>...]             # 进入 hub 路由表
  keywords: [<中英关键词>...]
  also_read: []                      # 阶 5 填充
  card: cards/<slug>.md
  frontmatter:
    description: |                   # A2 的浓缩版，≤300 字
      <何时用 + 何时不用 + 关键 trigger>
    tags: [...]
  source_evidence:
    - source_id: src-a
      location: 第三讲
    - source_id: src-b
      location: 00:12:30
```

**为什么元数据与正文分离**：同一份事实只存在一处。编译时正文与元数据组合出最终的 SKILL.md，修改说明文案不会污染卡片正文，也避免了"两处真相"。

## 常见失败模式

1. **I 段写成书摘** —— 读起来像"本章作者说了 X"，就是在抄书。重写。
2. **A2 太宽** —— "需要决策时"永远不会被精准调用。必须给出**可识别的语言信号**。
3. **E 段只有哲学没有动作** —— 见上表。
4. **缺 B 段** —— 没边界的卡会被过度调用，最终使用者失望。
5. **从 I 直接跳到 E，跳过 A1** —— 丢掉了"作者亲自用过"的证据，卡失去权威性。
6. **一句话塞两件事** —— 标题里出现"和/与/以及"，通常说明该拆成两张卡，或者其中一件应该降级为另一件的 example。
7. **用 C 级证据写 A 级语气** —— 单源单域的内容被写成"研究表明"，是多源项目最隐蔽的失真。写完卡后回查一遍每张卡的 `confidence` 字段与语气是否匹配。
