# 评估设计

修改 description、新增规则或更换骨架时读本文件。日常写文档不必读。

## 目录

- 无 Skill 基线
- 应触发
- 不应触发
- 相邻混淆
- 渐进读取
- 端到端评分
- 回归范围

## 无 Skill 基线

不给本 Skill 时，模型会产出：九节左右的完整文档，含公司介绍、产品对比、售后条款、确认回执，正文出现真实账号，图片按内容正确性挑选而不检查来源，确认环节写成品规格确认。

基线问题清单（作为评分对照）：

- 节数 ≥ 7
- 含对比表或售后条款
- 含真实账号或客户名
- 图片来自客户发来的截图
- 没有"我方动作 + 时限"节
- 判断标准写成形容词（正常、成功、没问题）

## 应触发

用户真实说法，均应加载本 Skill：

1. 「帮我给客户写个说明文档，说明这个号怎么用」
2. 「客户老问怎么绑定，你写个教程给他」
3. 「把聊天记录整理成一份交付文档，图文那种」
4. 「做份上手指引，客户第一次用会懵」
5. 「这个流程太绕了，写个步骤说明发客户」

## 不应触发

均应直接回应、不加载：

1. 「帮我写个产品介绍页，卖给企业客户」
2. 「这份合同条款帮我改得通俗点」
3. 「写个内部 SOP，下周一新同事入职要用」
4. 「报价单怎么列比较好」

## 相邻混淆

容易误判的边界，用于校准 description：

| 请求 | 判断 |
|---|---|
| 「把这份客户指引写得更专业一点」 | 触发。属于同一任务的修订模式 |
| 「这段文案太啰嗦了，帮我精简」 | 不触发。单段润色，无需骨架 |
| 「给我写个新手教程，教团队用这个工具」 | 触发。对象是操作者，即使受众是内部 |
| 「总结一下这个产品的功能」 | 不触发。功能说明不是操作指引 |

## 渐进读取

验证"该读的 reference 读到、不该读的不读"：

| 场景 | 期望读取 |
|---|---|
| 从零写一份交付说明 | document-skeleton.md |
| 用户说"这版太长，砍一砍" | failure-cases.md（定位是哪类冗余） |
| 用户说"图注写错了" | failure-cases.md 第 3 条 |
| 只是想加一条新规则 | evals.md + 回归 |
| 只问"这类文档该怎么写" | 只答，不读任何文件 |

## 端到端评分

一次完整交付应同时满足，任一不满足即判不通过：

1. **节数** 不超过 7 节，且每节只承担一个动作
2. **无条款** 不含价格、质保、售后承诺、确认回执
3. **无真实信息** 正文无真实账号、客户名、收款码、内部成本
4. **示例值** 存在、格式合法、全文一致、标注"以实际为准"
5. **顺序** 不存在"客户此刻做不到的动作"；若存在，必须有"先看位置、别操作"的说明
6. **可观察判据** 每个确认动作都有可见现象，无"正常/成功/没问题"式描述
7. **图片** 全部来自服务方、紧贴对应步骤、文件名与引用一一对应
8. **我方动作** 有时限，且说明客户此刻不要做什么

加分项（不满足不判失败）：文末警示块只针对会导致封号/丢数据/损失钱的事项。

## 回归范围

- 改 description → 必须重跑"应触发 / 不应触发 / 相邻混淆"三组
- 新增 Gotcha → 必须保留触发它的失败案例到 failure-cases.md
- 改骨架节数 → 必须重跑端到端评分第 1 项
- 只改措辞 → 不跑回归，但保留备份可回滚
