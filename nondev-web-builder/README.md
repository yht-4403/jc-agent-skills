# Non-Developer Web Builder

面向非开发者的 Web 项目技术教练，让用户只需要描述业务目标，由 Codex 负责技术选型、项目结构、代码边界、密钥配置、实现验证和交接说明。

它适合从零创建或继续维护这些项目：

- 纯 HTML、CSS、JavaScript 网站
- React + TypeScript 项目
- Next.js 前端或全栈项目
- 带有小型 Python 后端的 Web 项目

## 核心理念

> 用户决定产品要解决什么问题，Codex 负责如何安全、简单、可维护地实现。

这个 Skill 不要求非开发者选择框架、目录、状态管理、测试工具或密钥存放方式。Codex 会先理解用户和业务流程，再选择满足需求的最小技术方案。

## 解决什么问题

非开发者使用 AI 编程时，常见问题并不是“代码写不出来”，而是：

- 不知道应该使用什么技术栈；
- 项目目录随着功能增加逐渐混乱；
- 页面、接口、类型和错误处理互相脱节；
- Token 被直接写进浏览器代码；
- AI 擅自扩大修改范围；
- 项目看起来完成了，但没有真正运行和验收；
- 交给开发人员后，缺少启动方式和必要说明。

Non-Developer Web Builder 把这些工程决策固化为可重复执行的工作流。

## 工作流程

```text
理解业务目标
→ 选择或确认技术栈
→ 建立项目规则与任务范围
→ 按业务功能组织代码
→ 自动配置本地密钥
→ 纵向完成用户流程
→ 运行检查并实际打开页面
→ 用非技术语言交接
```

### 1. 只向用户询问产品问题

Codex 会确认：

- 谁使用这个产品；
- 用户需要完成什么；
- 是否需要登录、数据保存、文件上传或第三方服务；
- 当前必须完成什么；
- 哪些内容暂时不做；
- 项目如何运行、验收和交接。

技术细节由 Codex 自行判断，并在有重要取舍时给出简短解释。

### 2. 自动选择最小技术栈

| 产品需要 | 默认方案 |
| --- | --- |
| 静态展示、活动页面、简单内容站点 | HTML、CSS、少量 JavaScript |
| 无私密数据的浏览器交互工具 | React + TypeScript + Vite |
| 登录、数据库、上传、私密 API 或管理功能 | Next.js + TypeScript |
| AI、数据处理、长任务或已有 Python 能力 | Web 前端 + 小型 Python API |

已有项目不会因为出现了新的流行方案就被随意迁移。Skill 会优先保持现有技术和可运行状态。

### 3. 按业务功能组织代码

代码围绕用户能力组织，而不是只按文件类型堆放：

```text
src/
├── app/                         # 路由与页面入口
├── features/
│   ├── core-workflow/           # 核心用户流程
│   │   ├── components/
│   │   ├── screens/
│   │   ├── api.ts
│   │   ├── schema.ts
│   │   ├── types.ts
│   │   └── tests/
│   └── account/
└── shared/                      # 已被多个业务稳定复用的内容
    ├── components/
    ├── lib/
    └── styles/
```

主要边界：

- 路由和页面入口保持简洁；
- UI、状态、请求、数据结构和测试归属于对应业务功能；
- 只有真正跨业务复用的内容才能进入 `shared/`；
- 避免没有明确含义的 `utils`、`helpers`、`misc` 和 `common`；
- 文件按照业务含义命名，而不是按照页面位置命名。

### 4. 自动建立项目规则

Skill 会为项目维护简洁的 `AGENTS.md`，记录：

- 产品目的和主要用户流程；
- 当前技术栈和包管理方式；
- 目录和业务模块边界；
- 开发、检查、测试和构建命令；
- 密钥与浏览器公开配置的边界；
- 当前修改范围；
- 完成和交接要求。

较大的任务会先建立简短任务契约：

```markdown
## Goal
## Acceptance criteria
## Out of scope
## Assumptions and risks
```

验收条件描述用户能够观察到的结果，避免用“新增某个文件”代替真实完成标准。

### 5. 固定处理本地密钥

所有本地密钥统一放在项目根目录：

```text
.env.local
```

附带脚本会自动：

- 创建或补全 `.env.local`；
- 将文件权限限制为当前用户读写；
- 创建只包含空变量的 `.env.example`；
- 更新 `.gitignore`；
- 保留已经填写的值，只增加缺失变量；
- 不接受、不读取也不打印真实密钥。

技术边界：

- Next.js 只在服务端读取私密变量；
- `NEXT_PUBLIC_*` 和 `VITE_*` 一律视为公开配置；
- React 和纯 HTML 需要私密 Token 时，必须增加服务端接口；
- Python 后端读取同一个根目录 `.env.local`；
- 项目交接时排除 `.env.local`，保留 `.env.example`。

### 6. 纵向完成一个可用流程

每项功能按完整链路交付：

```text
页面入口
→ 用户输入
→ 数据校验
→ 业务行为
→ 接口或数据保存
→ 加载、成功、空数据和失败状态
→ 实际验证
```

这样可以避免只完成页面外观、只写接口，或者只处理正常情况。

### 7. 验证和交接

完成前根据项目实际情况检查：

- 依赖是否能够安装；
- 类型、Lint、测试和生产构建是否通过；
- 页面是否能够真实打开；
- 核心用户流程是否可完成；
- 加载、空数据、输入错误和服务失败是否有反馈；
- 手机和桌面尺寸是否可用；
- 浏览器控制台和网络请求是否存在异常；
- 修改是否超出任务范围；
- 文件和输出中是否出现密钥或私密数据。

最终使用普通用户能理解的方式说明：

- 现在可以做什么；
- 如何启动；
- 如何验收；
- 已经运行了哪些检查；
- 哪些检查没有运行；
- 还存在哪些风险；
- `.env.local` 中还需要填写哪些变量名，不展示变量值。

## 项目文档

小型项目默认使用精简文档结构：

```text
docs/
├── README.md
├── product/
│   ├── brief.md
│   └── current-task.md
├── decisions/
└── guides/
```

文档只保存当前有效的信息和重要决策，不保存原始对话，也不为每次小修改生成报告。

## 可选协作能力

当运行环境存在相应专业 Skill 时，主流程可以按需调用：

- `frontend-design`：视觉设计与界面实现；
- `web-design-guidelines`：可访问性和交互检查；
- `react-best-practices`：React 与 Next.js 实现审查。

这些能力是可选增强项。Non-Developer Web Builder 本身仍然负责整体流程和最终交付。

## Skill 结构

```text
nondev-web-builder/
├── SKILL.md
├── README.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── stack-selection.md
│   ├── project-rules.md
│   ├── business-slicing.md
│   ├── frontend-quality.md
│   ├── backend-and-data.md
│   ├── local-secrets.md
│   └── completion-and-handoff.md
└── scripts/
    └── setup_local_env.py
```

`SKILL.md` 保存主流程；详细规范按任务需要从 `references/` 读取；密钥初始化由脚本确定性执行。

## 使用方式

在项目目录中告诉 Codex：

```text
使用 $nondev-web-builder 帮我创建这个 Web 项目。
我会说明业务目标，技术方案、项目结构和检查方式由你决定。
```

也可以用于已有项目：

```text
使用 $nondev-web-builder 继续完善当前项目。
先理解现有结构和功能，再在不破坏已有内容的前提下完成我的需求。
```

## 设计边界

- 不强制复杂的测试驱动流程；
- 不强制多代理编排；
- 不强制复杂的分支和提交工作流；
- 不因为项目变大就自动拆成多个仓库；
- 不自动引入无明确用途的框架和依赖；
- 不用文档数量代替真实项目质量。

目标不是建立最复杂的工程体系，而是让非开发者也能持续产出结构清晰、安全、可运行、可验证、可交接的 Web 项目。
