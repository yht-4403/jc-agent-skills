# 视觉优先的技术评审主文与开发查询附录

适用于开发负责人既要快速理解业务，又要进行少量关键技术评审的复杂方案。目标不是减少技术信息，而是把信息放到正确阅读层级。

## 1. 文档读者契约

文档开头写清楚：

```markdown
> 主要读者：开发负责人、产品、相关开发和后续 AI
> 首次阅读：先完成 1 分钟结论和约 5 张核心图
> 深度阅读：关键技术评审控制在 30 分钟内
> 查询方式：分割线以下为开发附录，不要求顺序阅读
> 文档状态：{待评审 / 部分冻结 / 已冻结}
> 最后验证：{环境、样本范围、日期}
```

## 2. 第一部分：30 分钟技术评审

推荐结构：

```text
1. 一页结论
2. 图一：当前问题与目标方案
3. 图二：领域对象和核心 Key
4. 图三：目标业务主流程
5. 图四：系统职责与数据权威
6. 图五：关键分支、异常和演进方案
7. 必要技术评审
8. 待拍板问题
9. 验收结论
```

不要默认增加 `0. 阅读导航`。先让标题本身回答读者问题；只有文档确实存在多条互不相同的阅读路径时才补导航。

### 2.1 一页结论

只保留：

- 为什么要改；
- 推荐方案；
- 最大限制；
- 当前是否可以进入开发；
- 哪些问题会阻断开发。

不要在开头解释完整历史、接口调用过程或调试记录。

### 2.2 五张核心图

每张图只回答一个问题：

| 图 | 回答的问题 | 常用表现 |
| --- | --- | --- |
| 当前与目标 | 为什么改，最终变成什么 | `graph LR` 左右对比 |
| 对象与 Key | 重要对象怎么关联 | `graph LR` 或简化 `erDiagram` |
| 目标流程 | 一条业务数据怎么流转 | 主线 + 细节盒子 |
| 职责与权威 | 每个系统负责什么，谁说了算 | `graph LR` + `subgraph` |
| 分支与演进 | 第一期怎么做，失败如何兜底，长期怎么升级 | 决策树 |

不是每篇文档都必须正好五张。相邻问题能用一张清晰图回答时合并；单图出现多个无关问题时拆开。

画图前必须读取并遵循 `jc-markdown-visual-writer`。本 reference 不定义 Mermaid 语法和视觉样式。

### 2.3 必要技术评审占比

评审主文约 70% 用于理解业务，约 30% 用于检查会改变方案的技术设计。

通常需要进入主文：

- 数据权威与系统边界；
- 核心 ID、唯一性和对象关系；
- 一致性、历史归属和失败后的业务后果；
- 权限与鉴权边界；
- 数据库新增/修改数量和是否已经核对；
- 灰度、兼容和回滚方向；
- 会推翻方案的扩展条件。

通常不进入主文：

- 完整 BaseURL 和请求头；
- 完整请求响应 JSON；
- curl 和真实日志；
- 全量字段、错误码和枚举；
- 分页、锁、TTL 的完整伪代码；
- DDL、Flyway 脚本和回填 SQL；
- 逐文件代码路径和测试命令。

### 2.4 待拍板问题

使用稳定编号，并写清影响：

| 编号 | 状态 | 问题 | 不确认的后果 |
| --- | --- | --- | --- |
| D1 | 待确认 | {问题} | {阻断或风险} |

待确认内容不能夹在段落中，也不能被 AI 当成默认实现。

## 3. 技术细节很多时再结束首次阅读主线

首次阅读主线之后仍有大量接口、字段、算法或数据库细节时，可以使用分割线：

```markdown
---

# 开发时再看

> 本部分供实施和排查时按需查询，不要求顺序阅读全文。
```

内容较短时不要为了模板强行制造“附录”。需要分层时也不默认使用“附录 A/B/C”编号，优先使用“接口怎么调用？”“Python CRM 需要保存什么？”等直接标题。

## 4. 第二部分：开发时按问题查询

不默认提供按角色导航。只有前端、后端、数据库、测试确实存在互不相同的阅读路径，而且表格比清晰标题更省时间时，才使用角色导航：

| 角色 | 优先查询 |
| --- | --- |
| 前端 | 入口、状态、接口调用和错误展示 |
| Java / 主后端 | 上传契约、兼容字段和作品事实 |
| Python / 业务后端 | 同步算法、投影、并发和失败恢复 |
| 数据库 | 表、字段、索引、迁移、回填和回滚 |
| 测试 | 环境、样本、用例、命令和证据 |
| AI 执行者 | 已冻结决策、实施门禁、相关代码入口 |

默认直接使用读者能够理解的标题：

```text
接口怎么调用和鉴权？
前端和后端分别需要传什么？
同步怎样保证学生名单完整？
Python CRM 需要保存什么？
前端、Java 和 Python 分别改什么？
接口请求到一半失败怎么办？
哪些数据库改动现在还不能做？
怎样测试和保存证据？
```

## 5. 正文与附录去重

按下面顺序处理重复：

1. 删除附录重复的背景、目标、总体流程和推荐结论。
2. 主文只保留会影响决策的技术摘要，精确契约链接到附录。
3. 已确认业务规则只维护一份，附录通过标题或决策编号引用。
4. 全新接口保留完整契约；已有接口只写本次变化，除非要求完全自包含。
5. 样本日志只保留能证明结论的脱敏片段。

## 6. AI 实施计划仍然独立

开发查询附录回答“事实是什么”，不能代替“具体怎么改”。只有在业务决策冻结并检查真实代码后，才依据附录生成 AI 可执行实施计划。

AI 的阅读顺序：

```text
评审主文中的已冻结决策
  → 当前代码和项目规范
  → 按职责查询开发附录
  → 生成文件级实施计划
  → 执行测试和证据留存
```

如果仍有会改变数据模型、接口或权限的待确认问题，停止生成可执行任务，先请求确认。

## 7. 双重读者测试

### 人类测试

- 只看开头是否能说清方案和最大限制？
- 解释性章节是否使用问题式标题，并在下一行立即给出一句结论？
- 只看标题和下一句话，是否能判断这一节解决什么？
- 不看附录是否仍能完成技术决策？
- 图是否比对应文字更快，而不是把段落塞进节点？

### AI / 开发测试

- 能否从附录找到精确契约和验证证据？
- 是否能识别实测环境、合理推测和待确认项？
- 是否避免根据示例值和字段名擅自补齐需求？
