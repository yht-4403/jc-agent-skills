# 设计文档 + 实施文档成对产出

适用于把一次产品/技术讨论沉淀成两份互相配套的项目文档：

- **设计文档**：以用户体验、业务流程、角色视角、页面/交互/状态为主线，回答“这个东西对用户来说是什么、怎么用、边界在哪里”。
- **实施文档**：以系统改造、接口、数据模型、前后端落点、验证计划、扩展性为主线，回答“工程上怎么做、改哪里、怎么验证、以后怎么扩展”。

这套 reference 借鉴 `doc-coauthoring` 的好思路：先补齐上下文，再组织结构，最后用读者视角检查。但它不依赖外部 skill，本文件就是 `knowledge-capture` 内部可复用的个人规范。

## 最核心的写作契约

这类文档的核心不是“写两份文档”，而是把同一个方案拆成两个读者视角：

1. **设计文档必须以用户体验流程为主线串起。**
   设计文档先讲用户、入口、路径、页面、状态、反馈和边界。读者应该能顺着“用户从哪里来、看到什么、做什么、系统怎么响应、异常时怎么办”理解整个方案。

2. **实施文档必须讲清楚技术方案和具体改造位置。**
   实施文档要明确后端改哪里、前端改哪里、接口怎么变、数据怎么存、是否涉及数据库改造、权限/安全/审计怎么兜住，以及验证方式是什么。

3. **实施文档必须评估未来拓展性。**
   不只写这一版怎么做，还要写未来如果新增角色、主体、看板、权限范围、组织层级、数据维度或管理流程，这一版技术实现需要怎么调整。

4. **必须回答“这是不是足够企业级”。**
   评估者读完后要能判断：当前方案是不是有清晰边界、可审计、可扩展、可迁移、能灰度、能回滚；是否方便以后升级成更标准的企业级权限/工作台体系。

5. **必须说明哪些变化会推翻当前设计。**
   不要只说“可扩展”。要明确哪些变化只要配置，哪些变化需要小改，哪些变化需要新建模型，哪些变化会导致这一版方案需要重做。

如果一份双文档没有回答上面 5 点，就算结构完整，也还不合格。

## 什么时候用

用户出现类似表达时使用：

- “出一版设计文档和实施文档”
- “详细设计 + 实施计划”
- “先出方案，不着急开发”
- “把这个流程也加入文档”
- “从用户体验流程串起来，实施文档讲技术方案”
- “评估一下是不是企业级、后续好不好扩展”

如果用户只是要普通聊天总结、复盘或灵感沉淀，不要套用这套双文档结构，继续用 `context-note.md`。

## 核心原则

1. **先把上下文补齐，再写文档。**
   不要直接上来列目录。先确认业务目标、用户角色、当前痛点、已有实现、约束、争议点和下一步决策。

2. **设计文档写给“业务和产品读者”。**
   主线是用户怎么进入、看到什么、能做什么、遇到异常怎么办。少写代码名、接口名和数据库细节。

3. **实施文档写给“未来要动手的人”。**
   主线是改哪些模块、怎么分阶段、数据怎么存、接口怎么返回、前后端怎么协作、怎么测试、风险在哪里。

4. **两份文档必须能互相对照。**
   设计文档里的关键体验和业务规则，实施文档里必须能找到对应的技术落点。

5. **不要把实现细节塞进设计文档，也不要把产品判断藏在实施文档里。**
   设计文档负责“为什么这样设计”和“用户怎么理解”；实施文档负责“工程怎么落地”和“以后怎么演进”。

6. **显式回答扩展性。**
   用户经常关心“这是不是企业级”“以后改分类/角色/权限/看板会不会重做”。实施文档必须单独说明哪些变化只要配置，哪些变化需要小改，哪些变化会推翻当前设计。

## 工作流程

### 第一步：收集上下文

先用少量问题补齐必要信息，不要一次问太多。优先确认：

- 这次文档要解决什么决策？
- 主要读者是谁：自己、开发、产品、评审、团队？
- 当前系统已有哪部分实现？
- 用户最关心的体验流程是什么？
- 是否涉及权限、数据归属、审计、计费、后台管理、数据库改造？
- 是否要兼顾短期上线和长期企业级演进？

如果用户已经给了足够上下文，可以直接进入整理，不要机械追问。

### 第二步：先定两份文档的边界

在写正文前，先明确：

```text
设计文档：面向用户体验和业务流程，少讲技术。
实施文档：面向工程落地和后续维护，讲清楚改造点、数据、接口、验证和扩展。
```

如果用户对“设计文档”和“实施文档”的理解有偏差，按这条边界校准。

### 第三步：设计文档结构

设计文档推荐结构：

```markdown
# {主题}-设计文档

## 1. 背景和目标
## 2. 这次要解决的问题
## 3. 用户角色和使用场景
## 4. 核心体验流程
## 5. 页面和入口设计
## 6. 关键规则
## 7. 异常和空状态
## 8. 不做什么
## 9. 可扩展方向
## 10. 验收标准
```

写法要求：

- 用“用户从哪里进入 → 看到什么 → 做什么 → 系统怎么反馈”的顺序串起来。
- 重要规则要用普通人能听懂的话表达。
- 页面、按钮、入口、空状态、错误状态要说清楚。
- 需要权限时，写用户感知到的结果，不要只写权限 key。
- “不做什么”必须写，避免后续范围膨胀。
- 验收标准写成可检查的结果，不写空话。

### 第四步：实施文档结构

实施文档推荐结构：

```markdown
# {主题}-实施计划

## 1. 实施目标
## 2. 当前系统现状
## 3. 总体技术方案
## 4. 后端改造
## 5. 前端改造
## 6. 数据库和数据迁移
## 7. 权限、安全、审计
## 8. 兼容性和灰度策略
## 9. 测试和验证计划
## 10. 分阶段实施步骤
## 11. 风险和回滚
## 12. 后续扩展性评估
```

写法要求：

- 明确列出具体改造模块，不要只写“改后端”“改前端”。
- 数据库部分必须明确：是否需要新表/新集合/新字段/索引/迁移脚本/回滚策略。
- 权限类功能必须说明：前端只控制展示，后端做真正拦截。
- 写清楚接口契约：请求方需要什么，返回什么，旧字段是否保留。
- 测试计划要覆盖单测、集成、前端类型检查、页面验证、关键权限路径。
- 扩展性评估要诚实：哪些能自然扩展，哪些需要新一轮设计。

## 双文档对照检查

完成后必须做一次对照：

| 设计文档里的内容 | 实施文档必须对应说明 |
| --- | --- |
| 用户入口 | 前端组件/路由/接口调用 |
| 角色和主体 | 权限模型/数据字段/授权方式 |
| 页面状态 | 前端状态管理/接口返回/错误码 |
| 访问限制 | 后端鉴权/权限校验/审计 |
| 空状态/异常 | fallback、错误提示、日志 |
| 后续扩展 | 配置、数据模型、迁移成本 |

如果设计文档里有体验，但实施文档没有落点，要补实施方案。
如果实施文档里有复杂改造，但设计文档没有用户价值，要重新判断是否必要。

## 企业级扩展性评估模板

实施文档里建议单独写一节：

```markdown
## 后续扩展性评估

### 当前方案能直接支持
- {例：新增一个看板，只要在权限目录中加一项}

### 需要小改即可支持
- {例：主体变成组织级，需要给授权增加 organizationId}

### 会触发重新设计
- {例：从简单权限点升级为复杂组织层级、审批流、资源级继承}

### 为什么当前方案仍然值得做
- {说明当前方案的边界、成本和未来迁移路径}
```

这部分要避免自夸式表达。重点是让评审者知道：当前方案不是一次性脚本，也没有过度设计到拖慢上线。

## 文件命名

如果在项目文档目录中产出，遵循项目自己的文档规范。常见格式：

```text
docs/<业务分类>/YYYY-MM-DD-NNN-主题名称-设计文档.md
docs/<业务分类>/YYYY-MM-DD-NNN-主题名称-实施计划.md
```

同一个主题的设计文档和实施文档共用同一个编号，只替换文档类型。

如果是写入个人知识库，则继续遵循 `naming.md` 的“一句话承诺”命名规则。

## 最终自检

交付前检查：

- 是否回答了“用户怎么用”？
- 是否回答了“工程怎么做”？
- 是否说明了有没有数据库改造？
- 是否说明了权限、安全、审计边界？
- 是否说明了未来什么变化会让这一版方案需要调整？
- 是否让评估者能判断：当前方案是否足够企业级，或至少是否方便后续演进到企业级？
- 是否区分了“只要配置”“需要小改”“需要新模型”“需要重做”的变化类型？
- 设计文档和实施文档是否互相对得上？
- 是否删除了明显的 AI 腔、空泛形容词和没有落点的表达？
