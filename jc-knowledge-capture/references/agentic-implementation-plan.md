# AI 可执行开发计划

适用于把已经明确的产品需求、技术方案、改造方案或 spec，整理成另一位 AI / agent / 开发者可以直接执行的实施计划。

这类文档不是普通总结，也不是设计文档。它的核心目标是：让执行者在几乎没有上下文的情况下，也知道先读什么、改哪里、怎么写测试、怎么验证、何时提交。

## 什么时候用

用户出现类似表达时使用：

- “先出计划，不要直接开发”
- “整理成开发计划 / 实施计划 / 任务清单”
- “拆成 AI 可以执行的步骤”
- “给另一个 agent 执行”
- “按 TDD 拆一下”
- “把这个方案沉淀成可落地的执行文档”

如果用户要的是产品/业务视角的“设计文档 + 实施文档”成对产出，优先使用 `design-implementation-doc-pair.md`。如果用户要的是真正动手执行的工程任务清单，使用本文件。

## 核心原则

1. **执行者默认没有上下文。**
   写清楚背景、入口文件、相关规范、依赖命令和验证方式。不要假设执行者知道项目结构。

2. **先锁定文件结构，再拆任务。**
   在写任务前，先列出计划创建或修改的文件，以及每个文件的责任边界。文件职责不清时，后面的任务会失控。

3. **任务必须小到能执行。**
   每个任务只完成一个清晰变化。复杂任务继续拆成测试、实现、验证、提交几个步骤。

4. **优先 TDD，但不要机械 TDD。**
   对逻辑、接口、权限、数据处理、共享工具优先先写失败测试。纯样式、文案、一次性文档调整可以改用人工验收或截图验证。

5. **验证必须具体。**
   不写“测试通过”，要写执行什么命令、看什么页面、期望看到什么结果。

6. **计划是执行文档，不是愿望清单。**
   避免“完善”“优化”“处理一下”“参考类似实现”。必须写清楚具体动作和验收标准。

## 推荐保存位置

优先遵循项目自己的文档规范和用户指定位置。

如果写入个人知识库，继续遵循 `naming.md` 的一句话承诺命名规则。

如果写入项目文档目录，常见格式是：

```text
docs/<业务分类>/YYYY-MM-DD-NNN-主题名称-实施计划.md
```

## 文档结构

根据任务复杂度增减章节，但不要省略“文件结构”“任务拆解”“验证计划”。

```markdown
# {一句话说明这个计划要交付什么}

> 这份计划用于让 AI / agent / 开发者在低上下文情况下执行。执行前必须先阅读本文列出的项目规范和相关文件。

## 1. 目标

{一句话说明这次要做成什么，不写泛泛背景。}

## 2. 当前上下文

- 需求来源：{来自哪次讨论 / 哪份 spec / 哪个问题}
- 当前状态：{系统现在怎么工作}
- 目标状态：{完成后应该变成什么样}
- 不做范围：{明确不包含什么，防止执行时扩大范围}

## 3. 执行前必须阅读

- `{项目规范或 AGENTS.md 路径}`：{为什么要读}
- `{相关代码文件}`：{理解什么}
- `{相关文档}`：{理解什么}

## 4. 文件结构和责任边界

| 文件 | 动作 | 责任 |
| --- | --- | --- |
| `path/to/file` | 新建 / 修改 | {这个文件只负责什么} |

## 5. 实施任务

### Task 1：{组件 / 能力名称}

**涉及文件：**

- 新建：`path/to/new-file`
- 修改：`path/to/existing-file`
- 测试：`path/to/test-file`

- [ ] **Step 1：写失败测试**
  - 操作：{写哪个测试，覆盖什么行为}
  - 预期：{运行后应该失败，失败原因是什么}

- [ ] **Step 2：运行测试确认失败**
  - 命令：`{具体命令}`
  - 预期：{具体失败信息或失败类型}

- [ ] **Step 3：实现最小代码**
  - 操作：{改哪个函数 / 组件 / 接口，怎么改}
  - 约束：{不能破坏什么兼容性}

- [ ] **Step 4：运行验证**
  - 命令：`{具体命令}`
  - 预期：{通过标准}

- [ ] **Step 5：提交当前任务**
  - 范围：{只提交哪些文件}
  - 提交信息：`{type(scope): message}`

## 6. 总体验证

- 单元测试：`{命令}`，预期 `{结果}`
- 集成测试：`{命令}`，预期 `{结果}`
- 前端检查：`{命令或页面路径}`，预期 `{结果}`
- 回归检查：{关键旧流程不能坏}

## 7. 风险和回滚

- 风险：{具体风险}
  应对：{如何提前验证或兜底}
- 回滚：{如果失败，恢复哪些文件 / 配置 / 数据}

## 8. 后续入口

{这次不做但未来可能继续做的事项。}
```

## 任务拆分标准

每个任务都要尽量满足：

- 一个任务对应一个可独立理解的变化。
- 一个任务结束后，代码应处于可运行或至少可验证状态。
- 测试和实现放在同一个任务内，不把“补测试”拖到最后。
- 涉及数据库、权限、接口契约、迁移脚本时，必须单独成任务，并写清验证方式。
- 不要让单个任务同时修改多个无关模块。

## 文件结构检查

写任务前先检查：

- 新文件是否有单一职责。
- 计划修改的旧文件是否已经过大；如果会继续膨胀，计划里要说明是否拆分。
- 经常一起改的文件是否放在相近位置。
- 是否遵循项目现有目录和命名习惯。
- 是否误把临时脚本、生成物、子项目源码纳入不该提交的仓库。

## 自检清单

交付计划前检查：

- [ ] 是否写清楚目标、当前状态、目标状态和不做范围？
- [ ] 是否列出执行前必须阅读的规范、代码和文档？
- [ ] 是否先说明文件结构，再写任务？
- [ ] 每个任务是否有明确文件、测试、实现、验证和提交范围？
- [ ] 是否避免了 TODO、占位符、“类似某某实现”这类偷懒表达？
- [ ] 验证命令是否具体，预期结果是否具体？
- [ ] 涉及数据库、权限、安全、审计或数据修复时，是否单独写清楚？
- [ ] 是否能让另一个没有上下文的 agent 直接开工？
