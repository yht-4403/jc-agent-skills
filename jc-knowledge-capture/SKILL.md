# JC Knowledge Capture

先判断读者看完要做什么，再判断篇幅和模板。不要把“保存”“评审”“查询”“执行”混成一篇从头读到尾的长文。

「写入知识库」「沉淀」「保存」只决定存放位置，不决定产物形态。先看材料本身，以及用户已经认可的内容：

- 已有完整机制讲解，或用户说「这个感觉挺好」「按这个写进去」「整篇保存」：保留讲解，走第 2 节第 9 条；不要先收成结论卡。
- 日常对话、判断、灵感、复盘：轻量或标准知识笔记。
- 要拍板、要查询、要执行：走对应专项产物。

「以后回顾」恢复上下文和可复用判断；篇幅跟随材料，不是必须短。

## 一、先识别阅读任务

| 阅读任务 | 产物 | 目标 |
| --- | --- | --- |
| 忠实保存 | 原文轻整理 | 保留原意、顺序和表达 |
| 以后回顾 | 轻量或标准知识笔记 | 恢复上下文和可复用判断；已有讲解则整篇保存 |
| 对外分享 | 口语化或结构化直述体社交稿 | 像正常说话一样直接陈述观点，按内容复杂度使用少量分点，不套营销文案 |
| 理解并拍板 | 视觉评审主文 | 低心智负担地看懂方案、影响和风险 |
| 实施时查询 | 开发查询附录 | 精确检索接口、字段、数据和算法 |
| 直接执行 | AI 可执行实施计划 | 明确文件、任务、测试、验证和停止条件 |

同一请求可能需要多个产物，但不要自动全做。按用户明确目的和当前准备度选择最少充分集合。最少充分集合指不要同时产出评审、查询和执行稿，不是把已经写好的讲解压短。

## 二、选择沉淀模式

1. 用户要求“原封不动、只修格式、不要总结”时，读取 `references/faithful-note.md`。
2. 短灵感、几条判断或临时备忘，读取 `references/context-note.md` 的轻量部分。材料已经是完整机制讲解，或用户要求按当前讲解保存时，改走第 9 条。
3. 已有完整背景、推导、取舍和复盘，且主要目标不是讲解机制时，读取 `references/context-note.md` 的标准部分。
4. 用户明确要发朋友圈、小红书、公众号或其他公开平台时，默认读取 `references/plainspoken-assertive-social.md`。用户说“正常说话”“直接陈述”“不要小红书文案”“就用这种文风”时，也进入该模式。用户说“用直述体 v2”“测 v2 文风”时，改读 `references/plainspoken-assertive-social-v2.md`。
5. 产品或技术讨论需要设计与实施成对产出，读取 `references/design-implementation-doc-pair.md`。
6. 跨系统技术方案需要让开发负责人快速评审，同时保存完整实现细节，读取 `references/visual-technical-review.md`。
7. 用户明确要交给 AI、agent 或开发者执行，读取 `references/agentic-implementation-plan.md`；先检查“AI 实施门禁”。
8. 要从现有代码还原全链路接口、数据库和异常行为，读取 `references/full-chain-interface-doc-prompt.md`。
9. 文档主要目标是解释技术机制或帮助新人上手，且存在可核对的代码、接口、日志、截图或运行结果时，默认读取 `../jc-plain-explainer/SKILL.md` 和 `../jc-plain-explainer/references/artifact-first-understanding.md`，不等待用户主动索要“真实体感”。用户要求把当前讲解写入知识库时仍走本条，不因阅读任务是「以后回顾」而改套上下文笔记。如果主要目标是评审拍板、实施查询或验收结论，只在解释难点的局部章节使用该协议，不改变整篇文档的决策结构。
10. 视频教学、版本备份和命名分别读取对应 reference。

公开发布默认使用“口语化直述体”，不再自动套用悬念钩子、情绪焦虑、反转标题、表情符号、互动引导或传统小红书爆款模板。只有用户明确要求营销文案、强传播包装或指定其他文风时，才切换。

默认版和 v2 的直述体社交稿都必须读取 `references/social-expression-rules.md`：先确定读者要理解什么，直接呈现事实与机制，默认不用六类对抗句式制造反转，保留必要的事实对比和用户原意。此规则只用于社交稿的新写与授权改写。

模板是上限，不是必须填满的章节清单。材料没有的信息不能为了结构完整而补造。

## 三、标题先回答读者问题

默认优先使用**问题式标题**，并在标题下一行马上写一句**结论式答案**。正文继续补充依据、例外和实现细节，不要让读者读完整节后才知道答案。

口语化直述体社交稿是例外：标题直接使用正文里最核心的判断，不为了点击率制造问题、冲突或悬念；具体读取 `references/plainspoken-assertive-social.md`（测 v2 时改读 `references/plainspoken-assertive-social-v2.md`）和 `references/naming.md`。

```markdown
## 前端和 Java 需要传什么？

前端上传真实学习标识，Java 原样保存这些作品事实。
```

按内容状态选择标题：

| 内容状态 | 标题类型 | 写法 |
| --- | --- | --- |
| 已经确认的事情 | 结论式标题 | 直接写出已经冻结的答案 |
| 需要解释的事情 | 问题式标题 | 写读者会自然提出的问题，下一行先给一句结论 |
| 异常和特殊情况 | 场景式标题 | 写清真实触发条件和怎么办 |
| 需要拍板的事情 | 决策式标题 | 把选择、取舍或尚未确认的事项写进标题 |
| 操作和测试步骤 | 动作式标题 | 直接说明先做什么或如何验证 |
| 最底层查询资料 | 名词化主题标题 | 只用于字段、错误码、索引等稳定检索标签 |

避免把“数据模型”“同步算法”“迁移门禁”“字段对照”“异常处理”作为首次阅读主线的标题。优先改成“Python CRM 需要保存什么？”“老师打开侧边栏后发生什么？”“哪些数据库改动现在还不能做？”等读者语言。

不默认生成 `0. 阅读导航`、按角色导航表或“附录 A/B/C”字母目录。先让标题本身可理解；只有文档确实存在多条独立阅读路径，而且导航能明显降低查找成本时才添加。

标题交付前执行一秒钟测试：只看标题和下一句话，是否能判断这一节解决什么、当前答案是什么，以及是否需要继续阅读。

## 四、视觉规则只路由，不重复定义

当出现以下任一情况时，必须读取并遵循同级 Skill `../jc-markdown-visual-writer-latest/SKILL.md`：

- 用户明确要求画图、视觉优先或降低心智负担；
- 文档用于 30 分钟技术评审或新人快速上手；
- 材料包含复杂流程、分支、系统交互、状态或数据关系；
- 主文需要以图承载大部分理解。

需要 Mermaid 或文本模板时，继续读取该 Skill 指向的 reference。图种、主线与细节盒子、节点长度、颜色、编号和兼容性全部以 `jc-markdown-visual-writer-latest` 为准。

本 Skill 只决定：

- 哪些问题值得画图；
- 哪些内容进入首次阅读主线；
- 哪些内容移入开发查询附录；
- 每张图必须回答什么问题。

不要在本 Skill 复制第二套 Mermaid 标准。

## 五、开发负责人默认阅读模型

当主要读者既需要理解业务、又需要做必要技术评审时，默认按下面的阅读比例组织：

```text
评审主文
├── 约 70%：目标、概念、流程、边界、影响和方案
└── 约 30%：会改变方案选择的关键技术设计

开发查询附录
└── 精确接口、字段、JSON、DDL、算法、代码位置和测试
```

技术内容是否进入主文，只问一个问题：

> 这个细节是否会改变方案选择、风险判断或上线决定？

会改变就进入主文；只影响具体实现就进入附录。

## 六、复杂技术文档按需使用双层结构

技术细节足够多、会干扰首次理解时，优先在同一篇文档内分成评审主线和开发查询层；内容较短时不要为了模板强行制造“附录”：

1. 第一部分是视觉优先的“30 分钟技术评审”。
2. 需要分层时使用明显的 `---` 结束首次阅读主线。
3. 第二部分使用“开发时再看：接口怎么调用”“Python CRM 需要保存什么”等直接标题，不默认使用字母附录或按角色导航。
4. 正文和附录不能重复粘贴相同流程、结论和架构。
5. 详细内容必须移动到正确层级，不能因为追求短而删除契约。

具体结构、图表问题清单和内容分层读取 `references/visual-technical-review.md`。

## 七、显式区分事实状态

复杂技术文档至少区分：

- **已确认业务规则**：可以进入设计和实现；
- **已实测事实**：写明环境、样本范围和日期；
- **合理推测**：不能当成接口契约；
- **待确认问题**：用稳定编号 `D1`、`D2` 管理；
- **示例值**：帮助理解，不得写死；
- **本期不做**：防止实施范围膨胀。

AI 或开发人员遇到会改变代码结构的待确认项时必须停下来求证，不能从字段名、示例或行业惯例推导默认实现。

### 需要用户拍板时，必须先写完整决策卡

当 `D1`、`D2` 等待确认事项会改变接口、数据库、权限、业务流程、兼容策略或发布范围时，不能只用一行表格或一句“待确认”让用户拍板。提问前必须把决策放回真实链路中解释清楚。

一组关联决策先提供一张总览定位图，标出每个决策位于哪两个系统、哪个接口或哪个数据环节之间。随后每个复杂决策至少包含：

1. **通俗定义**：它实际在决定什么、不在决定什么，避免把版本、接口、DDL 和安全问题混成一类。
2. **所在链路**：用 `graph LR`、`sequenceDiagram` 或 `stateDiagram-v2` 画出受影响的那一段；每张图只回答一个决策问题。
3. **具体改动**：列出真实项目/仓库、HTTP 路由、请求与响应字段、错误行为、代码文件或模块、配置、数据库表/字段/索引，以及对应测试。
4. **上下游影响**：说明请求从哪里来、结果流向哪里，影响当前主链路的哪个环节，是否要求其他团队或调用方配合。
5. **选项与推荐**：对每个可行选项写清收益、代价和推荐理由，不能只给抽象名称。
6. **阻塞边界**：明确“不确认会阻塞什么”和“不会阻塞什么”，区分核心开发门禁、独立增强和发布门禁。
7. **确认后的动作**：用户拍板后立即把状态改为“已确认”，同步更新实施顺序、接口清单、测试口径和范围说明；不能继续残留相互矛盾的“待确认”“推荐”文本。

精确改动尚未从代码或数据库核实时，要写明缺少的证据和下一步只读检查，不能编造文件、路由或表名。多个简单决策可以共用一张总览图；会改变不同链路环节的复杂决策必须分别画图。

交付前追加一次决策可执行性检查：用户只看总览图、决策卡标题、推荐方案和影响表，是否能在几分钟内理解取舍并明确回答“选哪个”。

## 八、AI 实施门禁

开发查询附录不等于 AI 实施计划。只有同时满足以下条件，才产出“可直接执行”的计划：

- 用户明确授权进入开发或要求实施计划；
- 关键业务决策已经冻结；
- 已读取实际项目规则；
- 已检查当前代码、数据库和接口现状；
- 能写出真实文件路径、验证命令和预期结果。

条件不满足时，只能产出技术方案、证据附录或实施准备清单，不能伪装成可执行计划。

## 九、保存和命名

1. 先读取项目 `AGENTS.md`、`CLAUDE.md` 和文档规范。
2. 用户指定目录时使用指定目录；未指定时按项目现有分类选择，不能擅自创造目录体系。
3. 生成标题和文件名时读取 `references/naming.md`。
4. 项目仓库内使用相对链接；个人知识库遵循其内链习惯。
5. 密码、Cookie、Token、手机号、地址和私人标识统一脱敏。

## 十、交付前验证

### 人类快速阅读测试

- 保存已有机制讲解时，不以「1 分钟找结论」或「30 分钟评审」为由压缩原文；这两项检查适用于评审和查询文档。
- 能否在 1 分钟内找到结论、推荐方案和最大限制？
- 解释性章节是否优先使用问题式标题，并在下一行马上给出一句结论？
- 只看标题和下一句话，能否判断这一节是否值得继续读？
- 能否通过约 5 张核心图理解对象关系、目标流程、职责、触发和风险？
- 能否在 30 分钟内完成必要技术评审，而不阅读完整 JSON、DDL 和代码？
- 每张图是否只回答一个问题？
- 面向小白解释技术机制时，是否至少保留了一份可核对的原始代码、报文、日志、截图或实际运行结果？
- 抽象图之后是否回到同一份原始制品，帮助读者把图中节点重新对应到真实字段、分支或状态变化？
- 实测结果、来源事实、合理推断和模拟数据是否明确区分？

### 开发查询测试

- 接口、鉴权、数据模型、失败边界和验证证据是否可检索？
- 是否能通过直接的问题式、结论式、场景式或动作式标题找到细节？只有确实存在多条独立路径时才增加角色导航。
- 已确认、实测、推测和待确认是否清晰区分？
- 是否删除了正文和附录之间的重复内容？

### AI 执行测试

- 是否能找到真实文件、任务、测试和完成标准？
- 是否明确哪些决策尚未获准实现？
- 是否检查了实际代码，而不是只根据会议材料生成任务？

### 直述体社交稿测试

- 是否像一个人想清楚以后在正常说话，而不是套了“小红书文案”或诊断口吻？
- 核心判断单独拿出来是否已经有信息量？不够时是否先改判断，而不是加钩子？
- 是否以陈述句和判断句为主，先说结论，再解释原因、例子和边界？
- 结构是否匹配内容复杂度：单一观点自然分段，多个规则、冲突或步骤使用标题、中文编号和必要清单？
- 是否既避免无格式长文，也没有把简单内容机械拆成很多点？
- 使用 v2 时，对比句是否没有被当模板轮换，强调是否尽量落在句尾？
- 默认版和 v2 是否都按 `references/social-expression-rules.md` 检查了表达目的、六类句式和例外？改写是否保留事实、边界和原意？
- 是否删除“AI 说”“根据资料”“接下来逐一回答”等对话和生成痕迹？
- 是否没有擅自添加悬念钩子、焦虑话术、表情符号、关注收藏、互动提问和标签？
- 是否保留材料原有的不确定性，没有为了语气有力把推测写成事实？

保存为知识文档时，最终回复只需说明产物路径、主要读者、采用的模式和仍待确认的关键事项。用户要求直接得到朋友圈、小红书或其他发布稿时，最终回复直接给出成稿；只有确有必要时，再补一句使用说明。
