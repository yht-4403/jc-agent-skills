# 说明嗓（默认）

用于让人**信**、而不是让人**亲**的内容：产品与服务介绍、README、功能介绍、方法说明、社群或平台上的对外介绍。

来源：一段被逐句确认过的融合稿（附录 A）。这段稿子由三版演化而来，两版被否掉的留在附录 B 当反例——比规则更有约束力。

> **关于附录里的示例**：以下三段文案是为此方法构造的虚构示例，用于示范句式结构，其中的数字、行业和产品都不指向任何真实项目。若你自己使用本技能，把手写原文替换进去——锚点的约束力来自"这句话真的被人确认过"，虚构示例只能说明结构，不能替代语感。

## 先判断什么时候用它

一句话分：读者是在**评估一件东西靠不靠谱**，还是在**跟你打交道**。

- 评估 → 说明嗓（本文件）。不出现"我"，可信度由来源、口径和读者处境承担。
- 打交道 → 主理人嗓。前言、催材料、交付引导、答复具体某个人。

拿不准时看有没有具体读者对象：发给一个人的用主理人嗓，发给一群陌生人的用说明嗓。

## 句子规则

- **第一句给判断，不铺垫。** 判断可以是用户的原话，也可以是自己下的一句定论（"接口文档写不清楚，是有固定毛病的"）。
- **可信度用三样东西堆**：来源（这份方法从哪来）、口径（三百多份、从内部工具到对外 API）、标准（文档团队的实际审稿标准）。**不用"我做过什么"来堆**——一出现"我"，读者就从评估切换成社交，可信度反而变软。
- **把读者处境替他写出来。** 不是"解决你的文档问题"，而是"调用方看不懂参数含义、照着示例跑不通、报错信息查不到对应原因"。三条并列可以，但力量来自具体，不来自整齐。
- **"你"只出现在读者处境里**（"把你挡在门外"），不出现在安慰里（"你不用担心"）。
- **收尾落到能做的事**：能直接抄、照着做、今天就能开始。不写"希望能帮到你"。
- 长句用分号分层，不用箭头链；允许一个破折号接细项。

## 禁

在 L1 共用底座之外，本嗓音另外禁：

- 自述人称与主理人身份（"我做过评审""我在大厂看过"）→ 改成第三方陈述（"用的是文档团队的实际审稿标准"）。
- 安慰式收尾与祝福（"你不用自己摸黑试""希望能帮到你""你值得"）。
- 抽象卖点堆叠（"方法＋实战＋全链路＋实操细节"连着用四个）→ 抽象名词最多留一个，其余换成来源、口径、读者处境。
- 作者本人不用的比喻（"摸黑试"）。
- 替读者预设处境再解除（"你是不是一直在瞎试？"）。

## 附录 A：确认过的锚点（虚构示例，仅示范结构）

> 接口文档写不清楚，是有固定毛病的。这份清单来自三百多份公开 API 文档的逐字段比对，用的是云厂商文档团队的实际审稿标准，覆盖从内部工具说明到对外开发者文档。调用方看不懂参数含义、照着示例跑不通、报错信息查不到对应原因——从结构到字段说明，每一处都能对照着改。

用途：对外介绍的首屏（官网、README、平台介绍页同一份）。规则与锚点冲突时，以锚点语感为准。

## 附录 B：被否掉的两版（反例）

**第一版 · 抽象名词版**（用户评"缺代入感"）

> 接口文档写不清楚，是有固定毛病的。这份清单覆盖文档结构、字段说明、错误码、示例和版本管理，从内容规范到落地实操的完整方法，你都能直接照着改。

问题：抽象名词连用（清单、结构、字段说明、完整方法）。读者知道"很全"，但不知道跟自己有什么关系。

**第二版 · 主理人第一人称版**（用户评"不要说我之类的"）

> 接口文档写不清楚，是有固定毛病的。我在几家云厂商做过文档评审，比对过三百多份公开 API 文档，也帮几十个团队重写过内部说明。调用方看不懂参数含义、照着示例跑不通、报错信息查不到对应原因，这套清单就是一条条回答这几个问题。

问题：代入感对了，但"我在……做过"把读者从评估切换成社交。产品介绍要的是让人信，不是让人亲。

**融合版的取法**：身份用第三方陈述，代入感交给读者处境。
