# JC Work Coordination

让对方读完知道要帮哪一步、处理哪个对象，并能方便地开始处理。以用户原有的自然语气为准；技术分析可以深入，对接消息只带接收人完成这一步需要的信息。

## 按接收人的职责取舍

先判断对方能做什么、用户希望他做什么，再决定哪些事实必须进入消息。不要把完整排查报告缩小字号塞进聊天，也不要仅为了短而删掉操作对象、关键条件或定位入口。

- 对运维，域名、环境、服务、必要的端口或资源标识、部署链接有用；玩法、徽章数量、测试断言总数通常无助于改转发。
- 对研发，能复现问题的接口、参数、输入、现象和预期可能必须保留；不能把它们压成“接口有问题”。
- 对产品，业务规则、具体例子及待确认的选择可能就是必要信息；数据库字段和排查过程通常可以留在背后。
- 对负责人，是否影响交付、当前阻塞、已知时间约束及需要他协调什么，比内部技术过程更有用。

对每个细节问：删掉后，对方还能找对对象、理解请求并执行吗？能则删；会增加误操作、来回追问或错误判断则留。平台链接承担定位和详细背景，不把页面里的所有字段复制到消息里。

## 写成同事间的消息

让请求在开头附近出现，用“能不能帮忙切一下”“帮忙看下”“想确认一下”这类具体动作。不要先铺一段已经做完的分析，再让对方找诉求。

根据上下文自然组合：简短招呼、请求及对象、最小理由或对比现象、定位信息/链接。不是固定表单；对象、理由和链接够了就停。熟悉的同事可以沿用“哈咯”等用户招呼，已有对话直接接话，不给每条消息强加开场白。

验证通常只需要能支撑请求的关键对比，例如“域名访问还是旧接口，直连新 Pod 正常”。只有接收人需要进一步复现或判断时，才加具体接口、参数、时间或返回值。不要为了证明自己排查认真而列完测试数量、所有日志和中间假设。

保留人的自然语气、常用术语及已有称呼，不自动升级为“请协助核查相关配置并推进问题闭环”等公文写法，不添加过度致歉、套话或无依据的催促。清楚和礼貌可以同时成立，动作要明确。

## 事实、猜测与执行对象

- 已验证的现象直接说；原因未确认时，保留“可能”“应该”等余地。已知发生过 namespace 迁移，可以把迁移作为排查线索，不能写成已确认对方遗漏，也不要把猜测必填进每条消息。
- 准确保留用户给出的域名、环境、参数、端口、URL、负责人和 @ 提及。不要凭空补联系人、截止时间、紧急程度、业务影响、承诺或“已测通过”。
- 只放完成本次请求需要的定位信息。环境配置里的密码、Token、私钥等不进入对接正文。
- 请求“切到新服务”时，指向可持续使用的服务或部署对象；已知 Pod IP 可辅助定位，不把临时 Pod IP 偷换成永久域名绑定方案。若只知道现象、不知道正确目标，就请求核对，不编造修改值。
- 决定能否写清请求的信息缺失时，只问最关键的一项；信息够用就直接写，语气和格式偏好不构成阻塞。

## 交付方式

默认给一版可直接发送的消息。“给我一句”“一句话发给他”通常是在要求一条短消息：减少信息和阅读负担，允许自然的短句、问句或换行，不为了句号数量把细节串成一个长句。若用户明确要求只能有一个句子，就按一个句子写。不要附分析、多个版本或额外操作清单；必要链接可独占下一行。用户要求比较或解释时，另行说明差异，分析不混进代写正文。

让消息接续现有对话：对方已完成修改时请求复测，对方需要信息时先回答所问内容，跟进时引用当前事项并问进度。无事实依据时不擅自加“今天必须”“线上事故”等压力。

会话里的称呼约定（如“好的JC”）放在代写消息之外。不要把对用户的答复前缀写成对接对象的称呼。这个 Skill 生成文案，写文案本身不授权发送消息。
