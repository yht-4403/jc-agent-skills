# 对接实例与核对场景

## JC 的真实示例

2026-10-13，JC 在 Java staging 域名转发排查后提供了这条偏好的消息：

> 哈咯，staging-rocket-ai-backend.codemao.cn 的转发绑定能不能帮忙切一下？应该是之前换namespace的时候没有处理吧。 我刚刚部署的rocket-ai-backend 的staging服务（Pod IP：172.16.181.176，应用端口：5000），域名访问还是旧的接口，直连 Pod IP 才可以正常使用@左嘉彦
>
> https://crp.codemao.cn/release/mission/127668

这里的域名、IP、端口、姓名及链接是这次沟通的历史内容，不能视为其他任务的现行配置或联系人。

这条消息同时完成了几件事：

| 写法 | 接收人获得什么 | 改写时保留什么 |
| --- | --- | --- |
| 开头请求“转发绑定能不能帮忙切一下” | 立即知道要帮哪一步 | 动作及域名，不用先读报告 |
| “应该是之前换namespace的时候没有处理吧” | 一个与已知迁移背景有关的排查方向 | 不确定语气，不升级为归责结论 |
| 服务、环境、Pod IP和端口 | 定位这次新部署的对象 | 技术标识精确，数量按需要取舍 |
| 域名旧接口、直连正常 | 为什么应查转发关联 | 一组足以支持请求的对比 |
| @提及和部署链接 | 谁来接、从哪里开始查看 | 用户给出的负责人和可操作入口 |
| “哈咯”“帮忙切一下” | 同事间自然、低负担的语气 | 沿用关系和上下文，不固定公文模板 |

前一版把17/29个接口、三个业务查询、200/500及“说明新容器正常”等分析全部写进一句话。两版都把请求放在开头，但前一版的开头嵌入了命名空间、镜像版本和服务限定，随后又串入大量验证细节。JC先用短问句提出请求，再分句交代可能原因、新服务和现象，阅读负担更小。接口数量有助于诊断，但不必成为每条对接消息的固定材料。

JC此前说“给我一句话”，随后给出的偏好稿实际包含几个短句和一个独立链接。这说明此处更应理解为“一条简短可发的消息”，不能把它机械执行成“只用一个句号但用逗号塞满细节”。新任务若明确要求仅一个句子，则仍遵守该限制。

“应该是之前换namespace”只作为猜测。若新的原始材料没有迁移事实或背景，不主动添加这个原因；如果已掌握明确原因，直接写已确认事实即可。

## 内容核对场景

下面除真实示例外均为虚构练习，用来检查取舍是否随接收人职责变化；参考稿只是可能的写法，不要求逐字复制。

### 运维：有定位信息，压缩排查过程

原始材料：staging新部署可直连，域名仍提供旧接口；给出了域名、当前部署链接、服务和端口；有接口数量、返回码、构建过程、三种玩法测试数据；怀疑迁移后绑定未同步，但没有查到入口规则。

适合的输出就是上面的JC真实示例；可以更短，但保留域名、希望调整绑定、直连与域名的差异及定位入口。不得把猜测写成“确认是运维迁移遗漏”，不得要求永久绑定临时Pod IP。

### 研发：复现所需参数不能删

原始材料：用户在test请求 /api/interactivelesson/badges，page=last、pageSize=2，已有3枚徽章，却返回了第一页2枚；需要最后一页1枚；相关请求已复现，完整请求记录有链接；和本次修改无关的构建日志很多。

参考稿：

> 哈咯，徽章分页这边帮忙看下：test里已有3枚徽章，传page=last、pageSize=2时返回的是第一页2枚，预期应该是最后一页1枚；我这边能复现，完整请求在记录里。

这里的徽章数量和分页参数是复现所需信息，必须保留；不能机械套用运维示例，把所有业务细节都删掉。原始材料没有链接值时，不虚构URL。

### 产品：业务条件是对接对象

原始材料：要确认同课期、同关卡完成拼图和绘画后，是分别获得徽章还是只获得一枚；尚未确定产品规则；技术实现涉及唯一键和表结构，但产品无需了解这些。

参考稿：

> 想确认下，同一个课期、同一关卡里，孩子分别完成拼图和绘画，是各拿一枚徽章，还是这个关卡只拿一枚？

保留课期、关卡、玩法和两个选择；不能为了短写成“确认一下徽章规则”。不要把未确认的业务规则当成事实。

### 负责人：说清影响和需要的协调

原始材料：新应用已部署，外部域名还连旧服务，当前阻塞staging业务联调；需要负责人协调运维处理；没有已承诺的完成时间。

参考稿：

> staging新服务已部署，域名目前还连着旧服务，业务联调暂时卡在这里，能帮忙协调运维调整一下绑定吗？

这里交付影响必须保留，Pod IP、Java版本和SQL迁移过程通常可以留在详细记录里。没有给出的时间和严重程度，不添加“今晚必须上线”或“生产事故”。

### 跟进：不重复已经说清的背景

原始材料：上一轮已发域名转发请求，对方还未回复；用户只想问进度，没有明确截止时间。

参考稿：

> 哈咯，staging域名绑定这边现在处理得怎么样了？改好后喊我一下，我这边再测一轮。

不把完整首条请求重新贴一遍，不编造紧急程度，不把“还没回复”写成对方拖延。

### 回复推进：对方说已改好

原始材料：运维回复“绑定已调整”，用户尚未复测，只想先回复对方。

参考稿：

> 收到，谢谢，我这边再测一下域名访问，有结果同步你。

不能写成“已经验证正常”或“问题已解决”；收到处理反馈与测试通过是两个不同状态。

## 应触发与不应触发

| 用户请求 | 是否使用 | 判断依据 |
| --- | --- | --- |
| “整理一句发给运维，让他帮忙切绑定” | 是 | 接收人、动作和聊天文案明确 |
| “这段发给产品确认太啰嗦，改成我的口吻” | 是 | 工作对接改写，需要保留业务条件 |
| “同事说已经改好了，我回他一句” | 是 | 接续协作对话 |
| “学习我这条对接消息和你那条的区别” | 是 | 需要分析取舍与用户语气 |
| “为什么Service的8080能转到容器5000？” | 否 | 技术解释，没有对外消息任务 |
| “排查staging接口500的根因” | 否 | 应继续调查，不能用写话术代替排查 |
| “生成正式的故障复盘报告” | 否 | 正式报告需要系统信息与完整记录 |
| “写BOSS直聘上的首次求职招呼” | 否 | 属于求职沟通，由对应技能处理 |

## 内容检查标准

检查接收人能否找到具体对象、知道要做什么、获得必要理由和定位入口；检查验证结论和原因猜测是否保持原始状态，是否添加了未提供的事实；检查输出是否像用户与同事的自然对话，而非压缩后的技术报告；最后检查删减有没有导致接收人必须再追问关键参数或业务条件。

结构校验和这些场景的内容核对不等于独立模型行为测试；实际自动触发与新任务表现应根据后续真实使用继续核查。
