# 质量门

质量检查分成两类：工程底座必须严格，领域表达保留自由度。

## 硬性检查

### 来源与证据

- 来源可以定位，原文和二次稿没有混淆；
- 原子引用的 source、chunk、行号和短引真实存在；
- 已处理、未处理和跳过范围说得清楚；
- 推断、冲突和外部补充没有冒充作者原话。

### 工程关系

- ID 不重复，跨文件引用存在；
- 场景引用的原子存在，执行 Skill 和路由入口存在；
- 发布包不泄漏本地绝对路径、付费全文和私有附件；
- 高风险领域保留必要的专业审核和权限边界。

这些适合由脚本阻断。

## 语义检查

### 地图是否真的解释了领域

地图应让人理解主要结构、核心方法和常见卡点，但不要求固定栏目。检查它有没有机械抄目录、堆术语、虚构统一路线，或把工程归纳说成原书理论。

### 原子是否保留了意思

抽查重要原子，看条件、语境和边界是否丢失。核心方法应有足够解释；简单事实和案例不必为了格式漂亮硬凑概念四问。

### Skill 是否有明确方法

执行 Skill 应有清楚的中心任务、底层判断和工作过程。它能够使用用户材料，而不是只输出泛泛建议。不同 Skill 可以是诊断、生成、审查、训练或工具，不要求结构完全一致。

### Reference 是否提供了必要深度

重要方法要讲透，容易混淆的地方要有案例或反例，窄场景可以简洁。Reference 的长短由问题决定，不以栏目数量判断质量。

### 路由是否自然

用户不需要知道内部工程名词。路由能用用户会说的话识别问题，并根据已有结论继续导航。没有匹配项时明确知识缺口，不强行套相邻方法。

## 用真实任务测试

至少测试代表性正常问题、容易混淆的问题、信息不足的问题和越界问题。重视实际行为：是否选对方法、是否引用材料、是否做出有用产物、是否承认未知。

对于需要长期练习的领域，再增加失败反馈和后续纠正测试；对于一次性工具，不必为了统一而增加训练环节。

## 完成状态

- **样本链路**：少量代表材料已经走通原子、地图、Reference、Skill 和测试，只能说明方法可行。
- **批量可用**：主要来源和高频任务已经覆盖，剩余范围明确。
- **全量完成**：目标资料都有处理状态，关键方法和场景完成复核，代表性 Skills 通过独立测试。

不要用“字段齐全”“地图很长”“原子很多”作为完成证据。最终问题始终是：这套 Skill 是否真的掌握了来源中的方法，并能在真实任务中用出来。
