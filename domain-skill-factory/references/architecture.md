# 工程架构

工厂分成两个世界：构建工程负责保存证据和进度，发布 Skills 负责让用户解决问题。不要把构建工程的字段感带进最终对话体验。

## 构建工程

```text
<project>/
├── project.json
├── SOURCE_OF_TRUTH.md
├── corpus/           # 原始来源与可定位文本块
├── atoms/            # 可检索的知识原子
├── maps/             # 领域地图
├── scenes/           # 常见问题与方法之间的连接
├── references/       # 待发布的领域知识
├── skills/           # 路由与执行 Skills
├── evals/            # 代表任务
├── reports/          # 覆盖与审计
└── state/            # 批次和处理状态
```

这些目录帮助长任务恢复、复核和增量更新，不代表最终 Skill 必须采用同样的写作结构。

## 发布套件

发布时只保留真正会被调用的 Skills、References、必要脚本和少量证据说明。原文全文、绝对路径、付费附件和内部状态留在构建工程。

一套复杂领域通常包含一个路由入口和若干执行 Skills。执行 Skill 可以共享知识库，也可以各自携带 References，取决于调用时怎样最自然。

## 从知识到 Skill

原子库适合保存细节，地图适合展示关系，Reference 适合讲透一套方法，SKILL.md 适合规定怎样工作。不要让任何一层替代其他层：

- 原子很多，不代表已经形成方法；
- 地图完整，不代表能处理具体问题；
- SKILL.md 很长，也不代表知识有来源；
- 文件结构一致，不代表用户体验自然。

工程层追求一致和可校验，语义层追求忠实、清楚和有用。
