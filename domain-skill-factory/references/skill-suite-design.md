# Skill 套件设计

DBS 和 TDS 的共同点，不是文件结构完全一致，而是每个 Skill 都有鲜明的领域方法。

一个好 Skill 通常能说清三件事：它主要解决什么，它用什么框架判断，它怎样把判断落到用户当前问题上。

## 先提炼领域方法论

不要从“要建几个 Skill”开始。先从资料中找到：

- 作者最相信哪些底层判断；
- 面对问题时反复使用哪些分析角度；
- 哪些步骤、信号或分类真正影响下一步；
- 哪些案例最能说明方法为何有效或为何失效；
- 哪些边界不能靠这套方法处理。

这些内容构成领域 Skill 的骨架。原子库提供证据和细节，Skill 不需要把所有原子逐条搬进去。

## 怎样划分 Skills

当一组问题共享同一套判断框架和工作方式时，可以归入一个 Skill。只是案例不同、行业名词不同或表达不同，通常放进 Reference。

当用户目标、判断逻辑或最终产物明显不同，才考虑拆成不同 Skill。例如销售中的客户开发、需求诊断和谈判，虽然都属于销售，但它们关注的信号和动作不同。

不要追求粒度完全一致。DBS 里有大型诊断 Skill，也有完成一个具体动作的工具 Skill；这是正常的。

## 执行 Skill 的常见结构

以下结构来自 DBS/TDS 的共同写法，可以按领域取舍：

### 核心任务

先用一两句话说明这个 Skill 到底负责什么、不负责什么。一个明确的中心任务，比完整功能清单更容易形成稳定行为。

### 底层方法

写出几条真正会改变判断的原则、公理或核心模型。把原理讲透，必要时用例子和反例。不要堆很多貌似精准但无法解释的自造术语。

### 工作过程

说明拿到用户问题后通常怎样处理。诊断型 Skill 可以逐维判断，生产型 Skill 可以按步骤完成产物，审查型 Skill 可以按一组标准扫描。

过程需要稳定，但不必把每次对话锁死。简单问题可以直接完成，复杂问题可以边判断边让用户校正。

### 判断信号

列出有代表性的正面信号、失败信号和容易混淆的情况。让 Skill 知道什么证据支持哪种判断，而不是只会复述理论。

### 输出

给一份大体结果形态即可，例如诊断报告、行动方案、修改稿、检查清单或决策建议。领域不同，输出自然不同；不要求所有 Skill 都附训练计划和反馈表。

### 案例与边界

保留几类典型案例、反面案例和越界情况。案例的作用是教会模型怎样使用方法，不是装饰 Reference。

## Reference 怎样写

Reference 负责补充 SKILL.md 放不下的领域内容。它可以是一套完整方法、一个常见问题、一个案例库、一份标准或一个操作模板。

不要规定每篇 Reference 必须有同样的栏目。判断它是否合格，只看三点：

1. 什么时候应该读它；
2. 读完以后会改变什么判断或产物；
3. 它有没有足够解释、案例或证据，避免生搬硬套。

一个重要方法可以写成较完整的知识包；一个窄场景也可以只写几段判断和案例。内容密度由问题决定。

## 路由 Skill

当套件包含多个执行 Skills 时，建立一个简单入口：

- 用户第一次来时，告诉他可以交付什么问题或材料；
- 任务开始前，根据目标和处境选择最相关的 Skill；
- 一个 Skill 做完后，根据实际结论推荐下一步；
- 用户已经明确想做什么时，尊重他的选择。

路由只负责导航，不复制所有领域知识。路由表可以使用用户会说的话和典型问题，不必暴露工程字段。

## 卡点驱动怎样进入 Skills

卡点驱动是一种使用原则，不必成为所有 Skill 的固定格式。

当用户在学习、执行或复盘中受阻时，Skill 应尽量把宽泛评价还原成一个具体问题，再给当前最有价值的动作。如果任务本身只是查资料、转换文件或生成一个明确产物，就直接完成，不必强行设计练习闭环。

对于需要长期提高的能力，可以加入：当前阶段、主要卡点、一次练习和下次反馈。对于一次性工具，清楚完成任务和说明边界就够了。

## 避免 AI 味

- 少写“所有情况必须包含十五个字段”，多讲为什么这样判断。
- 少创造层层嵌套的新名词，多沿用来源中已经成熟的说法。
- 少给空洞的全能流程，多保留有代表性的案例。
- 不为对称而强行拆出同样数量的模块。
- 不把每项建议都包装成指标、样本量和状态机。
- 不把不确定的领域经验写成精确到小数点的普遍规律。

最终检查：读完 Skill 后，模型是否像掌握了一套有来历的方法，而不是拿到了一张需要机械填写的项目表？
