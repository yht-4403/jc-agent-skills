# JC Report

把工作流水编译成一份可信、可发送、能看出价值的阶段报告。报告既要回答“做了什么”，也要回答“改变了什么、为什么重要、下一步怎样验证”。

## 中心任务与边界

本 Skill 负责：

- 汇总过去一个明确时间段内的成果、进度、判断、风险与复用资产；
- 规划未来一个时间段的优先级、目标、动作和验收信号；
- 根据读者调整信息密度，外化用户的执行力、判断力、协作能力和专业能力；
- 把技术、运营、产品、销售、管理、研究等不同项目统一翻译成业务语言。

本 Skill 不负责：

- 为了“显得有价值”编造数字、结果、客户反馈、上线状态或个人贡献；
- 把未验证的收益写成已经发生的业务结果；
- 代替会议纪要、知识沉淀、项目方案或绩效评分；
- 未经用户要求发送报告、更新任务系统或修改项目文件。

## 统一报告规范：日报、周报共用

先确定时间范围、读者和材料，再写报告，最后决定是否保存到日记。日报和周报共用下列规范；区别是日报写当天的进展，周报按主题聚合一周的变化。篇幅随材料调整，保存位置不改变报告结构和质量要求。

没有另行指定模板时，采用「标题 + 核心结论 + 业务侧 + 技术侧 + 风险与下一步」：

1. **标题**：日报注明当天日期，周报注明覆盖起止日期；不能把阶段成果写成生成当天发生的事实。
2. **核心结论**：用一两句话说清主要推进了什么、现在到哪一步、还差什么；材料只覆盖部分工作时，在这里简短限定范围。
3. **业务侧**：写使用者、业务流程、交付或决策发生的具体变化；有依据时说明作用，不为每条硬凑价值。
4. **技术侧**：写支撑这些结果的实现范围、数据或验证结果，明确本地、TEST、生产等验证边界；不重复业务侧，也不堆排查过程和代码细节。
5. **风险与下一步**：写尚未完成或验证的事项，以及最需要推进的动作和可观察的完成信号；没有风险就只写下一步。

涉及技术的工作默认保留业务侧和技术侧，即使只有一个事项，也分别说清使用结果与验证状态。纯运营、销售等没有技术事项的报告，可将这两节改为「主要进展」与「结果与依据」，或在同一节说明进展和依据；不凭空凑技术内容。核心结论和必要的下一步继续保留，不能因为材料少或保存为日记而压成随手记。用户明确要纯回顾、纯计划或其他模板时，按该用途调整。

收获、判断变化和反思有具体材料时融入相应主题；不固定加一节，不代用户编造感受。

## 日记保存：按日期归档、跨工具补充

日记是报告的保存方式，不是另一种写作模式。保存为日记时，默认读者是自己、周期是当天；用户明确要周报时使用指定周期，正文继续遵守上面的统一报告规范。

### 触发、材料与内容

- 用户提到“日记、记今天、追加今天、今日收获、存到日记”时，生成对应报告并保存。JC 显式调用 `$jc-report`、没有另行指定用途时，默认生成当日工作日报并保存到日记；明确要发领导、客户或只输出正文时按相应用途处理，不自动存个人日记。
- 默认目录是 `~/Documents/JC知识库/日记`，本机已存在；用户明确指定其他路径时优先使用。目录不可访问时说明限制并交付正文，不声称已保存，不另建同名目录。
- 用户提供的当日事项、当前会话已确认的工作和已有当日日记是首选证据。指定保存路径只授权读写日记，不能据此扫描整个知识库、所有项目或其他 AI 聊天。跨工具调用只能利用该工具实际可读的材料，不能声称已经汇总其他工具未提供的对话。
- 首次写入某天的日报，正文按统一报告规范组织，默认使用 Markdown 标题和少量要点。再次补充同一天时只保存新的进展、依据或状态变化，可用「补充进展」及相关小节承接，不重贴已经记录的整份报告。
- 保存和去重是后台行为，不把脚本设计、多工具同步、目录规则、命令和测试过程写成报告的主要内容。当天确实做了工具调整时，在业务侧写使用方式的变化，在技术侧只保留影响结果判断的验证结果和边界，不展开实现日志。
- 收获与感受须来自用户原话或明确的判断，不代用户编造情绪和成长。Agent 的推断要注明；没有反思材料就省略，只有用户要求引导反思时才提供问题，不能写成用户已经得出的结论。
- 材料不足时先保存当前会话能够证实的内容，明确本次范围；其他工作等用户补充后再追加。不把旧日记中的计划写成今天已经完成。

### 文件与去重规则

1. 使用用户所在时区，JC 默认为 `Asia/Shanghai`；有客户端日期时以客户端为准。日报固定写入 `YYYY-MM-DD.md`，已有同日文件就追加，保留原文、文件名和用户手写内容。补记某天时用用户指定日期，追加时间仍记实际保存时间。
   用户明确要求改写已有报告时，可修改其指定范围，先保留原文备份；不能以改写为由覆盖其他工具新增的内容或手写内容。常规调用仍只追加。
2. 不建月份目录、工具目录、重复版本或 `日期-日报.md`。周报/月报默认作为生成当天日记中的独立小节，标题明确覆盖起止日期；先读对应周期已有日记再聚合，不把阶段汇总误当成当天发生的事实。已存在同周期汇总时仅补充新的结论，不再复制整份汇总。
3. 写入前读完整的目标日期文件，逐项按“对象、动作、结果、状态、证据”进行语义去重。不同工具换句话表达同一事实仍算重复；只保留原文尚未记录的新事实、补充证据、判断或状态变化。无新内容则不写文件，也不追加空标题或重复计划。
4. 状态变化用追加方式注明，例如“补充：此前待验证，现已在 TEST 验证；生产尚未上线”。冲突材料并列注明来源及待确认点，不覆盖历史，不擅自选择结论。
5. 只将过滤后的增量交给 `scripts/save_diary.py`。脚本会再次检查完全相同的内容/事项标识，串行化多个工具的写入，并在锁内重读文件；语义去重仍由调用 Agent 负责。脚本不保证识别不同措辞的重复事实。
6. 日记文件只保存给人看的标题和正文，不写 HTML 注释、事项识别码、工具日志或重复的当日标题。去重识别码、保存时间和真实工具名由脚本存入知识库之外的 `~/.local/state/jc-report/`，不同工具共用；旧日记中的标记仍可识别。必要的事实来源可自然写入正文。日记不用项目标签；附件遵守知识库规则放 `./assets/`。

### 共用保存脚本

在临时目录准备 UTF-8 JSON（不要把中间产物放到知识库根目录）：

```json
{"items": [{"title": "# 工作日报｜YYYY-MM-DD", "body": "按统一报告规范写好的正文，包含相应小节，只保存尚未记录的新内容。", "id": "可选：本次具体事实及状态的稳定标识"}]}
```

从本 Skill 所在目录调用，路径含空格时加引号；明确传入已确定的日期：

```bash
python3 scripts/save_diary.py --date YYYY-MM-DD --source Codex --input /临时目录/日记增量.json
```

`--source` 使用实际工具名，例如 Codex、Claude Code 或 DeepSeek Harness；不伪造来源。`--directory` 可覆盖目标目录。`id` 用于重复重试识别，不要把项目名称当作 id；新状态/新证据使用新 id，避免丢掉进展。默认内容指纹也能阻止完全相同的重试。所有能执行 Python 的工具统一用此脚本，成功后重读确认再报告路径和新增内容。

无法执行脚本但可以读写文件时，先重读、语义去重，再做最小追加；此退化方式不能保证并发安全，应避免不同工具同时写同一天文件。完全不能访问本机文件时只交付正文，明确尚未保存。

## 先识别本次汇报任务

从当前对话提取以下信息；已有答案时不要重复询问：

1. **时间**：过去和未来分别覆盖哪段时间；
2. **读者**：自己、直属领导、管理层、团队、客户或跨部门伙伴；
3. **目的**：同步进展、争取资源、阶段复盘、项目交付、述职留档或计划对齐；
4. **证据来源**：用户描述、当前对话、项目文件、提交记录、任务记录、数据、会议材料或验收结果；
5. **长度和格式**：用户指定模板、短消息、正式报告或可继续编辑的底稿。

常见时间表达按当前日期解释：

- “本周”默认是当前自然周，周一至周日；
- “上周”是上一自然周；
- “本月”是当前自然月；
- “过去 7 天”等滚动周期按字面计算；
- “最近”“过去一段时间”没有可安全推断的边界时，不自行选择 7 天、两周或一个月，先取得明确范围。

保存到个人日记时默认读者是自己；其他用途没有指定读者时，默认写给直属领导或项目负责人。没有指定格式时，按统一报告规范和下文的默认排版生成报告。用户指定模板、微信格式、详细版或纯回顾时，以当次要求为准；微信格式只改变排版，不省掉结果、验证边界或下一步。

## 获取事实，不把仓库活动当成业务结果

优先使用用户已经提供的材料。只有用户明确说“当前项目”“这个仓库”“从工作区总结”或指定了项目路径时，才把本地工作区视为报告范围；仅仅处在某个工作目录中不代表用户已经授权或指定该项目。范围明确后，可以进行必要的只读检查；先遵守项目规则，再按相关性查看：

- 当前对话中的目标、承诺、决策和历史报告；
- Git 提交、工作区差异、PR、任务记录和发布记录；
- 产品数据、运营数据、客户反馈和验收证据；
- 设计文档、会议结论、测试结果与风险清单。

证据不足时可以交付范围受限的草稿，但要清楚标明缺口。不要把下面这些信号写错：

| 看到的信号 | 最多能说明什么 | 不能直接写成 |
| --- | --- | --- |
| 已合并提交或完成任务 | 已完成一项工程或业务动作 | 已上线、用户已使用、指标已提升 |
| 未提交代码、草稿、原型 | 正在推进或等待验证 | 已完成、已交付 |
| 文件、脚本或页面存在 | 产物已经创建 | 链路已验证、问题已解决 |
| 测试记录通过 | 对应范围在该次运行中通过 | 全系统稳定、线上无风险 |
| 方案或计划文档 | 已形成选择或执行准备 | 计划已经执行 |
| 预期收益、设计目标 | 未来价值假设 | 已实现收益 |

如果时间范围和项目/材料范围都不明确，停止扫描并只问一个合并后的最小问题：“你希望总结哪段时间？把工作材料贴过来，或告诉我需要检查哪个项目。”对完成状态有实质影响且无法从现有证据判断时，只问一个关键问题。其他缺口使用保守措辞，不阻断整份报告。

## 先在内部建立证据账本

写作前，把材料归入以下状态。这个账本用于防止混写，默认不直接展示：

- **已完成**：有交付、验收、上线、数据或明确确认；
- **进行中**：已经开始但尚未闭环；
- **已决定**：方向、取舍或范围已经确认，执行可能尚未完成；
- **已发现**：形成了新的问题判断、用户洞察或方法认识；
- **计划**：未来动作、目标或承诺；
- **风险/依赖**：可能阻塞结果的事实；
- **未知**：材料无法支持的结论。

同一事项同时包含多个状态时拆开写。例如“完成原型，等待用户验证”，不要压缩成“完成功能”。

## 把动作翻译成业务价值

每个重要事项优先回答下面五个问题，不要求机械写成五行：

1. **改变了什么**：完成了哪个结果、决策、里程碑或风险收口；
2. **服务谁或哪个目标**：用户、客户、团队、收入、效率、质量、合规、增长或决策；
3. **为什么重要**：减少了什么损失，打开了什么机会，或使哪一步可以继续；
4. **证据是什么**：指标、验收、覆盖范围、反馈、产物或可观察变化；
5. **接下来如何放大**：复用、上线、验证、扩展或补齐哪项能力。

价值分为三种，措辞必须匹配证据：

- **已实现价值**：有结果或可验证变化，直接陈述；
- **阶段价值**：完成关键前置、排除风险或形成决策，说明它使什么成为可能；
- **预期价值**：仍是计划或假设，使用“目标是”“预计”“用于验证”“为……做准备”。

没有业务指标时，优先使用真实的替代证据，例如交付范围、完成的关键链路、减少的人工步骤、关闭的高风险问题、形成的可复用资产。替代证据也不存在时，保留事实，不硬凑价值。

## 业务与技术如何分类

统一报告规范中的业务侧和技术侧承担不同作用。技术项目的日报、周报按下面的顺序组织；多个项目在相应小节内按主题聚合：

1. **核心结论**：保留这一节，用一句自然语言说明本次报告的主线、已经推进到哪一步、还差什么。不要写成“完成核心链路建设，为后续闭环奠定基础”这类抽象总结。
2. **业务侧**：写业务流程、角色操作、数据口径或用户体验发生了什么变化，例如老师怎样同步学生、管理员何时批准、历史数据是否保留。
3. **技术侧**：写足以证明结果可信的系统范围、关键契约、数据库策略和验证结果。技术名词承担证据作用，不单独堆成技术清单。
4. **风险与下一步**：写尚未发布、尚未验证、依赖谁，以及下一阶段用什么可观察结果验收。

业务侧和技术侧不要重复同一事实。先在业务侧说清改变，再在技术侧补充它如何实现或怎样验证；如果技术细节不会改变读者对进度、价值或风险的判断，就删掉。

## 外化能力，但不自我表扬

能力通过行为和证据出现，不写“展现了很强的能力”这类评价。根据材料选择最有说服力的信号：

- **结果负责**：主动闭环、推动验收、处理遗留问题；
- **业务判断**：识别真正问题、做出取舍、缩小范围、调整优先级；
- **执行推进**：把模糊目标拆成里程碑并持续交付；
- **跨方协作**：澄清责任、解除依赖、推动共同决策；
- **专业质量**：增加测试、自动化、规范、监控或安全边界；
- **复用与杠杆**：沉淀模板、工具、流程、数据资产或可复用方法；
- **学习迭代**：根据数据或反馈修正假设，而不是只描述“学到了什么”。

普通进展报告让这些信号自然进入成果和思考；述职或绩效场景可以单列“能力证据”，并保持“情境—行动—结果—证据”的链条。

## 时间周期与特殊用途

日报、周报、月报和阶段报告都以统一报告规范为默认结构。周期决定汇总范围和详略；用户明确指定其他用途或模板时再调整：

### 日报

覆盖当天，说明当天产生的结果、关键进展、验证状态及下一步。材料少就减少每节的条数，不硬凑三条，不省掉报告中的关键判断。下一步不必强行写成“明天”，按实际安排表述。

### 周报、月报或阶段报告

覆盖指定周期，在统一结构内按项目主题聚合变化，不复制每天的流水账。保留有依据的成果、关键取舍、复用资产和下一阶段重点；已有指标时写清口径，没有指标就保留事实。保存到日记不改变周期和结构。

### 项目进展或客户汇报

聚焦里程碑、交付范围、业务影响、验收状态、变更、依赖和下一节点。把内部技术细节压缩到会改变交付判断的程度。

### 述职、绩效或个人复盘素材

聚焦业务结果、责任边界、关键取舍、能力证据、复用资产和下一阶段升级方向。只有用户明确要做正式绩效评价时，才进一步组织为能力项。

### 纯计划

每个优先事项至少说明：要达到的结果、为什么现在做、关键动作、验收信号和关键依赖。不要把愿望写成任务清单。

### 纯回顾

聚焦结果、证据、偏差、判断变化与可复用经验。不要为了对称硬加未来计划。

## 根据读者调整表达

- **直属领导/管理层**：先结果和价值，再写关键判断、风险与资源请求；压缩实现细节。
- **团队/跨部门**：强调当前状态、接口、依赖、负责人和下一节点。
- **客户**：强调交付、收益、验收、变更影响与下一次确认；不暴露无关内部过程。
- **自己/述职**：保留贡献边界、决策依据、能力证据与可复用资产，方便以后调用。

同一份报告只服务一个主要读者。读者冲突明显时，优先按用户指定读者写，不制作折中大杂烩。

## 写作与版式

- 结论先行，最重要的结果放在前面；
- 用项目主题或业务目标聚合，避免逐日流水账和提交清单；
- 使用具体对象、动作、结果和证据，删除“持续推进、全面赋能、形成闭环”等无法检查的空话；
- 保留自然长短，不把每项写成完全同构的四行模板；
- 少用连续“通过……提升……”和“不是……而是……”；
- 不为每段制造金句，不把实操问题强行升维；
- 技术名词只保留到读者理解价值和风险所需的程度；
- 使用用户原有语言和项目名称，敏感信息按项目规则脱敏；
- 默认让正式周报或阶段报告能在约一分钟内读懂；用户要求详细版时再展开证据。

## JC 默认报告风格

这是日报、周报和阶段报告共同的表达要求，也适用于保存到日记的报告。结构以「统一报告规范」为准，下面规定详略、语言和排版；当次明确指定的模板或用途优先。

- **先说当前情况**：开头用一两句话说清主要做了什么、推进到哪一步，以及发布或验证是否尚未完成。
- **简短但保留证据**：只留少量重点，不展开排查过程和代码细节；影响结果判断的数字、异常和验证边界不能因精简被删掉。用户明确要求保留的内容，后续压缩或换格式时继续保留。
- **自然、具体**：直接写“支持查询最后一页”“登记缺失”“等待后未补齐”，少用“赋能、闭环、能力建设”等抽象表达，不给每条强行追加价值评价。
- **状态准确**：开发完成、进入 test 分支、本地通过、TEST 验证和生产上线分别表述；未确认上线就直接说明，不能用本地或 TEST 结果替代生产结论。
- **默认排版**：聊天正文和保存的 Markdown 文件使用一级报告标题、二级小节标题和少量要点，便于看清核心结论、进展、验证及下一步。不叠加多层分类，不默认使用表格、代码块或内部文件链接。
- **明确要求微信格式时**：去掉 Markdown 标记，以普通文字小标题和自然分段保留同样的报告结构；直接交付可复制的正文，不附使用说明。项目或会话要求的称呼按原规则保留。
- **下一步短而明确**：结尾用一小段写最需要推进的动作，围绕已发现的问题安排计划，不堆任务清单。纯回顾没有要求计划时不硬加。

不要用“一段概述”替代完整报告，也不要为了模板条数拆分事项。结构帮助读者区分结果、依据和未完成项；每节写多长、写几条由实际材料决定。

精简时，例如“50 并发、250 次签发全部成功，登记齐全；100 并发、400 次签发缺少 33 条登记，150 并发、450 次签发缺少 120 条登记，等待后未补齐”这类数据应保留，因为它说明了问题发生的条件和程度。同时保留“未实际上传图片，不能代表完整上传流程或生产容量”等必要边界。此例仅说明取舍方式，数字不能迁入其他报告。

## 保持自然，不写成模板生成物

自然表达检查属于本 Skill 的交付质量，不转交给外部写作诊断流程。先检查事实是否说清，再处理下面这些高频问题：

- **结构过满**：标题、四级分类、连续编号同时出现，读者先看到模板，后看到工作。只保留帮助定位信息的层级。
- **句式匀速**：每句都写成“完成/新增 + 能力 + 降低风险或提升效率”。打破同构句式，让重要事项展开，普通事项短写。
- **抽象名词过多**：“核心链路改造、跨项目验证、完整闭环、能力建设”如果不能指向具体对象，就改成“哪条流程已经能怎么跑”。
- **价值收束过度**：不要在每条末尾追加“降低风险、提升效率、赋能业务”。只有材料能支持，且这项影响对读者重要时才写价值。
- **技术翻译过度**：业务读者不等于不能看技术。保留 `Java`、`Python`、`Flyway` 等能说明范围和可靠性的词，删掉不会影响判断的文件名、提交号和内部实现。
- **过度换词**：同一个对象用同一个准确名称即可，不为避免重复而轮换“链路、通路、闭环、流程”等近义词。
- **语气过度确定**：本地测试通过就写本地通过；尚未发布或真实环境未测，直接写出来，不用积极措辞盖住边界。

优先使用用户平时会说的话，例如“本周主要在推进……”“本地已经跑过……”“现在还差……”。自然不等于口语化或降低专业度，而是让句子保留真实重点、自然长短和必要的未完成状态。

## 统一报告规范示例：技术项目周报

这个案例展示统一报告规范如何应用于多仓库技术项目：先讲业务变化，再用技术事实说明结果与验证边界，最后写尚未完成的动作。日报也按这个顺序组织，只改变日期、材料范围和详略；保存到日记时继续保留结构。

### 编译判断

- **证据状态**：真实班级相关功能已在本地完成并验证；SQL 审核、代码归并和 TEST 真实账号验证尚未完成。
- **表达重点**：保留“核心结论”；先写老师、管理员、作品和报告发生的业务变化，再用系统范围、测试和 Flyway 证明技术可信度。
- **删减原则**：不展示提交清单、内部文件名和全部测试数字；不把每项都收束为“降低风险”或“提升效率”。
- **节奏处理**：不用九条完全同构的编号，保留少量分区；句子有长有短，直接使用“现在还差”“没有强行回填”等自然说法。

### 可直接发送的版本

```markdown
# 工作周报｜2026-08-10—2026-08-16

## 核心结论

本周把 CRM 真实班级这条线的主要功能做完，并在本地跑通；目前还差 SQL 审核、代码归并和 TEST 真实账号验证。

## 业务侧

- 企微老师登录后，系统可以按真实班级分页同步学生；上游接口有问题时，仍可以用 Excel 增量补录。
- 重复老师可以通过“认领”合并，不需要手工删数据，原来的老师信息和学生关系也会保留。
- 新发现的课期先进入待批准列表，管理员确认后，再等老师下次登录同步学生。
- 作品、学情报告和作品评价都补上了真实课期，后续查询和生成时不会把不同课期的数据混在一起。

## 技术侧

- 这次改动涉及主前端、Java、Python、CRM 前端和两套数据库，几端使用的真实学习作用域已经对齐。
- 本地跑过 MySQL、Redis、Celery 和前后端相关测试，Java、Python 回归以及 CRM 前端构建均通过。
- 数据库改动全部走 Flyway，旧班级、旧作品和旧报告没有强行回填或删除。

## 风险与下一步

- 先完成 SQL 审核和代码归并，再到 TEST 用真实账号跑一遍课期发现、管理员批准、学生同步以及作品和报告按课期生成。
```

复用这个案例时，使用统一结构和判断顺序：结论先行、业务变化在前、技术事实作证、未完成项直说。项目名、条数、数字、时间和技术栈必须来自本次材料，不能照抄案例。

## 首次使用与材料不足

这是一次完成型 Skill。材料足够时直接输出报告，不插入欢迎语、功能菜单或方法介绍。

完全没有可用事实时，用一个短段落说明：本 Skill 会基于证据整理“结果—价值—能力—计划”，不会替用户编数据；随后只索取最小输入：时间范围，以及工作材料或用户明确指定的可检查项目。用户已给出其中一项时只补另一项，不扫描碰巧打开的工作区。

## 交付前自检

输出前逐项检查并在内部修正：

1. 标题和时间范围是否明确，过去与未来有没有混淆；
2. 已完成、进行中、决定、发现和计划是否正确区分；
3. 每个核心价值判断是否有证据，预期收益是否仍写成预期；
4. 是否能看出用户的贡献和判断，而不是只有团队流水账；
5. 是否把能力写成行为证据，而非自我评价；
6. 下一阶段是否有优先级、原因和验收信号，而非事项堆积；
7. 是否保留了真实的不确定性、风险和需要支持；
8. 核心结论是否用自然语言说清主线、当前阶段和剩余事项，而不是抽象口号；
9. 如果分为业务侧和技术侧，两边是否各有职责，技术事实是否真正支撑业务判断；
10. 是否存在连续同构句、抽象名词堆叠、每条强行追加价值或层级过多；
11. 是否保留用户原话、准确技术词和自然长短，而不是为“流畅”抹平真实重点；
12. 读者能否在一分钟内找到结论、价值、风险和下一步；
13. 是否先按统一规范组织报告，再按保存或发送渠道排版；只有明确要求微信格式时才去掉 Markdown 标记，不能因此删掉报告结构。
14. 精简或换格式后，是否仍保留影响判断的数字、异常、验证边界和用户明确要求保留的内容。
15. 保存到日记是否仍然是一份日报或周报，而非随手记、保存流程说明或机器日志；同日追加是否只包含新内容。
