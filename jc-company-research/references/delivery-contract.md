# 交付契约

用途：规定产出什么文件、放哪里、命名怎么定、什么时候算完成。

## 两份产物

| 产物 | 给谁看 | 内容 | 语言风格 |
|---|---|---|---|
| 口播稿 | 当场的自己 | 一段能直接开口讲的话，按场合控制长度 | `jc-voice`，口语，第一/第二人称 |
| 调研底稿 | 被追问时的自己 | 来源、日期、三档证据、待确认清单 | 书面、结构化 |

**两份不要合并。** 口播稿里出现表格和来源链接就没法开口讲；底稿里出现口语话术就没法查证据。

## 落地位置

遵循当前项目自身的文档规则。在 JC 知识库中：

- 放入 `01-个人/简历/`（求职面试场景）或 `01-个人/职业事业/`（生意判断、日常调研场景）
- 命名：`YYYY-MM-DD-{公司名}调研-{场合}.md`
- 两份可以合成一个文件的两节，也可以拆成两个文件。**默认合成一个文件**：口播稿在前，底稿在后，中间用分隔线隔开。这样用户打开一个文件就能用。
- 不打标签（除项目标签外）

其他项目：优先遵守该项目 AGENTS.md 或 README 的文档规则；无规则时询问用户。

## 单个文件的推荐结构

```markdown
# {公司}调研｜{场合}

> 调研日期：{日期}
> 场合：{面试 / 见客户 / ...}
> 深度目标：{各维度 L 级别}

---

## 口播稿

### 主稿（{时长}）
{一段话}

### 追问备用
{面试官/对方可能追的几个问题的短答}

---

## 调研底稿

### 阶段判断
{一句话 + 依据}

### 六维
{按 research-protocol.md 的底稿结构}

### 来源清单
| # | 来源 | 链接 | 日期 |

### 待确认清单
- [ ] ...

### 本次未查的维度
{及原因}
```

## 完成标准

交付前逐条确认：

- [ ] 场合和输出已确认，不是默认假设的
- [ ] 阶段判断有依据，不是凭感觉贴的标签
- [ ] 只深挖了用得上的维度，其余标了 L 级别和未查原因
- [ ] 每条结论都有来源和日期
- [ ] 三档证据分开写了
- [ ] 拿不到的信息进了待确认清单，没有硬凑
- [ ] 口播稿读一遍能顺下来，时长对得上
- [ ] 口播稿里三档证据都用自然语言体现了
- [ ] 口播稿没有禁用词（箭头链、排比、伪标题、赋能类）
- [ ] 文件按项目规则命名和存放了

## 部分交付

用户只要一部分时，尊重范围，但要做两件事：

1. **说明放弃了什么**。只出口播稿时，告诉用户"底稿没做，被追问深层证据时你手上没有备份"。
2. **不留半成品**。只要底稿时不做口播；只要口播稿时，至少要口头确认用户知道哪些结论是推断。

## 重做与更新

同一家公司第二次调研时：

- 先找有没有上一次的底稿。
- 复用还能用的部分，只补变化的部分（现状、近期动作）。
- 特别在入职场景：把上次的推断逐条对照实际情况，标成成立/不成立/部分成立。

不要从零重写，也不要直接套用旧结论。
