# 规则怎么写：主张与证据 + 精确度与自由度

两个场景读这个文件：

- 判断"什么能写成规则、什么不能" → 看「主张与证据」
- 判断"一条规则该写多死" → 看「精确度与自由度」

---

## 主张与证据

### 主张分类

**A. 安全、权限和任务边界**

例如：未经授权不修改外部系统；不处理超出专业边界的高风险问题；安装用户 Skill 必须遵循单一来源规则。

这些可以写成低自由度强制规则，但仍要避免与更高优先级规则冲突。

**B. 有支持的稳定机制**

具备多个可靠来源、长期案例或清楚机制解释，且会改变判断。写法应包含：适用条件、支持证据、反例或边界、证据不足时的处理。不要因为有一篇来源就升级成普遍定律。

**C. 作者经验或产品假设**

来自 JC 实践、个人判断、局部样本或仍待验证的产品设计。可以用于生成候选假设、设计试验、提醒模型关注某个信号、建立暂定工作原则。必须标注状态和适用范围，不能写成不可谈判公理。

**D. 真实失败形成的 Gotcha**

来自可复现错误，例如：模型把 Description 写成功能介绍而不是触发条件；用户只要求审查，模型却直接安装；Skill 已触发但没有读取条件 Reference；新 Skill 抢走相邻领域请求。

Gotcha 必须绑定：原始失败、可观察错误、正确处理、对应 Eval。

**E. 品牌声音和个人偏好**

例如直接、短句、少套话、先给结论。可以约束表达，不得替代用户证据、事实来源、边界和对不确定性的说明。

**F. 模型已知常识**

模型在无 Skill 基线中已经稳定做到的，默认删除。"写得清楚""理解用户需求""提供专业建议"这类说明不值得占用上下文，除非历史失败证明它们在本任务中有特殊含义。

### 证据状态

| 状态 | 含义 | 可采取动作 |
|---|---|---|
| 已验证 | 有来源和真实任务反复支持 | 可进入稳定判断 |
| 有支持 | 有来源或案例，但边界未充分验证 | 写明条件，继续测试 |
| 待验证 | JC 假设、局部经验或新设计 | 进入试验，不写成事实 |
| 有冲突 | 来源或案例互相矛盾 | 保留分歧，说明选择依据 |
| 无依据 | 仅来自模型生成或作者确信 | 不进入领域规则 |

### 主张清单

创建或审查时可使用：

| 主张 | 类型 | 来源 | 适用条件 | 反例/边界 | 没有它会错什么 | 写入位置 | 状态 |
|---|---|---|---|---|---|---|---|

只有会改变模型行为的主张才进入 Skill，其余留在知识库或删除。

### 伪精确审查

重点寻找：

- 无来源百分比、统一投递次数、固定准备月数、精确人格适配分数；
- 把概率语言改写成确定结论；
- 把作者样本的比例推广到所有用户；
- 用评分表掩盖无法度量的问题。

数字可以保留的情况：明确制度和截止时间；可验证的数据统计；用户自己的预算和期限；被清楚标注的本轮试验规则；评测量表本身的操作性定义。

### 从失败形成 Gotcha

不要提前写大量免责声明。按下面流程积累：

```text
观察真实失败
→ 判断是否可复现
→ 定位失败层级
→ 写一条最小 Gotcha
→ 保存原始案例
→ 增加对应 Eval
→ 检查是否破坏相邻任务
```

一次偶发输出不好，先调整任务上下文或复测，不要立刻增加新的普遍规则。

## 精确度与自由度

### 四层自由度

**任务与边界：低自由度。** 明确：负责和不负责什么；何时停止；何时转交；哪些权限或安全要求不能违反；哪些输出属于任务失败。这些内容一旦错，任务方向会整体偏离。

**证据与判断：中低自由度。** 明确：证据优先级；会改变结论的分类；正面、失败和混淆信号；证据不足时怎样处理。不要把启发式规则写成无条件阈值，让模型结合情境解释，但不能忽略证据。

**工作过程：中自由度。** 提供默认顺序，同时允许：已有信息充分时跳过；新证据出现时回退；简单任务直接完成；高风险判断分步确认；选择更合适的工具或表达形式。过程用于保持方法，不用于证明已经工作。

**提问与表达：高自由度。** 通常不要写死：每轮必须问几个问题；先问哪一句；必须使用哪张表；必须引用哪个案例；固定开场、金句和结尾；每次都生成同样长度的报告。表达应服从用户信息量、风险、语言习惯和当前目标。

### 过度精确的信号

- 无论输入是否完整，都要求跑完同样步骤；
- 每个步骤都必须等待用户回复；
- 用固定比例或数字替代证据判断；
- 案例中的处理顺序被写成普遍流程；
- 同时规定问题、步骤、答案、语气和结尾；
- 输出是否填满表格比是否解决问题更重要；
- 模型无法根据简单任务缩短流程。

常见后果：流程过拟合、案例套用、伪精确、忽视当前用户证据、对边界情况缺少适应。

### 过度模糊的信号

- 只说"专业地帮助用户"；
- 没有中心任务和停止条件；
- 没有证据优先级、关键失败信号和交付契约；
- 同一个 Skill 可以解释成任何任务；
- 输出退回通用建议和正确废话。

### 改写示例

把固定流程：

> 无论任何情况都依次完成七步，每步询问用户。

改为：

> 通常按以下顺序处理。已有信息足够时直接使用；简单任务可以跳过不影响判断的步骤；高风险和不可逆选择需要分步确认。

把伪精确：

> 投递十次没有面试就必须换方向。

改为：

> 根据岗位样本、投递质量、回复类型、时间窗口和当前证据判断是否需要降仓；统一次数不能代替市场诊断。

把空泛要求：

> 根据用户情况做专业职业规划。

改为：

> 识别用户当前属于信息、决策、准备、执行还是求职反馈问题；结合截止时间、现金流、可达性和市场证据，交付与当前问题匹配的下一步。

### 审查问题

逐条检查：

1. 这条要求不写死会造成任务失败吗？
2. 它是边界、判断、默认流程还是表达？
3. 是否存在多条合理完成路径？
4. 用户已提供答案时，Skill 能否跳过追问？
5. 简单问题能否缩短，高风险问题能否加深？
6. 数字来自制度、数据、案例还是作者想象？
7. 案例是在解释方法，还是在替新用户下结论？
8. 删除固定格式后，交付质量是否真的下降？

最终目标：精确约束不该犯的错误，开放允许完成任务的路径。
