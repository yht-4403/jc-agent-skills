# 主张与证据

当需要从母文档、经验、案例或现有 Skill 中判断“什么能写成规则”时读取本文件。

## 目录

- 主张分类
- 证据状态
- 主张清单
- 伪精确审查
- 从失败形成 Gotcha

## 主张分类

### A. 安全、权限和任务边界

例如：

- 未经授权不修改外部系统；
- 不处理超出专业边界的高风险问题；
- 不把任意 Offer 当成职业规划成功；
- 安装用户 Skill 必须遵循单一来源规则。

这些可以写成低自由度强制规则，但仍要避免与更高优先级规则冲突。

### B. 有支持的稳定机制

具备多个可靠来源、长期案例或清楚机制解释，且会改变判断。

写法应包含：

- 适用条件；
- 支持证据；
- 反例或边界；
- 证据不足时的处理。

不要因为有一篇来源就升级成普遍定律。

### C. 作者经验或产品假设

来自 JC 实践、个人判断、局部样本或仍待验证的产品设计。

可以用于：

- 生成候选假设；
- 设计试验；
- 提醒模型关注某个信号；
- 建立暂定工作原则。

必须标注状态和适用范围，不能写成不可谈判公理。

### D. 真实失败形成的 Gotcha

来自可复现错误，例如：

- 模型把 Description 写成功能介绍而不是触发条件；
- 用户只要求审查，模型却直接安装；
- Skill 已触发，但没有读取条件 Reference；
- 一个新 Skill 抢走相邻领域请求。

Gotcha 必须绑定：

- 原始失败；
- 可观察错误；
- 正确处理；
- 对应 Eval。

### E. 品牌声音和个人偏好

例如直接、短句、少套话、先给结论。

可以约束表达，不得替代：

- 用户证据；
- 事实来源；
- 边界；
- 对不确定性的说明。

### F. 模型已知常识

如果模型在无 Skill 基线中已经稳定做到，默认删除。

“写得清楚”“理解用户需求”“提供专业建议”等说明通常不值得占用 Skill 上下文，除非历史失败证明它们在本任务中具有特殊含义。

## 证据状态

不要假装所有领域都能使用统一的证据等级。至少记录以下状态：

| 状态 | 含义 | 可采取动作 |
|---|---|---|
| 已验证 | 有来源和真实任务反复支持 | 可进入稳定判断 |
| 有支持 | 有来源或案例，但边界未充分验证 | 写明条件，继续测试 |
| 待验证 | JC 假设、局部经验或新设计 | 进入试验，不写成事实 |
| 有冲突 | 来源或案例互相矛盾 | 保留分歧，说明选择依据 |
| 无依据 | 仅来自模型生成或作者确信 | 不进入领域规则 |

## 主张清单

创建或审查时可使用：

| 主张 | 类型 | 来源 | 适用条件 | 反例/边界 | 没有它会错什么 | 写入位置 | 状态 |
|---|---|---|---|---|---|---|---|

只有会改变模型行为的主张才进入 Skill。其余内容留在知识库或删除。

## 伪精确审查

重点寻找：

- 无来源百分比；
- 统一投递次数；
- 固定准备月数；
- 精确人格适配分数；
- 把概率语言改写成确定结论；
- 把作者样本的比例推广到所有用户；
- 用评分表掩盖无法度量的问题。

数字可以保留的情况：

- 明确制度和截止时间；
- 可验证的数据统计；
- 用户自己的预算和期限；
- 被清楚标注的本轮试验规则；
- 评测量表本身的操作性定义。

## 从失败形成 Gotcha

不要提前写大量免责声明。按下面流程积累：

```text
观察真实失败
→ 判断是否可复现
→ 定位失败层级
→ 写一条最小 Gotcha
→ 保存原始案例
→ 增加对应 Eval
→ 检查是否破坏相邻任务
```

一次偶发输出不好，先调整任务上下文或复测；不要立刻增加新的普遍规则。
