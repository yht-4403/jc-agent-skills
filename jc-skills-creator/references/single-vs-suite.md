# 单 Skill、套件与其他形态

当需要判断单 Skill 还是套件、是否拆分，或设计路由入口时读取本文件。"要不要建 Skill"的准入判断见 `SKILL.md` 步骤 1，以那里为准。

## 目录

- 单 Skill 的信号
- 套件的信号
- 路由 Skill 的职责
- 生命周期与工具箱
- 套件成本

## 单 Skill 的信号

优先单 Skill，当以下大部分条件成立：

- 用户只有一个中心目标；
- 使用同一套主要判断逻辑；
- 必要输入高度重叠；
- 最终产物相近；
- 不同情况只是案例、行业词汇或表达差异；
- 一个入口可以通过内部模式保持清楚；
- Description 能准确覆盖而不泛化到整个领域。

内部可以有创建、审查、迭代等模式，但模式不等于必须拆成多个 Skills。

## 套件的信号

考虑拆分，当差异已经稳定体现在：

- 用户目标不同；
- 判断逻辑不同；
- 必要输入不同；
- 工具和资源不同；
- 交付产物不同；
- 权限或风险边界不同；
- Description 无法同时保持精确；
- 单个 Skill 经常加载大量无关内容。

不要因为章节多、作者概念多或想让目录对称而拆分。

## 路由 Skill 的职责

套件需要入口时，路由只负责：

- 识别用户当前目标和问题阶段；
- 选择最相关执行 Skill；
- 处理信息不足和相邻混淆；
- 根据执行结果推荐下一步；
- 尊重用户已明确指定的处理方式。

路由不要：

- 复制所有领域知识；
- 完成执行 Skill 的诊断；
- 强迫用户走固定课程；
- 用工程字段代替用户语言；
- 把每个问题都送入同一条长链。

## 生命周期与工具箱

领域可能有两种常见形状：

### 生命周期型

例如：

```text
认知 → 展示 → 接触 → 聊天 → 约会 → 关系
```

适合按阶段拆，但仍要允许回退和跨阶段诊断。

### 任务工具箱型

例如：

```text
概念拆解 / 内容诊断 / 决策 / 对标 / 行动设计
```

适合按中心任务和交付拆，不要求粒度完全一致。

职业规划等领域可能同时具有阶段和问题类型。先用单 Skill 内部模式验证，等真实案例证明差异稳定后再拆。

## 套件成本

每增加一个 Skill 都会增加：

- Description 常驻成本；
- 相邻路由冲突；
- 重复共享规则；
- 维护和回归范围；
- 版本不一致风险。

拆分带来的上下文收益必须大于这些成本。

## 决策输出

给出：

1. 推荐形态；
2. 中心任务；
3. 拆分或不拆分的证据；
4. 每个 Skill 的正向和负向边界；
5. 共享知识放置位置；
6. 路由是否需要；
7. 下一批验证案例。
