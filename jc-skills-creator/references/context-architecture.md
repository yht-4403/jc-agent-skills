# 上下文与文件架构

当需要决定内容进入 Description、`SKILL.md`、References、Scripts、Assets 或配置时读取本文件。

## 目录

- 三层上下文成本
- Description
- SKILL.md
- References
- Scripts
- Assets
- Onboarding 文案
- 配置与记忆
- 去重规则
- 架构输出

## 三层上下文成本

### 索引层

包括 Skill 名称和 Description，通常在会话开始时常驻。

要求：

- 短而密；
- 描述何时加载；
- 使用真实用户意图；
- 包含关键相邻边界；
- 不总结完整工作流；
- 不堆品牌口号。

### 加载层

即 `SKILL.md` 正文，触发后进入上下文。

只放：

- 中心任务；
- 模式与边界；
- 稳定判断；
- 默认流程；
- 资源导航；
- 交付契约；
- 最高价值 Gotchas。

接近平台建议上限时主动拆分。行数不是质量指标，删除无效句子优先于机械分文件。

### 运行时层

包括 References、Scripts、Assets、配置和持久记录。

只在条件满足时读取或执行。容量更大不代表可以无结构堆放。

## Description

检查：

1. 删除 Skill 正文后，只看 Description 能否判断何时加载；
2. 是否覆盖用户真实说法，而不是作者的内部术语；
3. 是否包含不应加载的关键边界；
4. 是否与相邻 Skills 使用同一组模糊词；
5. 是否把流程和价值宣传塞进路由；
6. 一个小词变化是否可能扩大误触发。

Description 改动必须有正负 Eval 支持。

## SKILL.md

把它当成控制面和导航页。

推荐内容：

```text
中心任务
工作模式
边界与转交
稳定工作流程
条件资源导航
交付契约
核心 Gotchas
停止条件
```

不要放：

- 母文档全文；
- 大量背景历史；
- 完整案例库；
- 所有变体；
- 模型已经知道的教程；
- 安装说明、README、更新日志；
- 仅为解释作者思考过程的内容。

## References

适合：

- 详细领域方法；
- 条件化标准；
- API 或数据结构；
- 完整案例、反例和边界；
- 某种模式才需要的流程；
- 质量门和评测规范。

每个 Reference 在 `SKILL.md` 中必须有直接链接和读取条件。

Reference 应回答：

1. 什么时候读；
2. 读后改变什么；
3. 不读会产生什么可观察错误。

避免深层引用。较长文件在顶部提供目录。

## Scripts

适合：

- 每次都会重新写的代码；
- 需要确定性和一致性的计算；
- 容易遗漏边界条件的机械处理；
- 已反复验证的检查和转换；
- 可以通过参数组合的稳定能力。

不适合：

- 高度依赖情境的领域判断；
- 多条路径都合理的开放决策；
- 尚未稳定的方法假设；
- 只是为了显得工程化的薄脚本。

新增脚本必须实际运行测试。

## Assets

适合最终产物需要复制或修改的：

- 模板；
- 图标、字体和品牌素材；
- 项目脚手架；
- 固定示例文件；
- 输出骨架。

Assets 不应被当作默认上下文阅读。

## Onboarding 文案

直接面向终端用户的 Skill 需要首次使用价值说明。文案较长、需要跨模型稳定、需要版本管理或由产品 Runtime 复用时，使用：

```text
onboarding/core-introduction.md
```

`SKILL.md` 只保留：

- 何时读取；
- 首次回复必须完成什么；
- 材料齐全和缺失时分别怎样继续；
- 何时不再重复；
- Runtime 状态由谁维护。

不要把完整公共文案同时复制进 `SKILL.md`。简单单轮 Skill 的介绍只有一两句话时，可以直接内联，不为目录对称拆文件。

## 配置与记忆

只有出现以下需要时增加：

- 首次使用必须保存用户设置；
- 跨任务比较历史结果；
- 记录每次运行状态；
- 需要持久化而非依赖对话上下文。

明确数据位置、更新方式、隐私和失效条件。不要把用户隐私数据随意写进 Skill 源目录。

## 依赖闭包与零配置启动

发布前把 Skill 放到一台“只有宿主 Agent、没有作者个人环境”的新机器上思考：

- 跨 Skill 引用是否只指向明确随套件分发的成员；
- 外部 CLI、系统应用、Python/Node 包是否能够检测版本和可用性；
- 安装来源是否是官方或明确受信来源，安装前是否取得用户同意；
- 浏览器登录、扫码、OAuth 或权限开通是否把链接和下一步交给用户；
- 用户完成授权后，Agent 是否负责继续验证和执行，而不是让小白自己排命令；
- 工具不可用或用户不愿安装时，是否仍有诚实、可完成的降级交付。

通用方法不要通过引用作者本机的另一个 Skill 复用。提取当前任务真正需要的最小规则放进 Reference；确定性能力放进 Script；只有同一套件明确声明并共同分发的成员可以互相路由。

## 产品包与开发包

Skill 目录中的文件会随 Skill 一起分发，但不一定都会进入模型上下文。是否保留，取决于运行时是否会用到：

- **产品包保留**：`SKILL.md`、按需 References、执行 Scripts、产物 Assets、必要 Schema 与用户可见 onboarding。
- **开发仓库保留**：Evals、基准结果、回归记录、发布门清单、设计推演和维护说明；除非运行时确实需要读取，否则不要塞进产品 Skill。
- **直接编译进规则**：少量高价值 Gotcha 和质量红线应写进 `SKILL.md` 或对应 Reference，因为它们能稳定不同模型的行为，不应仅留在测试文档。

“用户不直接阅读”不是删除文件的理由；“运行时不读取、不执行、不复制到产物”才是移出产品包的主要依据。

## 去重规则

- 同一知识只保存在一个权威位置；
- 共享规则不要在路由和每个执行 Skill 中重复；
- `SKILL.md` 只做摘要和导航，不复制 Reference；
- 首次介绍的完整公共文案只保存在 onboarding 文件或 `SKILL.md` 其中一处；
- 通用平台规则由通用创建器管理；
- 用户 Skill 的存储和激活由安装器管理；
- 领域大资料管线由领域工厂管理。

## 架构输出

给出一张最小文件树，并为每个文件写一句：

```text
负责什么
何时加载
为什么不能放在别处
```

没有明确用途的目录不要创建。
