# Evals：测试怎么设计 + 本 Skill 的测试案例

创建、修改 Description、增加 Gotcha、拆分 Skill 或验证真实失败时读这个文件。

- 前半部分：怎么设计测试（通用方法）
- 后半部分：本 Skill 自己的测试案例（可直接用于前向测试）

---

## 一、Eval 设计方法

### Eval-first

在写 Skill 正文前，先准备能够暴露差异的请求。来源优先级：

1. 真实用户请求；
2. 已知失败；
3. 相邻 Skill 混淆；
4. 边界和反例；
5. 人工构造的补充案例。

先记录无 Skill 基线。没有基线，就无法知道 Skill 是否真的改善结果。

### 测试层级

**1. 准入测试**

比较：无 Skill / 一句临时提示 / 加载完整 Skill。如果一句提示已经稳定解决，不要用更重的 Skill。

**2. 触发测试**

至少覆盖：应触发；不应触发；与相邻 Skill 表达高度相似；用户没有说内部 Skill 名称；用户明确调用；用户只要求普通领域任务。记录欠触发、误触发和抢路由。

**3. 渐进加载测试**

检查：Skill 触发后是否读取了正确 Reference；不满足条件时是否避免读取；读取后是否实际改变判断或产物；是否漏读关键模板、标准或边界；是否无条件加载全部资源。

**4. 首次体验测试**

对直接面向终端用户的 Skill，至少测试：

- 材料齐全：首次回复说明定位、适用人群、处理方式和用户收获，并在同一回复开始任务；
- 材料缺失：首次回复完成价值说明后，只索取最小必需输入；
- 价值差异：用户能从首次回复理解它相对普通做法多解决了什么；没有真实差异时不强行制造对立；
- 机制到收益：至少一个关键机制被翻译为用户可感知的体验或结果，而不是只列功能；
- 方法披露幅度：适度说明证据依据、判断顺序、核验方式或反馈闭环，使专业性可见；不倾倒状态字段、文件结构、工具轨迹或完整流程；
- 具体交付：至少出现一个可检查的判断、文档、改写稿、证据、方案、任务或下一步；
- 参与风险：缺材料、答不上来或中途结束的处理符合真实能力，不虚构保存、恢复或效果保证；
- 后续一轮：不重复介绍；
- 用户已经说过目标或偏好：介绍和起始动作正确复用，不重新盘问；
- 用户说"直接开始"：不展示菜单或等待确认；
- 多入口顾问型 Skill：用户能从问题地图认出自己，地图不是内部功能清单，也没有被写成必须全部完成的固定流程；
- 推荐顺序：默认路径和改变顺序的条件清楚，用户仍可选择其他入口；
- 锁定公共文案：首次逐字输出、后续不重复，动态材料判断和个性化第一步没有被错误锁进正文；
- Markdown 结构：有序列表、子级缩进、空行和分隔线在目标客户端能形成正确层级；
- 去 AI 味：没有连续同构句、抽象名词堆叠、过度对偶或内部术语，专业细节仍足以建立可信度；
- 人工确认文案：用户提供逐句标注或明确要求直接沿用时，保留原意、口语和自然长短，只对事实错误、不可验证承诺、平台硬限制或安全边界做最小调整。

只检查信息、价值与动作契约，不把某一版固定文案当成唯一正确输出，也不把篇幅、术语密度、宣传感或继续使用率当作替代指标。

如果产品明确采用人工确认的锁定公共文案，Eval 可以检查逐字一致性；这只验证产品一致性，不代表该文案本身已经证明更有效。文案质量仍需用真实用户反馈和端到端任务表现判断。

**5. 端到端任务测试**

使用明确 Rubric 判断：是否解决用户目标；是否使用用户证据；是否遵守边界；是否交付正确形态；是否减少已知错误；是否产生新的副作用。不要只比较语气和篇幅。

对会调用外部工具、账号或套件成员的 Skill，再增加零配置测试：

- 新机器没有作者本机的其他 Skill、CLI 和第三方运行包；
- 用户不知道安装、配置、OAuth、二维码和权限术语；
- Agent 能检测缺口，说明可信来源，并在安装前取得同意；
- 必须由用户完成的授权会把原始链接、二维码和返回口说清；
- 用户完成后由 Agent 继续验证，不把命令排障甩回用户；
- 用户拒绝安装或宿主不能执行时，仍有范围诚实的降级交付。

产品包测试与开发仓库测试分开：确认运行时不会读取的 Evals、基准结果和发布记录没有随单个 Skill 分发，同时确认移出后关键 Gotcha 仍已编译进运行规则。

**6. Skill 库回归**

新增或修改 Skill 后，重跑：相邻 Skills 的正向请求；当前 Skill 的负向请求；共享触发词请求；旧版本曾经通过的英雄案例；系统或项目规则容易产生竞争的请求。

### 测试记录

每条至少记录：

```text

失败层级

```

可以先用 Markdown。案例增加、需要批量运行时再转 JSONL 或脚本。

### 前向测试

保持验证完整性：

- 使用新上下文或独立 Agent；
- 像真实用户一样提出任务；
- 传原始材料，不传预期答案和诊断；
- 不告诉测试者怀疑的 Bug；
- 清理可能泄漏答案的旧产物；
- 查看实际输出、工具轨迹和文件；
- 复杂或可能影响真实系统的测试先取得授权。

如果只有看到预期答案才成功，Skill 或测试设计仍不可信。

### 失败定位

| 层级 | 问题 |
|---|---|
| 准入 | 根本不该建，或应是全局规则、Script、Reference |
| 触发 | Description 欠触发或误触发 |
| 模式路由 | 创建、审查、迭代或执行分错 |
| 资源读取 | 没读、错读或过度读取 |
| 首次体验 | 用户不知道 Skill 价值、介绍缺项、重复介绍或介绍阻断任务 |
| 领域判断 | 规则、证据或边界错误 |
| 执行 | 工具、脚本或步骤错误 |
| 交付 | 产物形态、清晰度或完成度错误 |
| 回归 | 当前改动破坏相邻任务 |

先修改最靠近根因的一层，不要用更长输出掩盖前面错误。

### 失败 → 修改位置

| 失败表现 | 首选修改 |
|---|---|
| 该触发时没触发 | Description、正向 Eval |
| 不该触发却触发 | Description、负向 Eval |
| 模式选择错误 | 模式边界、路由 |
| 没读正确 Reference | 加载条件、渐进读取 Eval |
| 领域结论错误 | 主张、证据、领域 Reference |
| 每次重复实现且不一致 | Script |
| 判断正确但产物散乱 | 交付契约、Asset |
| 同品牌 Skill 在 UI 中中英混排或品牌拼写不一致 | `agents/openai.yaml`、界面命名约定、UI 元数据 Eval |
| 首次调用后用户仍不知道能得到什么 | 首次使用价值说明、首轮 Eval |
| 首次介绍信息齐全但缺少继续使用的明确理由 | 最小价值契约、首轮 Eval |
| 首次介绍缺少可信方法或披露过深 | 可信机制、方法披露幅度 Eval |
| 介绍阻断了已有材料的实际任务 | 首次回复动作、onboarding 契约 |
| 用户已确认的文案被统一改写成 AI 产品说明书 | 用户原话优先规则、场景式产品说明文风、文案回归 Eval |
| 作者观点被公理化 | 主张等级、证据标注 |
| 单个新案例失败 | 先复现，不立即加规则 |
| 修改后相邻 Skill 变差 | 收窄 Description、合并或重新拆分 |

完成一次修改后，记录：

```text
失败证据
根因层级
最小修改
新增 Eval
回归范围
验证结果
仍未解决
```

### 回归与跨模型

Description、系统规则和模型版本变化都可能改变路由。当 Skill 进入稳定使用或公开发布后：

- 固定一组英雄案例；
- 保留历史失败；
- 对不同模型分别跑触发和端到端测试；
- 记录差异，不假设 Claude、GPT 或其他模型行为一致；
- 新模型上线时优先复查路由、资源读取和强制流程。

V1 可以先完成单模型前向测试，但必须把跨模型标记为未验证，不能声称普遍稳定。

## 二、本 Skill 的测试案例

测试时只把"用户表达"和必要原始材料交给独立 Agent，不要暴露预期结果。

### 正向触发

| ID | 用户表达 | 预期模式 | 必须关注 |
|---|---|---|---|
| P01 | 把这套职业规划母文档做成一个 Skill，但先判断哪些该写进去。 | 创建 | 准入、规则筛选、上下文 |
| P02 | 我有销售、谈判和客户开发三套方法，应该做一个 Skill 还是套件？ | 创建 | 单 Skill/套件 |
| P03 | 帮我审查这个 Skill 是不是写得太死，为什么每次都问十几个问题？ | 审查 | 自由度、具体证据 |
| P04 | 这是一次失败对话，它该触发却没触发，帮我迭代。 | 迭代 | 触发、正向 Eval |
| P05 | 给这个 Skill 设计正向、负向和相邻混淆 Evals。 | 创建或审查 | Eval-first |
| P06 | 这套方法有很多个人观点，帮我区分哪些能写成规则。 | 创建或审查 | 主张与证据 |
| P07 | DBS 和 TDS 哪些结构能复用到我的新 Skill，哪些会过拟合？ | 审查 | 结构与世界观风险 |
| P08 | 这个 Skill 第一次调用时要先让用户知道适合谁、怎么用、能得到什么，再直接开始。 | 创建或迭代 | 首次使用价值说明、首轮 Eval |
| P09 | 新建一个"橙子职业规划" Skill，放进现有 ChengziCV 产品列表；中文只作为右侧备注。 | 创建或迭代 | `name` 用 kebab-case；`display_name` 为 `ChengziCV` 开头的英文产品名；`short_description` 为中文备注；检查相邻 Skill 一致性 |
| P10 | 这个顾问 Skill 第一次只问我上传材料，我不知道它有什么用。请把历史对话里的真实卡点整理成固定开场，但不要照抄职业规划的九类问题。 | 迭代 | 卡点地图、锁定正文与动态跟进分层、Markdown 层级、去 AI 味、首次体验回归 |
| P11 | 这个 Skill 在我电脑上能用，但新用户没装飞书 CLI，也没有旁边那几个辅助 Skill。帮我改成零配置也能走完，并清理发布包。 | 迭代 | 依赖闭包、可信安装与授权、无工具回退、产品包与开发包分离 |
| P12 | 这是我逐句标注的 ChengziCV 功能说明，直接用我的话，适当微调即可，别改成 AI 产品说明书。 | 迭代 | 读取首次使用文案 Reference；保留用户原话和自然长短；只收口"最高回复率、保证进面、隐藏想法"等不可验证表达；检查场景、材料、AI 动作和结果是否清楚 |

### 端到端英雄案例

**H01：从成熟母文档创建**

输入：一份有方法论、案例和作者观点的母文档；三条真实用户请求；两条相邻任务；明确要求创建但尚未指定单 Skill 或套件。

通过条件：先判断 Skill 是否应存在；区分稳定机制、假设、Gotchas 和语气；给出正负触发语料；设计最小上下文结构；面向终端用户时设计首次价值说明，材料齐全后不等待确认；不复制整篇母文档；在写文件前建立 Eval。

**H02：审查长 Skill**

输入：一个 400 行以上、包含固定轮次、比例、公理和大量案例的 Skill；没有真实失败记录。

通过条件：区分静态风险和已验证问题；引用具体原文；不因长度本身判死刑；给出最小修改方向；不擅自改文件。

**H03：根据失败迭代**

输入：原始请求；实际加载 Skills；错误输出；当前 Skill；一个不能被破坏的相邻请求。

通过条件：定位失败层级；优先修改最靠近根因的位置；增加对应 Eval；检查相邻回归；不用全面重写代替诊断。

**H04：从作者机器迁移到零配置用户**

输入：一个会调用外部 CLI、OAuth 和本机辅助 Skill 的产品 Skill；一个包含 Evals、发布记录和运行时 Reference 的混合目录；要求小白在新机器完成完整流程。

通过条件：列出套件内部、外部工具和作者本机隐式依赖；套件外的方法引用被内聚为最小规则或 Script；外部工具具有检测、官方来源、安装同意、授权链接/二维码、状态验证和回退；不承诺绕过用户授权，也不静默安装软件；Evals、基准和发布记录移到开发仓库，高价值 Gotcha 留在运行规则；在没有第三方运行包的环境中执行确定性脚本回归。
