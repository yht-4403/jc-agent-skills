# 质量门与维护定位

发布前、审查现有 Skill，或根据失败决定修改位置时读取本文件。

## 目录

- 准入门
- 任务与边界门
- 触发门
- 主张与证据门
- 自由度门
- 上下文门
- 首次体验门
- Eval 门
- 生命周期门
- 硬失败
- 失败到修改位置

## 准入门

- 是否有无 Skill 基线或已知失败？
- 一句话提示是否已经足够？
- 是否重复系统、项目或模型常识？
- 是否应该是 Script、Reference 或全局规则？
- 知识是否稳定且可维护？
- 新 Skill 是否会增加明显路由冲突？

未通过时停止创建。

## 任务与边界门

- 是否只有一个清楚中心任务？
- 非目标和停止条件是否明确？
- 是否尊重只读审查与修改请求的授权差异？
- 是否知道何时转交领域工厂、通用创建器和安装器？
- 是否把普通领域任务误路由为 Skill 创建？

## 触发门

- Description 是否说明何时加载？
- 是否使用真实用户表达？
- 是否包含关键相邻边界？
- 是否避免总结完整工作流？
- 是否有正向、负向和混淆 Evals？
- 修改 Description 后是否运行回归？

## 主张与证据门

- 每条强规则是否有类型和来源？
- 是否把作者确信写成事实？
- 是否存在伪精确比例和阈值？
- 是否说明适用条件、反例和证据不足？
- 是否删除模型已知常识？
- Gotchas 是否来自真实、可复现失败？

## 自由度门

- 边界是否足够严格？
- 判断是否依赖证据而不是固定答案？
- 流程是否允许跳过、回退和缩短？
- 表达是否保留适应空间？
- 是否存在固定轮次、固定问题数和万能表格？
- 案例是否控制了新情境结论？

## 上下文门

- `SKILL.md` 是否是控制面，而不是母文档副本？
- 每个 Reference 是否有直接链接和加载条件？
- 是否存在跨文件重复？
- 确定性执行是否优先用 Script？
- 是否只创建实际需要的目录？
- 是否避免深层引用？
- `agents/openai.yaml` 是否与 Skill 一致？
- JC 自有品牌 Skill 的 `display_name` 是否为与相邻产品一致的英文产品名，`short_description` 是否承担中文备注？
- 是否避免把本地命名约定强加给第三方上游 Skill？
- 是否只依赖同包成员，或已经把外部方法内聚为当前 Skill 的最小规则？
- 是否扫描外部 CLI、Python/Node 包、绝对路径、私有配置和凭据假设？
- 零安装用户是否能得到检测、可信安装、明确授权、验证和降级路径？
- 产品包是否移除了运行时不会读取的 Evals、基准记录和发布文档，同时保留会改变行为的高价值规则？

## 首次体验门

对直接面向终端用户的 Skill 检查：

- 首次回复是否讲清定位、适用人群、处理方式、用户收获和开始方式？
- 是否建立了真实的价值差异，或在不适合比较时直接讲清核心问题？
- 关键机制是否被翻译成用户收益，而不只是功能或内部流程？
- 是否适度展示了能证明专业性的证据依据、判断顺序、核验方式或反馈闭环？
- 方法论细节是否保持克制，没有展开为状态机、文件结构、工具轨迹或完整工作流？
- 是否承诺了至少一个具体、可检查的交付物，而不只有“帮助、提升、优化”？
- 是否诚实说明了影响参与的回退或边界，降低继续投入材料和时间的不确定性？
- 是否复用用户已经提供的目标、材料与偏好？
- 材料齐全时是否介绍完立即工作，而不是等待确认？
- 缺少材料时是否只索取最小必需输入？
- 是否避免展示内部 Skill、路由表、文件结构或冗长功能菜单？
- 后续回复是否避免重复介绍？
- 需要稳定公共文案时是否使用单一权威 onboarding 文件？
- 有 Runtime 时，介绍版本和已读状态是否明确由平台维护？
- 多入口任务是否提供了用户可识别的卡点地图，而不是内部模块菜单？
- 问题地图是否来自真实用户表达，分类数量和领域方法是否有依据，没有机械复制其他 Skill？
- 是否说明默认路径与改变顺序的条件，同时避免把地图写成必须全部完成的流程？
- 锁定文案和动态跟进是否分层：固定品牌与价值，自适应材料判断和第一步？
- 面向 C 端小白的说明是否从用户场景出发，并尽量说清材料、AI 动作和可拿到的结果，而不是只翻译内部能力？
- 用户已经逐句标注或确认文案时，是否保留了原话和自然节奏，只对事实、不可验证承诺、平台限制或安全边界做必要微调？
- 是否把“最高回复率、保证进面、隐藏想法”等不可验证表达收口为目标、可能性或基于对话证据的考察意图？
- 有序列表、子级缩进、空行和分隔线是否在目标客户端正确渲染？
- 是否完成去 AI 味审查，保留用户语言、具体例子和自然节奏？

内部 worker、底层工具或由宿主完整介绍的 Skill 可以不适用，但必须有可解释的省略理由。

## Eval 门

- 是否有无 Skill 基线？
- 是否同时有正向、负向和相邻混淆？
- 是否测试渐进读取？
- 是否有端到端 Rubric？
- 用户交互型 Skill 是否覆盖材料齐全、材料缺失和后续不重复的首次体验？
- 是否保留历史失败？
- 是否运行相邻 Skill 回归？
- 前向测试是否没有泄漏预期答案？
- 未做跨模型测试时是否明确标注？

## 生命周期门

- 真实文件是否位于单一来源仓库？
- 运行时是否只使用预期链接？DeepSeek Harness 是否只在 `~/.dsh/skills` 看到指向单一来源的符号链接，而没有第二份实体或 `~/.agents/skills` 副本？
- 是否检查同名冲突和本地修改？
- 是否运行结构校验和安装审计？
- 是否避免修改系统 Skills 和无关用户文件？
- 是否如实报告创建、激活和验证状态？

## 硬失败

出现任一项即不能声称完成：

- 没有准入判断就直接生成；
- 没有证据却创造领域公理；
- 只有正向案例；
- 直接面向终端用户的 JC Skill 没有首次使用价值说明，也没有明确、合理的省略依据；
- 首次介绍只有功能、流程和输入要求，没有真实价值差异、具体交付或参与边界；
- 首次介绍把方法论完全隐藏为抽象承诺，或反向倾倒内部实现导致首屏失焦；
- 面对多种入口卡点时，只罗列功能或要求用户自己选择模式，没有降低选择难度；
- 把另一个 Skill 的卡点数量、分类方法或推荐顺序机械复制为当前领域标准；
- 锁定公共文案包含会随用户材料变化的虚假确认，或 Markdown 层级在实际渲染中失效；
- Description 改动没有路由 Eval；
- 把母文档全文放入 `SKILL.md`；
- 把真实用户 Skill 直接放入运行时目录；
- 未经授权修改、安装或发布；
- 依赖作者本机的外部 Skill 或隐藏工具，导致新机器无法完成主流程；
- 需要安装软件或账号授权，却没有检测、同意、链接/二维码交付和失败回退；
- 只通过格式校验就声称有效；
- 新 Skill 破坏相邻任务但没有处理；
- 测试者看到了预期答案或诊断。

## 失败到修改位置

| 失败表现 | 首选修改 |
|---|---|
| 该触发时没触发 | Description、正向 Eval |
| 不该触发却触发 | Description、负向 Eval |
| 模式选择错误 | 模式边界、路由 |
| 没读正确 Reference | 加载条件、渐进读取 Eval |
| 领域结论错误 | 主张、证据、领域 Reference |
| 每次重复实现且不一致 | Script |
| 判断正确但产物散乱 | 交付契约、Asset |
| 同品牌 Skill 在 UI 中中英混排或品牌拼写不一致 | `agents/openai.yaml`、界面命名约定、UI 元数据 Eval |
| 首次调用后用户仍不知道能得到什么 | 首次使用价值说明、首轮 Eval |
| 首次介绍信息齐全但缺少继续使用的明确理由 | 最小价值契约、首轮 Eval |
| 首次介绍缺少可信方法或披露过深 | 可信机制、方法披露幅度 Eval |
| 介绍阻断了已有材料的实际任务 | 首次回复动作、onboarding 契约 |
| 用户已确认的文案被统一改写成 AI 产品说明书 | 用户原话优先规则、场景式产品说明文风、文案回归 Eval |
| 作者观点被公理化 | 主张等级、证据标注 |
| 单个新案例失败 | 先复现，不立即加规则 |
| 修改后相邻 Skill 变差 | 收窄 Description、合并或重新拆分 |

完成一次修改后，记录：

```text
失败证据
根因层级
最小修改
新增 Eval
回归范围
验证结果
仍未解决
```
