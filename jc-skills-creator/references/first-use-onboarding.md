# 首次使用价值说明

当创建或审查直接面向终端用户的 Skill，尤其是多轮交互、训练、诊断、顾问或产品化 Skill 时读取本文件。

## 目标

首次回复先降低用户的理解成本，让用户立即知道：

1. 这是什么，核心解决什么问题；
2. 适合谁、适合什么场景，必要时说明不适合什么；
3. 用户需要提供什么，哪些材料是可选的；
4. 系统会怎样处理，并适度展示最能证明专业性的关键方法论；
5. 用户最终能获得什么可感知结果；
6. 现在怎样开始，以及过程中有哪些重要预期或边界。

固定的是信息契约，不是措辞模板。根据领域、用户已有材料和当前任务自由组织长度、语气、标题与顺序。

首次回复同时是一份“最小价值契约”。它不靠宣传语承诺效果，而要让用户在继续投入材料、时间或注意力前看清：

- 这个 Skill 相比普通做法多解决了哪一层问题；
- 哪些处理机制会直接改变用户体验，以及为什么有用；
- 本轮结束时能带走哪些具体、可检查的产物或判断；
- 材料不全、答不上来或中途停止时，已经投入的内容会怎样被诚实处理；
- 下一步是否会立刻产生进展。

可以用下面的关系检查价值感，但不要把它原样输出给用户：

```text
继续使用的明确理由
= 问题与普通做法的差异
+ 可信且与用户有关的处理方式
+ 可想象、可检查的交付
+ 可承受的参与成本
+ 立即发生的下一步
```

这是产品设计要求，不是已经证明能够提高留存率的因果结论。没有行为数据时，不要声称某种介绍必然提高继续使用率。

## 最小价值契约

根据任务复杂度选择最短的完整表达，不要求每项各占一段：

1. **价值差异**：优先用用户熟悉的普通做法作参照，指出本 Skill 进一步解决的问题。差异不存在或会显得牵强时，直接陈述核心问题，不制造对立。
2. **适用判断**：让用户快速知道是否适合当前场景；容易误用时说明不覆盖什么。
3. **可信机制**：只选 1—3 个真正改变结果或体验的方法论细节，例如证据依据、判断顺序、核验方式或反馈闭环，并把它们翻译成用户收益。可以适度暴露内部方法来建立专业度，但不要展开状态机字段、路由名、文件结构、工具轨迹或完整工作流。
4. **可感知交付**：使用判断、文档、改写稿、证据、方案、任务或下一步等具体名词，让用户能想象并检查本轮产物。不要只写“帮助、提升、优化”。
5. **低风险参与**：只说明真实存在且影响参与方式的回退，例如允许缺省、跳过、中止、阶段性交付或证据不足时降级；不要虚构保存、恢复或兜底能力。
6. **无缝启动**：材料齐全时介绍后立即开始；材料不足时只索取最小必需输入；不增加确认页。

机制必须落到收益。例如，“动态生成下一问”只是功能；“你的回答会决定下一问，没说清楚的地方会继续核验”才说明体验；如果再说明“这样能区分表达流畅与证据可信”，用户价值才完整。

方法论细节的披露以“能否增加可信度”为边界：如果一个细节能解释结果为何更可靠，可以保留；如果只证明系统复杂、需要额外解释或不能改变用户预期，就删除。首次介绍不必穷举全部机制，也不要为了显得专业堆叠术语。

## 卡点地图式公共介绍

当用户会带着多种相似但处理方式不同的入口问题进入 Skill 时，首次介绍优先使用“卡点地图”，不要只做功能介绍。它的作用不是展示系统有多少模块，而是让用户快速认出自己、降低选择难度，并理解为什么下一步会这样安排。

一份成熟的卡点地图式公共介绍通常按以下逻辑组织：

1. **品牌与职责**：第一句说清产品身份或品牌名；紧接着说明主要处理什么，容易混淆时补一句不处理什么。
2. **用户熟悉的困境**：用真实用户会说的话描述普通做法为什么仍然卡住，不先讲理论。
3. **一个核心分辨方法**：只引入当前领域最有解释力的一组区分，例如“该补信息还是该拿反馈”“缺表达还是缺证据”。说明区分之后用户能少走什么弯路。
4. **问题地图**：用有序列表列出几种高频卡点。每项包括用户能认出的现象、当前处理方向和一句具体例子，不使用内部节点名。
5. **推荐路径与例外**：说明通常从哪里开始，以及有期限、已有材料或目标明确时为什么改变顺序。地图不是一套必须全部完成的流程。
6. **可信方法与具体交付**：披露 1—3 个会改变结果的方法，并列出本轮可检查的产物。
7. **低阻力入口**：让用户回复数字、一个选项、一份现有材料或一个核心事实即可开始；材料齐全时直接进入实际工作。

可以把这条用户路径作为设计草图，但不要原样输出：

```text
认出自己的卡点 → 理解推荐顺序 → 相信处理方法 → 看见具体交付 → 只做一个低成本动作
```

不是每个 Skill 都需要九项地图，也不是每个领域都适合“调查 / 执行”或 `Question / Problem`。只在入口确实存在多个可辨认状态时使用地图；分类数量由真实问题决定。领域方法必须从该 Skill 的任务和失败证据中提炼，不能从成功案例机械移植。

### 从真实对话提炼文案

优先使用以下材料，而不是凭空写品牌宣传页：

1. 收集用户原话、历史失败输出、常见误解和用户反复修改的句子；
2. 标出用户为什么没有继续、为什么不知道怎么选、为什么不相信结果；
3. 合并同类卡点，保留用户能立即识别的表述；
4. 找出一个足以解释处理顺序的领域方法，不堆多套理论；
5. 为每个抽象判断补一个现实例子或可观察信号；
6. 写清默认路径、改变顺序的条件、产物和首次动作；
7. 最后单独做一次去 AI 味与 Markdown 层级审查。

真实迭代中已经证明有用的判断是：用户通常不是因为“不知道功能”而停住，而是没有认出自己的问题、看不出下一步的依据，或无法想象会拿到什么。这里的“证明”只指具体案例中的产品设计证据，不外推为普遍留存规律。

### JC 小白友好的场景式产品说明文风

面向 C 端小白写 README、首次介绍、功能列表和中文界面备注时，默认使用“像一个懂业务的朋友带着用户做事”的语气：口语化、场景化、结果导向，但不油腻，也不夸大效果。可将它称为“朋友式陪跑文风”。内部技术文档、正式制度、法律文本、第三方品牌文案和明确要求专业书面语的场景不自动套用。

优先按下面的关系组织内容，但不要把它写成五段固定模板：

```text
用户什么时候会用
→ 需要交什么材料或做什么
→ AI 具体会怎样帮他
→ 最后能拿到什么
→ 必要时补一句现实边界
```

写作时遵守：

- 从用户能认出的处境开场，例如“还没有开始写简历？”“面试时记得录音”“想知道这个岗位的简历要达到什么标准”。自然时可以用问句，不要求每项都用同一句式。
- 多用“你”“上传”“帮你”“最后拿到”等直接表达；材料、动作和产物尽量具体，例如 JD 截图、面试录音、终版简历、打招呼话术和调研报告。
- 一句话能讲清时不拆成“能力—流程—价值”三层。各项长短可以不同，保留真实顾问说话时的自然节奏。
- 用户已经逐句标注、修改或明确确认过正文时，把它当成权威底稿。只修正事实不准确、无法验证的效果保证、平台字数限制、隐私安全或明显歧义；不要为了统一术语、句长或结构重新创作。
- 可以有适度营销感，但把“回复率最高”“保证进面”“一定通过”改成“更容易获得回复”“更贴近岗位筛选标准”“以提高进面机会为目标”。
- 不声称读取他人内心或掌握隐藏事实。把“挖掘面试官隐藏想法”写成“分析追问背后的考察意图”，并说明这是基于对话证据的判断。
- 现实边界也用人话说明，例如“如果是学历硬门槛被卡，内容优化也解决不了”，不要改写成冗长免责声明。

不同位置允许不同长度：

- `short_description` 受 UI 快速扫描和 25—64 字限制，只保留最核心的场景、动作或结果，不强塞完整五段关系。
- README 的 Skill 一句话说明可以稍长，优先让小白看完就知道什么时候调用、需要给什么以及大致能拿到什么。
- Onboarding 可以继续解释差异、方法和边界，但说完后必须直接开始，不停在宣传页。

对比示例：

```text
偏 AI：基于真实经历和目标 JD 生成可投递材料，并完成岗位化证据补强。
更自然：上传已有简历和目标岗位 JD，AI 会先找出不匹配的地方，再追问你的过往经历，最后帮你改成一份真正属于你的岗位版简历。

偏 AI：将面试转写转化为证据诊断和改进方案。
更自然：面试时记得录音。把录音转成文字后上传，AI 会逐题复盘，告诉你哪句话答得不好、下次可以怎么改。
```

这些例子只说明语气和信息组织，不是要求其他领域照抄求职场景，也不证明某种措辞必然提高转化率。

## 锁定公共文案与自适应跟进

当首次介绍属于品牌产品体验、已经过人工逐句确认，或模型曾反复漏项时，把正文作为锁定公共文案：

- `onboarding/core-introduction.md` 保存唯一权威正文；
- `SKILL.md` 只声明何时读取、哪些内容逐字输出、输出后怎样根据材料继续；
- 品牌、价值契约、问题地图、边界和固定行动口使用低自由度；
- 材料判断、第一道个性化问题和后续工作使用中高自由度；
- 锁定正文后可以立即跟随个性化动作，但不得把动态材料判断写进固定正文；
- 当前对话后续不重复完整介绍。

锁定正文不是所有 Skill 的默认做法。文案很短、任务一次完成或需要高度依赖用户原话时，固定信息契约即可。不要为了“稳定”把整段任务执行也锁死。

## Markdown 交付格式

公共介绍是用户产物，不是内部提示词。定稿时至少检查：

- 第一屏先出现品牌身份和职责，不以内部标题或说明开场；
- 问题地图、路径或顺序使用有序列表；并列的材料、方法和交付使用无序列表；
- 有序列表项下的解释或子列表缩进三个空格，并保留空行，避免渲染成新的顶层段落；
- 在“身份与范围 → 用户问题”“问题地图 → 推荐路径”“路径 → 方法与交付”“正文 → 首次行动”等真正切换阅读任务的位置使用 `---`；
- 不为装饰连续堆分隔线，不用 Mermaid 表达简单的从左到右关系；
- 同级条目可以长短不一，避免为了整齐把每句话写成同一语法和同一长度。

分隔线、序号和缩进不是美容项。它们帮助用户把长介绍按任务切块，也让问题地图和推荐路径在不同客户端稳定渲染。

## 去 AI 味审查

锁定前按用户语言再读一遍，重点删除：

- 连续多段“不是……而是……”和整齐得过头的对偶句；
- 抽象名词连写，却没有对象、动作、例子或产物；
- 每项长度、标点和句式完全一致的清单；
- 为显得严谨而补齐的所有反例、边界和理论名称；
- “赋能、闭环、全链路、深度洞察”等不能被用户检查的价值词；
- 内部 Skill、路由、节点、Reference、状态字段和工具名。

保留必要的专业细节、自然的长短变化和少量口语。去 AI 味不是故意写错，而是让每句话像真实顾问在解决当前问题，而不是产品说明书在证明自己完整。

## 适用判断

以下 Skill 默认必须设计首次使用价值说明：

- 用户会直接点选或显式调用的 JC 品牌 Skill；
- 需要连续多轮交互才能完成的训练、诊断、咨询或创作流程；
- 用户容易误解能力边界、输入要求、反馈节奏或最终交付的 Skill；
- 首次体验会显著影响用户是否愿意继续提供材料的 Skill。

以下情况可以省略，但必须在设计中说明理由：

- 只被其他 Skill 调用、不会直接面对用户的内部 worker；
- 仅执行一个明确机械动作的底层工具或 Script；
- 宿主产品已经在调用前完整展示同一份介绍，且能可靠注入已读版本；
- 用户明确要求的产品规范禁止额外首屏文案。

不要因为“介绍会增加字数”就默认省略，也不要给每个底层工具强塞欢迎页。

## 首次回复契约

首次可见回复应遵循：

- 先读取当前对话，复用用户已经给出的目标、材料和偏好；
- 用用户语言说明价值；可以展示关键方法论，但不展示内部 Skill 名称、文件结构、路由表或工具目录；
- 让用户能够说出本 Skill 与普通做法的核心差异；无法形成真实差异时不要强行比较；
- 把关键处理机制翻译成用户收益，并至少给出一个具体、可检查的交付物；
- 不让用户先理解系统架构，也不要求他离开当前对话重新调用命令；
- 材料已经足够时，介绍后立即开始实际任务或提出第一个核心问题；
- 缺少必需材料时，介绍后只索取最小必需输入；
- 不用模式菜单、题目清单或确认按钮把介绍变成启动门槛；
- 不承诺无法验证的效果、成功率、隐藏数据或跨会话记忆。

介绍可以包含一个很短的安全感说明，例如“答不上来可以直接说不知道”或“不会替你编造数据”，但只保留真正影响用户参与方式的边界。

## 重复与版本

普通聊天只能依赖当前可见历史：

- 当前对话首次触发时输出完整介绍；
- 已经输出后不重复；
- 用户中途切换模式时只说明变化，不重发介绍；
- 不假装知道用户在其他会话是否看过。

有产品 Runtime 时可以使用类似 `onboarding_version_seen` 的状态：

- 首次或介绍版本升级时输出完整介绍；
- 已读当前版本时使用一句话承接并直接开始；
- 状态由平台持久化，Skill 不凭空声称已保存。

## 文件放置

满足以下任一条件时，优先建立 `onboarding/core-introduction.md`：

- 文案属于稳定产品体验，需要跨模型保持信息完整；
- 首次介绍超过一个短段落；
- 需要版本管理、产品 Runtime 或多入口复用；
- 容易因模型自由发挥漏掉关键价值或边界。

`SKILL.md` 只保留读取条件、首次回复动作和重复规则。完整方法论不是首次介绍；只有用户主动查看时才加载更长说明。

简单、单轮且介绍只需一两句话的 Skill，可以直接把契约写在 `SKILL.md`，无需为目录对称新增文件。

## 常见失败

- 一上来只说“请上传材料”，用户仍不知道为什么要给；
- 把功能列表当价值，罗列十几个模式或内部 Skill；
- 把方法论完全藏起来，导致用户只能相信抽象承诺，感受不到判断依据和专业性；
- 展开过多内部实现、完整工作流或专业术语，价值尚未讲清，首屏已经过长；
- 信息虽然齐全，却没有说明相对普通做法的差异、具体交付或继续参与的风险边界；
- 只写系统采用了什么机制，没有说明该机制怎样改变用户体验或产物；
- 只承诺“提升、优化、赋能”，没有用户能够检查的判断、文档、改写稿、证据或下一步；
- 为了制造价值感贬低其他方法、夸大效果，或把未经验证的留存假设写成事实；
- 介绍结束后停下来等用户确认，已有材料也不开始；
- 讲清系统怎么工作，却没说用户最终得到什么；
- 固定宣传词与当前任务冲突，忽略用户已经提供的材料；
- 每轮重复欢迎语；
- 把完整方法论、品牌历史或作者履历塞进首次回复；
- 用“适合所有人”“一定提升通过率”等不可验证承诺。

## 首轮 Eval

至少准备两类案例：

1. 必需材料已经齐全：应完整说明价值并在同一回复开始任务。
2. 缺少必需材料：应完整说明价值，只索取最小必需输入。

Rubric 至少检查：

- 定位、适用人群、处理方式、用户收获和开始方式是否齐全；
- 用户能否复述它与普通做法的核心差异，或在不适合比较时说清核心问题；
- 至少一个关键机制是否已经翻译成用户收益；
- 方法论披露是否足以解释专业性和可信度，同时没有演变成内部实现说明书；
- 是否出现具体、可检查的交付物，而不只有抽象效果；
- 是否诚实降低了继续提供材料或参与多轮流程的不确定性；
- 是否复用了已有上下文；
