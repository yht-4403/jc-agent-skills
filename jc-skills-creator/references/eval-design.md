# Eval 设计

当创建、修改 Description、增加 Gotcha、拆分 Skill 或验证真实失败时读取本文件。

## 目录

- Eval-first
- 测试层级
- 测试记录
- 前向测试
- 失败定位
- 回归与跨模型

## Eval-first

在写 Skill 正文前，先准备能够暴露差异的请求。

来源优先级：

1. 真实用户请求；
2. 已知失败；
3. 相邻 Skill 混淆；
4. 边界和反例；
5. 人工构造的补充案例。

先记录无 Skill 基线。没有基线，就无法知道 Skill 是否真的改善结果。

## 测试层级

### 1. 准入测试

比较：

- 无 Skill；
- 一句临时提示；
- 加载完整 Skill。

如果一句提示已经稳定解决，不要用更重 Skill。

### 2. 触发测试

至少覆盖：

- 应触发；
- 不应触发；
- 与相邻 Skill 表达高度相似；
- 用户没有说内部 Skill 名称；
- 用户明确调用；
- 用户只要求普通领域任务。

记录欠触发、误触发和抢路由。

### 3. 渐进加载测试

检查：

- Skill 触发后是否读取了正确 Reference；
- 不满足条件时是否避免读取；
- 读取后是否实际改变判断或产物；
- 是否漏读关键模板、标准或边界；
- 是否无条件加载全部资源。

### 4. 首次体验测试

对直接面向终端用户的 Skill，至少测试：

- 材料齐全：首次回复说明定位、适用人群、处理方式和用户收获，并在同一回复开始任务；
- 材料缺失：首次回复完成价值说明后，只索取最小必需输入；
- 价值差异：用户能从首次回复理解它相对普通做法多解决了什么；没有真实差异时不强行制造对立；
- 机制到收益：至少一个关键机制被翻译为用户可感知的体验或结果，而不是只列功能；
- 方法披露幅度：适度说明证据依据、判断顺序、核验方式或反馈闭环，使专业性可见；不倾倒状态字段、文件结构、工具轨迹或完整流程；
- 具体交付：至少出现一个可检查的判断、文档、改写稿、证据、方案、任务或下一步；
- 参与风险：缺材料、答不上来或中途结束的处理符合真实能力，不虚构保存、恢复或效果保证；
- 后续一轮：不重复介绍；
- 用户已经说过目标或偏好：介绍和起始动作正确复用，不重新盘问；
- 用户说“直接开始”：不展示菜单或等待确认。
- 多入口顾问型 Skill：用户能从问题地图认出自己，地图不是内部功能清单，也没有被写成必须全部完成的固定流程；
- 推荐顺序：默认路径和改变顺序的条件清楚，用户仍可选择其他入口；
- 锁定公共文案：首次逐字输出、后续不重复，动态材料判断和个性化第一步没有被错误锁进正文；
- Markdown 结构：有序列表、子级缩进、空行和分隔线在目标客户端能形成正确层级；
- 去 AI 味：没有连续同构句、抽象名词堆叠、过度对偶或内部术语，专业细节仍足以建立可信度。
- 人工确认文案：用户提供逐句标注或明确要求直接沿用时，保留原意、口语和自然长短，只对事实错误、不可验证承诺、平台硬限制或安全边界做最小调整。

只检查信息、价值与动作契约，不把某一版固定文案当成唯一正确输出，也不把篇幅、术语密度、宣传感或继续使用率当作替代指标。

如果产品明确采用人工确认的锁定公共文案，Eval 可以检查逐字一致性；这只验证产品一致性，不代表该文案本身已经证明更有效。文案质量仍需用真实用户反馈和端到端任务表现判断。

### 5. 端到端任务测试

使用明确 Rubric 判断：

- 是否解决用户目标；
- 是否使用用户证据；
- 是否遵守边界；
- 是否交付正确形态；
- 是否减少已知错误；
- 是否产生新的副作用。

不要只比较语气和篇幅。

对会调用外部工具、账号或套件成员的 Skill，再增加零配置测试：

- 新机器没有作者本机的其他 Skill、CLI 和第三方运行包；
- 用户不知道安装、配置、OAuth、二维码和权限术语；
- Agent 能检测缺口，说明可信来源，并在安装前取得同意；
- 必须由用户完成的授权会把原始链接、二维码和返回口说清；
- 用户完成后由 Agent 继续验证，不把命令排障甩回用户；
- 用户拒绝安装或宿主不能执行时，仍有范围诚实的降级交付。

产品包测试与开发仓库测试分开：确认运行时不会读取的 Evals、基准结果和发布记录没有随单个 Skill 分发，同时确认移出后关键 Gotcha 仍已编译进运行规则。

### 6. Skill 库回归

新增或修改 Skill 后，重跑：

- 相邻 Skills 的正向请求；
- 当前 Skill 的负向请求；
- 共享触发词请求；
- 旧版本曾经通过的英雄案例；
- 系统或项目规则容易产生竞争的请求。

## 测试记录

每条至少记录：

```text
id
来源
原始用户表达
是否应加载
禁止加载的相邻 Skills
预期模式
必须读取的资源
禁止行为
端到端 Rubric
无 Skill 基线
当前版本结果
失败层级
备注
```

可以先用 Markdown。案例增加、需要批量运行时再转 JSONL 或脚本。

## 前向测试

保持验证完整性：

- 使用新上下文或独立 Agent；
- 像真实用户一样提出任务；
- 传原始材料，不传预期答案和诊断；
- 不告诉测试者怀疑的 Bug；
- 清理可能泄漏答案的旧产物；
- 查看实际输出、工具轨迹和文件；
- 复杂或可能影响真实系统的测试先取得授权。

如果只有看到预期答案才成功，Skill 或测试设计仍不可信。

## 失败定位

使用以下层级：

| 层级 | 问题 |
|---|---|
| 准入 | 根本不该建，或应是全局规则、Script、Reference |
| 触发 | Description 欠触发或误触发 |
| 模式路由 | 创建、审查、迭代或执行分错 |
| 资源读取 | 没读、错读或过度读取 |
| 首次体验 | 用户不知道 Skill 价值、介绍缺项、重复介绍或介绍阻断任务 |
| 领域判断 | 规则、证据或边界错误 |
| 执行 | 工具、脚本或步骤错误 |
| 交付 | 产物形态、清晰度或完成度错误 |
| 回归 | 当前改动破坏相邻任务 |

先修改最靠近根因的一层，不要用更长输出掩盖前面错误。

## 回归与跨模型

Description、系统规则和模型版本变化都可能改变路由。

当 Skill 进入稳定使用或公开发布后：

- 固定一组英雄案例；
- 保留历史失败；
- 对不同模型分别跑触发和端到端测试；
- 记录差异，不假设 Claude、GPT 或其他模型行为一致；
- 新模型上线时优先复查路由、资源读取和强制流程。

V1 可以先完成单模型前向测试，但必须把跨模型标记为未验证，不能声称普遍稳定。
