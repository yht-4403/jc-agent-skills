# JC Skills Creator

把已有的领域判断、证据和失败经验编译成真正会改变 Agent 行为的 Skill。先证明 Skill 应该存在，再设计上下文和文件；不要把母文档改写成一份更长的提示词。

## 识别工作模式

根据用户当前目标选择一种主模式；需要时组合，但不要机械输出全部产物。

- **创建**：判断准入、单 Skill 或套件，编译规则、资源和 Evals；用户要求落地时再生成文件。
- **审查**：检查现有 Skill 的存在价值、触发、证据、自由度、上下文和交付；除非用户要求修改，否则只报告。
- **迭代**：根据真实请求、输出、工具轨迹或产物定位失败层级，只修改导致失败的部分并补回归。

用户直接要求解决职业、销售、写作、文件处理等领域问题时，转给相应领域能力，不要因为其中出现“方法”“流程”等词就进入本 Skill。

## 先处理边界与转交

- 需要从大量书籍、课程、论文或行业资料恢复知识地图与方法时，先使用 `domain-skill-factory`；本 Skill 接收它形成的领域底座。
- 边界已经清楚、只需标准脚手架和格式校验的简单 Skill，可直接使用通用 `skill-creator`。
- 安装、激活、停用、迁移、去重或运行时链接管理，必须使用 `jc-skill-installer`。
- 不要在没有领域资料、真实经验或失败证据时，凭空宣布一套方法论可靠。

正式创建或更新 Skill 时，完整读取并遵守当前环境的通用 `skill-creator`。涉及用户 Skill 的存储或运行状态时，再完整读取 `jc-skill-installer`。不要复制它们已有的初始化、校验和安装逻辑。

## 先决定发布状态与版本通道

创建或迭代前明确 Skill 属于哪一类，不把“仓库中存在”等同于“每天都应加载”：

- **核心自动触发**：JC 自有常用入口或被近期真实任务反复证明的高频能力；Description 必须有清楚边界。
- **显式调用**：兼容入口、高风险动作、昂贵流程或容易与邻居混淆的能力；在 `agents/openai.yaml` 设置 `policy.allow_implicit_invocation: false`。
- **仓库存档、按需搜索**：低频和长尾能力；不进入 active manifest，用户口头要求搜索时由 `jc-skill-installer` 发现。

JC 自有 Skill 必须在默认核心集合中显式列出，不能被通用清理规则误删；但这不代表每个 JC Skill 都允许自动触发。负责搜索候选 Skill 的入口必须可自动触发，否则用户自然语言说“帮我找适合这次任务的 Skill”时无法稳定路由。

需要版本迭代时遵循安装器中用户已确认的固定入口约定：

1. 当前版只保留一份 `family-latest` 实体目录，机器名、默认调用名和当前入口保持一致，展示名使用 Latest。
2. 替换当前内容前，按 `archive_on_next_update` 将旧内容归档为未占用的 `family-vN`，改好归档元数据；历史归档不可覆盖。
3. `skill-channels.json` 的 `latest` 为 `latest`，`versions.latest` 指向固定实体目录；归档登记后递增待归档编号。
4. 同一 family 日常只加载当前版；旧版保留用于回归和回滚。回滚也恢复到固定 latest 入口，不直接启用历史版。
5. 创建器负责内容准入、差异说明和 Evals；安装器负责通道记录、启停与同步。未采用版本管理的 Skill 不强加 latest，其他旧 family 不批量迁移。

交付时说明本次是否属于未注册 family 的原地修订，或已注册 family 的归档更新；列明当前入口、归档位置和回归范围。没有通过回归，不宣称内容已验证。本 Skill 与安装器目前未注册版本 family，窄范围维护可原地修订并保留可恢复备份。

## 执行五阶段编译

### 1. 做 Skill 准入判断

先检查无 Skill 基线、历史失败或相邻能力，不要默认用户说“做 Skill”就必须新增一个。

依次判断：

1. 模型没有 Skill 时是否已经稳定做好；
2. 一句临时提示是否足够；
3. 规则是否适合所有任务，应进入项目或全局说明；
4. 问题是否主要是确定性重复执行，应写 Script 或工具；
5. 知识是否变化快到无法可靠维护；
6. 条件化上下文是否会明显改变判断或一致性；
7. 新 Skill 是否会与已有 Skill 争抢同类请求。

输出一种准入结论：

- 不建立；
- 写入全局或项目规则；
- 只建立 Script 或工具；
- 给已有 Skill 增加 Reference；
- 建立单 Skill；
- 建立 Skill 套件；
- 先进入领域资料工厂。

没有完成准入判断，不生成 Skill 文件。需要详细分流时读取 [single-vs-suite.md](references/single-vs-suite.md)。

### 2. 编译领域主张

只保留会改变判断、执行或边界的非显然内容。逐条区分：

- 安全、权限与任务边界；
- 有来源支持的稳定机制；
- 作者经验或产品假设；
- 从真实失败形成的 Gotcha；
- 品牌声音或个人偏好；
- 模型已知常识；
- 条件化重知识；
- 确定性重复执行。

每条候选规则都问：

1. 没有它，模型真的会做错吗？
2. 它改变结论，还是只增加解释长度？
3. 它的来源和适用条件是什么？
4. 它是否把个案、偏好或作者确信写成普遍事实？

需要建立主张清单或审查伪精确时，读取 [claims-and-evidence.md](references/claims-and-evidence.md)。

### 3. 分配自由度与上下文

遵循四层自由度：

| 层级 | 默认自由度 |
|---|---|
| 任务、权限、停止和转交边界 | 低 |
| 证据顺序、关键分类和失败信号 | 中低 |
| 默认过程、回退和跳过条件 | 中 |
| 具体问法、案例选择、格式和措辞 | 高 |

精确约束不该犯的错误，开放允许完成任务的路径。

判断规则写得太死或太泛时读取 [specificity-and-freedom.md](references/specificity-and-freedom.md)。设计 Description、`SKILL.md`、References、Scripts、Assets 或持久配置的分工时读取 [context-architecture.md](references/context-architecture.md)。

面向外部用户发布的 Skill 或套件还必须做依赖闭包检查：默认不能依赖作者本机恰好安装的其他 Skill、CLI、Python 包、绝对路径或私有配置。套件内部可以引用明确随包分发的成员；其他方法应提炼为最小必要规则、Reference 或 Script 内聚进当前 Skill。确实需要外部工具时，必须写清检测、可信安装来源、用户授权、验证和无工具回退，不能只写“请先安装”。

直接面向终端用户的 Skill，尤其是多轮训练、诊断、顾问或产品化流程，必须设计首次使用价值说明。读取 [首次使用价值说明](references/first-use-onboarding.md)：先建立最小价值契约；入口问题较多时用卡点地图降低选择难度；产品文案已经人工确认时再锁定公共正文，并把动态材料判断留给后续动作。内部 worker、底层工具或宿主已经可靠完成同一介绍时才可说明理由后省略。

### JC 界面命名约定

创建或更新 JC 自有及用户在当前 Skill 库中维护的品牌 Skill 时，区分三类名称：

- `name` 与目录名是机器标识，使用英文小写 kebab-case，二者保持一致；
- `agents/openai.yaml` 的 `interface.display_name` 是列表左侧的产品名，默认使用简洁的英文 Title Case；产品线系列统一以 `自有产品线` 开头，例如 `Acme Career Planner`；
- `interface.short_description` 是列表右侧的中文备注，用中文说明核心价值；`default_prompt` 跟随目标用户语言，并显式包含 `$skill-name`。

除非用户明确指定其他语言，不要把 `SKILL.md` 的中文标题直接复制成 `display_name`。生成前先检查同品牌相邻 Skill 的拼写、前缀和命名结构，避免同一列表中中英混排或品牌大小写不一致。第三方 Skill 保留上游展示名，不因本约定擅自翻译。

为直接面向 C 端小白的 README、onboarding、功能介绍或中文 `short_description` 写文案时，读取 [首次使用价值说明](references/first-use-onboarding.md) 中的“JC 小白友好的场景式产品说明文风”。默认用用户能认出的场景、要提供的材料、AI 会做的事和最终拿到的结果来说明，不把内部能力翻译成一串抽象产品词。用户已经逐句标注或明确确认过文案时，以用户原话为底稿，只为事实准确、不可验证承诺、平台硬限制或安全边界做最小调整，不重新改写成整齐同构的“专业版”。

### 4. 先设计 Evals

至少建立：

- 无 Skill 基线；
- 应触发案例；
- 不应触发案例；
- 相邻 Skill 混淆案例；
- 渐进读取案例；
- 首次体验案例：材料齐全时介绍后直接工作，材料缺失时只索取最小输入；
- 端到端任务质量门；
- 修改后的回归范围。

当目标是讲解、教学、代码学习或新人上手 Skill，且任务通常能取得可核对制品时，不要只写“多举例”或“通俗易懂”。把以下行为编译进 Instructions 和端到端 Eval：无需关键词的默认触发、原始制品的真实性分级、实测与模拟的标注、局部高亮、抽象图回映到原始制品、脱敏与复现入口，以及结尾留给读者的一次动作或判断。同时加入一句话定义、纯执行、只绘图和决策报告等负向案例，防止协议误触发。固定的段落数量和措辞不作为 Eval；验证读者能否把代码、报文或日志与机制对应起来。

不要只用几个与作者结论同向的成功案例证明 Skill 有效。每次修改 Description，都增加或更新路由 Eval；每次新增 Gotcha，都保留对应失败案例。

设计或运行测试时读取 [eval-design.md](references/eval-design.md)。需要创建器自身的第一批测试请求时读取 [eval-cases.md](references/eval-cases.md)。

### 5. 实现、校验与维护

用户只要求讨论、分析或审查时，不写文件、不安装、不激活。

用户明确要求创建或修改时：

1. 按通用 `skill-creator` 初始化标准目录；
2. 先写必要 References，再写精简 `SKILL.md`；
3. 对直接面向用户的 Skill 实现首次使用价值说明及其首轮 Eval；
4. 只创建实际需要的资源目录；
5. 生成与 Skill 一致的 `agents/openai.yaml`，并按 JC 界面命名约定检查展示名、中文备注和默认提示；
6. 运行通用结构校验；
7. 按 `jc-skill-installer` 的单一来源规则激活和审计。活动清单必须同步到 Codex、Claude Code、Gemini、CodeBuddy，以及 DeepSeek Harness 的 `~/.dsh/skills`（只放符号链接）。不要把实体文件复制进 Harness 目录，也不要为此重建已废弃的 `~/.agents/skills`。创建器不另写同步脚本，安装器的 `activate`、`bootstrap` 和 `sync-dsh` 是唯一维护入口；
8. 用未泄漏预期答案的真实请求做前向测试；
9. 把失败定位到准入、触发、路由、资源读取、首次体验、判断、执行或交付层。
10. 扫描跨 Skill 引用、外部二进制、运行时包、绝对路径和凭据假设；对终端用户路径做一次“新机器、零配置”演练。
11. 区分运行必需文件与开发期文件。用户安装包只保留会改变运行行为、提供模板或支持确定性执行的内容；Evals、基准结果、发布清单和设计记录默认放在开发仓库，不因目录对称塞进产品 Skill。
12. 若属于已注册版本 family，先归档旧 latest，再更新固定入口、运行回归并同步；确认历史版本只保留在源仓库。

发布前或审查现有 Skill 时读取 [quality-gates.md](references/quality-gates.md)。

## 交付契约

### 创建

先交付准入结论，再按需要给出：

- 中心任务、非目标与转交边界；
- 正向、负向和相邻触发语料；
- 主张与证据清单；
- 自由度分配；
- 单 Skill 或套件判断；
- 上下文与文件结构；
- 首次使用价值说明方案及是否需要独立 onboarding 文件；
- 第一批 Evals；
- 用户要求落地时生成并校验实际文件。

### 审查

结论先行，按影响排序。每个问题都引用具体原文或行为，区分：

- 已被真实案例证明的问题；
- 静态检查发现的风险；
- 纯偏好差异。

说明最小修改位置，不用完整重写掩盖根因。

### 迭代

交付：

- 失败分类与根因证据；
- 应优先修改的层；
- 最小补丁方向；
- 新增或修改的 Eval；
- 是否形成 Gotcha；
- 回归范围与验证结果。

### Kimi Work 兼容验收

目标包含 Kimi Work 时，复用安装器的专用同步机制。验证目标客户端实际发现、相对 References/脚本读取和一次代表性任务；只通过链接或结构检查时不得称已完成模型任务回归。Codex 专用工具、插件 MCP、绝对路径和包依赖要检测或回退；`agents/openai.yaml` 的展示名和显式调用策略不默认跨平台生效，不为迁移修改第三方原始正文。

## 核心 Gotchas

- 不要跳过准入判断，直接满足“做一个 Skill”的表面请求。
- 不要把母文档、书籍摘要或全部案例复制进 `SKILL.md`。
- 不要重复模型常识、系统规则或通用创建器已经提供的说明。
- 不要把 JC 观点、单个案例、品牌语气或模型生成内容写成领域事实。
- 不要用未经验证的比例和阈值制造确定感。
- 不要把固定提问数量、固定轮次、固定表格当成执行稳定性。
- 不要用目录完整、格式通过代替真实任务验证。
- 不要把中文正文标题直接复制为 JC 品牌 Skill 的 `display_name`；英文产品名放左侧，中文价值说明放 `short_description`。
- 不要让用户首次调用后只看到材料请求、功能菜单或内部架构；先让他知道适合谁、怎样工作和能获得什么。
- 不要把信息齐全误认为有价值感；首次介绍若只有功能、流程和输入要求，却没有真实差异、具体交付和低风险参与说明，仍然不合格。
- 不要把方法论全部藏成黑箱，也不要倾倒内部实现；只展示足以说明证据依据、判断顺序、核验方式或反馈闭环的关键细节，并说明它为什么让结果更可信。
- 不要把首次介绍做成固定长模板或启动确认页；固定信息完整性，保留表达自由，并在材料齐全时直接开始任务。
- 不要机械复制其他 Skill 的卡点数量、领域二分法或推荐顺序；复用的是“认出卡点—理解路径—看见交付—立即行动”的结构。
- 不要把序号、缩进、空行和分隔线当作润色；锁定公共文案必须在目标客户端形成稳定可读的 Markdown 层级。
- 不要用整齐同构的句式、抽象名词和连续对偶制造专业感；保留用户原话、具体例子和自然长短。
- 不要在解释型 Skill 里用加工后的架构图替代全部原始证据，也不要把手写模拟 JSON 冒充真实接口结果。
- 不要把用户已经逐句标注或确认的产品文案统一重写成 AI 产品说明书；除非存在事实错误、不可验证承诺、平台限制或安全问题，只做必要微调。
- 不要只测试应触发案例；新增 Skill 可能让整个 Skill 库变差。
- 不要为文件对称而拆 Skill；按目标、判断逻辑、必要输入和产物拆分。
- 不要自行重写脚手架、校验器和安装器；先复用已有能力。
- 不要为 DeepSeek Harness 再复制一份 Skill。运行时只链到 `~/.dsh/skills`，由 `jc-skill-installer` 维护。
- 不要在审查请求中擅自修改，在创建请求中擅自安装或发布。
- 不要把作者机器上的其他 Skill、CLI、Python 包或绝对路径当作默认能力；外部依赖要内聚、检测或提供可完成的回退。
- 不要把 Gotchas、Quality Gates、Evals 等开发术语当成必须分发的文件名；只把运行时确实需要执行的规则留在产品包，把测试与发布证据留在开发侧。
- 不要静默安装软件或代替用户完成账号授权；可以自动检测、说明来源，并在取得同意后执行安装和发起授权。
- 不要因为一次偶发失败持续扩写 Instructions；先确认能否复现和失败层级。
- 不要同时启用同一 Skill family 的多个版本，也不要给固定 `family-latest` 再复制一份同内容的 v 目录。

## 停止条件

出现以下情况时停止生成，说明缺口并给出最小下一步：

- 缺失信息会改变 Skill 是否存在或所属类别；
- 没有任何领域来源、真实经验或可验证任务；
- 用户要求把未经支持的观点包装成事实；
- 目标实际是普通领域任务、资料总结或安装管理；
- 目标系统不支持所设计的触发、依赖或运行方式；
- 存在未解决的同名 Skill、真实目录或来源冲突。
