# JC Skills Creator

把领域经验、证据和真实失败变成会改变模型行为的 Skill。先判断这个 Skill 该不该存在，再动手写。

## 先选模式

- **创建**：从准入判断做到测试设计；用户明确要求落地时才生成文件。
- **审查**：检查现有 Skill 值不值得存在、写得好不好；只出报告，不改文件，除非用户要求。
- **迭代**：带着真实失败案例来，定位是哪一层出了问题，只修那一层。

用户要求直接解决职业、销售、写作等领域问题时，转给对应领域 Skill，不要因为话里出现"方法""流程"就启动本 Skill。

## 交给别人做的事

- 从大量书籍、课程恢复完整领域知识 → `domain-skill-factory`。
- 边界已清楚的简单 Skill 脚手架 → 通用 `skill-creator`。
- 安装、启停、版本归档、多端同步 → `jc-skill-installer`，本 Skill 不处理。

## 五个步骤

### 1. 先判断要不要做

用户说"做个 Skill"不等于要做。依次问：

1. 没有 Skill 时，模型是不是已经能稳定做好？
2. 一句临时提示够不够？
3. 规则是不是适用所有任务，该写进全局说明？
4. 问题是不是确定性重复执行，该写成脚本？
5. 知识变化快到维护不住吗？
6. 上下文条件不同时，模型的判断会明显不同吗？
7. 新 Skill 会不会和已有 Skill 抢同一类请求？

得出一个结论再动手：不做 / 写进全局规则 / 只写脚本 / 给已有 Skill 加 Reference / 做单 Skill / 做套件 / 先去领域资料工厂。没做准入判断，不生成任何 Skill 文件。单 Skill 还是套件拿不准时，读 [single-vs-suite.md](references/single-vs-suite.md)。

### 2. 筛选要写进 Skill 的规则

每条候选规则问四个问题，答不上就不写：

1. 没有它，模型真的会做错吗？
2. 它改变结论，还是只增加篇幅？
3. 它的来源和适用条件是什么？
4. 它是不是把个案、偏好或作者确信写成了普遍事实？

需要逐条分类（边界、机制、经验、Gotcha、语气、常识）或审查伪精确数字时，读 [writing-rules.md](references/writing-rules.md) 的"主张与证据"部分。

生成的 Skill 正文说人话：

- 用祈使句写具体动作，不堆抽象名词；
- 术语第一次出现时给一句人话解释，之后照用；
- 每条规则都能回答"没有它会做错什么"。

### 3. 决定哪里管死、哪里放手

| 内容 | 管多死 |
|---|---|
| 任务边界、权限、停止和转交 | 写死 |
| 证据优先级、关键分类、失败信号 | 写清方向，允许情境解释 |
| 默认流程、回退条件 | 给默认顺序，允许跳过 |
| 问法、案例选择、措辞 | 放手 |

一句话：把不该犯的错误写死，把能完成任务的路径放开。规则写得太死或太泛时，读 [writing-rules.md](references/writing-rules.md) 的"精确度与自由度"部分。

面向外部用户发布的 Skill，不能只依赖作者本机的其他 Skill、CLI、Python 包或绝对路径；必须用外部工具时，写清检测方法、可信安装来源、用户授权和没有工具时的回退。直接面向终端用户的 Skill 还要设计首次使用价值说明，读 [first-use-onboarding.md](references/first-use-onboarding.md)。

### JC 界面命名约定

JC 自有及库内维护的品牌 Skill：

- `name` 和目录名：英文小写 kebab-case，二者一致；
- `agents/openai.yaml` 的 `display_name`：简洁英文 Title Case，ChengziCV 系列以 `ChengziCV` 开头；
- `short_description`：中文说明核心价值；`default_prompt` 跟随用户语言，包含 `$skill-name`。

生成前先看同品牌相邻 Skill 的命名，避免中英混排和大小写不一致。第三方 Skill 保留上游展示名。

### 4. 先写测试

写正文前先准备能暴露差异的请求：无 Skill 基线、应触发、不应触发、相邻 Skill 混淆、首次体验（材料齐全直接开始，材料缺失只索取最小输入）、端到端质量门。改一次 Description 就更新一次路由测试；加一条 Gotcha 就留一个对应失败案例。具体设计方法和本 Skill 自身的测试案例，读 [evals.md](references/evals.md)。

### 5. 落地与验证

用户只要求讨论或审查时，到此为止，不写文件。用户明确要求创建或修改时：

1. 用通用 `skill-creator` 初始化目录；
2. 先写 References，再写精简 `SKILL.md`（正文控制在 120 行左右，放不下就移入 References）；
3. 只创建实际需要的资源目录；
4. 生成 `agents/openai.yaml`，按上面的命名约定检查；
5. 运行结构校验，再按 `jc-skill-installer` 完成激活和同步；
6. 用没看过预期答案的真实请求做前向测试；
7. 发布前审查和失败定位，用 [evals.md](references/evals.md) 的回归节和"失败 → 修改位置"表。

文件结构怎么分层（Description / SKILL.md / References / Scripts 分工），读 [context-architecture.md](references/context-architecture.md)。

## 好 Skill 长什么样

同一个规则点的两种写法：

**坏：抽象 + 禁令堆砌**

```markdown
## 交付质量管控

不要把未经验证的输出交付给用户。
不要用固定模板代替真实判断。
不要在材料不足时强行给出结论。

## 过程要求

执行多维度信息整合，完成深度需求挖掘，
确保交付物具备专业性与针对性。
```

**好：具体动作 + 可核对**

```markdown
## 交付前检查

- 材料不足时，说出缺哪一项，只问这一个问题；
- 每个结论后面注明来自用户材料还是推测；
- 不确定的推测用"可能"，不改成确定句。
```

写 Skill 时按右边这种写：每条能被执行、被核对。

## 交付什么

- **创建**：先给准入结论，再给触发语料、规则清单、自由度分配、文件结构和第一批测试；用户要求落地时才生成文件。
- **审查**：结论先行，按影响排序；每个问题引用原文，区分"已被真实案例证明""静态风险""纯偏好"；给出最小修改位置，不用整体重写掩盖根因。
- **迭代**：失败层级与证据、该修哪一层、最小补丁、新增测试、回归范围。

## 红线

1. 先完成准入判断，再满足"做一个 Skill"的请求。
2. SKILL.md 只写模型不知道、且没有它就会做错的事；母文档、案例全集和模型常识不进正文。
3. 规则区分事实与观点：JC 经验、单个案例、品牌语气都要标注适用范围；数字和阈值必须标来源。
4. 用真实任务验证，不用目录完整、格式通过当成交付。
5. 面向终端用户的 Skill，首次调用先让用户知道适合谁、能得到什么；材料齐全就直接开始任务，不先展示菜单。
6. 面向外部用户的 Skill 不假设作者本机环境；外部依赖必须可检测、有回退。
7. 审查请求只报告，创建请求经确认才写文件，安装和同步永远交给 `jc-skill-installer`。
8. 一次偶发失败先复现、定位层级，再改规则；只修导致失败的那一层。

## 停止条件

出现以下情况时停下来，说明缺口并给出最小下一步：

- 缺失的信息会改变"要不要做、做成什么"；
- 没有任何领域来源、真实经验或可验证任务；
- 用户要求把没有依据的观点包装成事实；
- 目标其实是普通领域任务、资料总结或安装管理；
- 存在未解决的同名 Skill 或来源冲突。
