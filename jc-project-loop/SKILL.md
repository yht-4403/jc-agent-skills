# JC Project Loop

把长任务从“依赖对话记忆”改成“读取账本 → 领取一项 → 执行 → 提交 → 复核 → 更新账本”。始终以项目文件为准，不凭聊天历史声明进度。

## 边界

- 只负责调度、状态和机械校验；把研究、写作、开发等语义工作交给当前任务指定的领域 Skill 或协议。
- 只使用 Python 标准库和本地文件；不引入 Redis、Celery、BullMQ、数据库、Codex SDK、并发 Agent、Cron、Web 后台或复杂成本预测。
- 不运行无限循环。必须设置完成标准、有限重试、质量门和阻塞状态。
- 不自动执行发布、付款、删除、生产写入等不可逆动作；在对应任务前设置人工质量门。
- 不把 Skill 源目录用于保存项目数据。每个实际项目使用独立目录。
- 本 Skill 是底层内部能力，不单独展示长篇首次介绍；首次调用时用一句话说明“会建立本地账本并可恢复”，随后直接工作。

## 首次初始化

先确定项目目录、目标、完成标准和第一批任务。信息足够时直接初始化；只有项目目录或完成标准缺失且无法安全推断时，才索取最小输入。

```bash
python3 scripts/project_loop.py \
  --项目 <项目目录> \
  初始化 \
  --目标 "<可验证目标>" \
  --完成标准 "<怎样证明全部完成>" \
  --最大尝试次数 3
```

初始化默认在第 1 个任务完成后设置“首批样本”质量门。需要其他门时重复传入：

```bash
--质量门 "首批样本:1" --质量门 "中期抽检:10"
```

初始化后使用 `添加任务` 或 `导入任务` 建立队列。批量导入前读取 [状态、目录与命令契约](references/状态与命令.md)。

## 每次进入项目

无论是否仍在同一对话，都按以下顺序开始：

1. 运行 `检查`，确认账本结构有效。
2. 运行 `状态`，读取真实覆盖率、当前任务、质量门和阻塞。
3. 运行 `下一步`，只根据返回动作继续：
   - `领取`：运行 `领取`；
   - `执行`：读取返回的当前任务并完成语义工作；
   - `复核`：按任务验收标准顺序复核；
   - `质量门`：暂停并报告需要谁确认什么；
   - `阻塞`：报告具体任务、原因和最小解法；
   - `完成` 或 `已停止`：不得继续领取。

## 推进一轮

### 1. 领取

```bash
python3 scripts/project_loop.py --项目 <项目目录> 领取
```

一次只允许一个 `进行中` 任务。已有当前任务时必须继续它，不得再领新任务。

### 2. 执行

只读取：

- 当前任务；
- 当前任务声明的输入文件；
- 任务指定的领域 Skill 或协议；
- 输出契约；
- 必要的少量黄金样本。

不要默认加载全部历史产物、完整事件日志或其他无关任务。把产物写进项目目录，避免依赖未落盘的对话内容。

### 3. 提交

至少提交一个实际存在的产物文件：

```bash
python3 scripts/project_loop.py --项目 <项目目录> 提交 \
  --任务编号 <编号> \
  --产物 <文件路径> \
  --说明 "<本轮完成内容和实际验证>"
```

脚本只检查文件存在、状态合法和路径可记录；领域正确性必须经过复核。

### 4. 顺序复核

不使用并发多 Agent。优先在新的 Codex 上下文中顺序复核；若用户只允许当前上下文，则明确记录复核局限，不把自评描述为独立复核。

```bash
python3 scripts/project_loop.py --项目 <项目目录> 复核 \
  --任务编号 <编号> \
  --结果 通过 \
  --复核者 "<身份>" \
  --意见 "<依据、命令和实际结果>"
```

不通过时使用 `--结果 返工`。达到任务最大尝试次数后自动进入 `已阻塞`，不得无限重试。

## 持续运行

用户明确要求“持续跑到质量门”“不要每项询问”或创建了 Goal 时，重复“运行 `下一步` → 完成返回动作”，直到出现：

- 未确认质量门；
- 已阻塞；
- 已暂停或已停止；
- 权限、资料或关键决定缺失；
- 全部任务完成并满足完成标准；
- 当前运行环境中断。

每完成一次状态转换就已落盘；不要因为上下文即将压缩而提前宣称项目完成。重新进入时从 `检查` 和 `状态` 恢复。

## 人工控制

支持：

```text
确认质量门 / 暂停 / 恢复 / 停止 / 跳过 / 标记阻塞 / 解除阻塞
```

具体参数读取 [状态、目录与命令契约](references/状态与命令.md)。停止不删除任何任务或产物；跳过和解除阻塞必须记录理由。

## 验证与交付

交付前必须同时满足：

1. `检查` 通过；
2. `下一步` 返回 `完成`；
3. 没有 `进行中`、`待复核`、`待返工` 或 `已阻塞` 任务；
4. 所有已触发质量门均已确认；
5. 实际产物和验证结果存在；
6. 用户定义的完成标准已经人工或机械验证。

运行或修改本 Skill 时读取 [评测案例](references/评测案例.md)，覆盖正向、负向、相邻混淆、恢复、返工和质量门。

## 核心 Gotchas

- Skill 规定方法，脚本保存状态，Codex完成语义工作；脚本不会自行“思考”或调用 Codex。
- 同一个 Task 可以持续，但活跃上下文可能压缩；任务账本和产物才是长期记忆。
- `进度.md` 是脚本生成的人类视图，`任务.jsonl` 才是任务事实源；不要手改两份制造漂移。
- `提交` 不等于完成；只有复核通过才计入已完成。
- 不用产物数量代替质量，不用一次成功代替完整覆盖。
- 不允许一个任务失败后偷偷新建同义任务绕过重试上限。
- 不自动越过人工质量门，不自动把草稿升级为发布态。
