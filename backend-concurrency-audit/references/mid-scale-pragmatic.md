# 中等并发简化方案

## 使用方式

当用户目标是中小公司、快速迭代、单体或模块化单体、Sealos/云平台部署、50-300 QPS 左右时，优先使用本参考。目标是够用、可上线、可定位问题，而不是大厂 SRE 全套体系。

## 默认可以砍掉

这些能力默认不作为第一阶段建议：

- 生产环境大流量压测
- 影子表、影子库、完整压测流量染色体系
- 完整服务网格、自动化金丝雀发布、按百分比精细分流
- 所有接口都建压测脚本
- 浏览器大并发压测
- 全量链路追踪平台
- 分库分表
- 复杂微服务拆分
- 自建 Prometheus、Grafana、Loki、ELK 全套
- 自建 Kubernetes 运维体系

## 不能砍掉

这些是最小上线保障：

- 健康检查
- 错误日志可查
- 慢 SQL 可查
- 核心接口 p95/p99 和错误率可见
- 外部可用性监控
- 应用版本可回滚
- 数据库变更有回滚或补救方案
- 核心业务链路压测
- 登录 token 场景可压测
- 数据库连接池、线程池、Redis 连接池有明确配置

## 可以交给第三方或云平台

Sealos/云平台通常可以承担：

- 应用部署
- 多实例运行
- CPU/内存资源限制
- 基于 CPU/内存的弹性伸缩
- 环境变量和配置
- 公开访问、域名、TLS
- 数据库托管
- 对象存储
- 基础日志和运行状态

第三方平台可以承担：

- UptimeRobot/Better Stack：外部可用性监控、HTTP 监控、状态页
- Sentry：异常追踪、性能事务、前后端错误聚合
- Grafana Cloud：指标、日志、告警
- 云厂商数据库：备份、监控、慢 SQL、连接数

注意：平台扩缩容不等于系统一定抗压。扩缩容解决不了慢 SQL、锁竞争、连接池打满、Redis 热 key、外部 API 限流、本地状态不安全等问题。

## Sealos 场景建议

如果用户部署在 Sealos，默认建议：

1. 应用保持无状态。
   - session 放 Redis 或 JWT。
   - 上传文件放对象存储。
   - 不把业务状态写在容器本地磁盘。

2. 配置多实例前先检查水平安全。
   - 定时任务不能每个实例重复跑，必要时加分布式锁或拆 worker。
   - 本地缓存不能影响一致性。
   - 本地文件不能作为共享数据。

3. 弹性伸缩只作为兜底。
   - 设置最小实例数 2 起步。
   - 设置最大实例数控制成本。
   - 目标 CPU/内存阈值不要太高，常见从 60%-70% 开始。
   - 压测验证扩容是否真的发生。

4. 日志和告警不足时补第三方。
   - 至少接一个外部可用性监控。
   - 后端接 Sentry 或等价错误追踪。
   - 有条件再接 Grafana Cloud 或云厂商监控。

## 中小团队推荐架构

第一阶段：

```text
前端
  -> Sealos App Deploy / Nginx
  -> Spring Boot 单体
  -> MySQL
  -> Redis
  -> 外部 AI API 或第三方服务
```

第二阶段：

```text
前端
  -> Sealos App Deploy 多实例
  -> Spring Boot API
  -> Worker 实例
  -> MySQL
  -> Redis
  -> MQ
```

同一套代码可以用不同 profile 启动：

```text
api profile：处理在线请求
worker profile：处理 MQ、定时任务、异步任务
```

第三阶段才考虑拆服务：

- AI 对话模块压力独立
- 文件解析 CPU 高
- 后台统计扫库影响在线接口
- 支付/计费需要独立发布和稳定性
- 团队协作已经受单体影响

## 最小压测方案

只做三类：

1. 核心接口压测。
   - 5-10 个核心接口。
   - 10/50/100 并发。
   - 每档 5-10 分钟。

2. 核心业务链路压测。
   - 1-3 条真实链路。
   - 登录拿 token 后串联接口。
   - 20/50/100 并发。

3. 稳定性测试。
   - 50-100 并发。
   - 30-60 分钟。
   - 观察内存、线程、连接池、慢 SQL、p95 是否变差。

## 最小上线清单

上线前确认：

- 构建产物可复现。
- Sealos 上有可回滚版本。
- 环境变量和密钥没有写死。
- `/health` 可访问。
- 数据库迁移可回滚或可补救。
- 核心接口压测通过。
- 核心业务链路压测通过。
- 外部可用性监控已配置。
- 错误追踪已配置。
- 核心日志可按 requestId 查询。
- 有人工回滚步骤。

上线后观察：

- 30 分钟：启动错误、接口 5xx、CPU/内存、慢 SQL。
- 2 小时：真实用户路径、p95/p99、Redis、第三方 API。
- 24 小时：定时任务、内存趋势、连接泄漏、费用和日志量。
