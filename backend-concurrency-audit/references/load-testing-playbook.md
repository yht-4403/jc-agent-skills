# 压测与上线保障

## 使用方式

当用户要求如何压测、如何做全链路压测、如何处理登录 token、多接口串联、上线后怎么确保稳定时，使用本参考。

## 压测分层

单接口压测回答：这个接口快不快。

模块压测回答：一个业务模块能不能稳定承载。

业务链路压测回答：真实用户操作顺不顺。

全链路压测回答：入口、网关、应用、数据库、缓存、MQ、第三方整体稳不稳。

稳定性压测回答：系统跑久了会不会内存泄漏、连接泄漏、性能衰减。

峰值压测回答：系统极限在哪里。

## 后端接口压测和前端压测

中小团队不要用大量浏览器实例制造后端 QPS。默认组合：

- 后端接口压测：制造主要压力，验证服务端容量。
- 少量浏览器路径测试：验证真实页面加载、接口串联和 SSE/WebSocket 体验。
- 核心业务链路 API 压测：模拟真实用户流程。

推荐比例：

```text
后端接口压测：70%
业务链路压测：20%
前端真实页面测试：10%
```

## 有登录 token 的接口

### 方式一：预生成 token

适合业务接口压测。流程：

```text
准备测试账号
批量登录生成 token
保存 token 到 CSV/JSON
压测时每个虚拟用户读取一个 token
请求业务接口
```

优点是避免登录接口污染业务接口结果。缺点是无法测试登录压力，token 过期要处理。

### 方式二：虚拟用户启动时登录

适合完整业务链路压测。流程：

```text
虚拟用户启动
  -> 登录
  -> 提取 token
  -> 保存到变量
  -> 后续请求带 Authorization: Bearer token
```

优点是接近真实用户。缺点是登录接口可能成为瓶颈，业务接口结果会被登录性能影响。

### 方式三：混合模式

推荐中等规模验收使用：

```text
10% 用户执行登录
90% 用户使用预生成 token 执行业务接口
```

## 多接口串联

压测脚本必须支持：

- 提取响应字段
- 保存变量
- 后续请求引用变量
- 校验状态码和业务字段
- 不同虚拟用户使用不同账号
- 不同用户创建不同业务对象
- 清理或标记测试数据

示例链路：

```text
POST /login
  -> 提取 token
GET /user/me
POST /chat/conversation
  -> 提取 conversationId
POST /chat/send
GET /chat/history?conversationId=xxx
GET /quota
```

关键变量：

- token
- userId
- conversationId
- messageId
- taskId
- testRunId

## 中等并发推荐压测流程

第一轮：单接口基准测试。

```text
并发：10、50、100
每档：5-10 分钟
每个核心接口请求数：不少于 1000
关注：p50、p95、p99、max、错误率、CPU、慢 SQL、Redis 命中率
```

第二轮：业务链路测试。

```text
并发：20、50、100
持续：10-30 分钟
关注：链路总耗时、接口依赖、token、数据一致性、部分成功部分失败
```

第三轮：稳定性测试。

```text
并发：50-100
持续：30-60 分钟，风险较高时 1-2 小时
关注：内存上涨、线程上涨、连接泄漏、p95 越跑越高、错误率增加
```

第四轮：峰值测试。

```text
并发逐步增加：50 -> 100 -> 200 -> 300 -> 500
出现错误率明显上升、p95 超目标、CPU 长期超过 80%、慢 SQL 激增、连接池打满时停止
```

安全容量不要写峰值。通常取拐点前稳定容量的 70%-80%。

## 企业级全链路压测

只有在大促、生产大流量、复杂微服务、多团队协作、大版本上线时默认建议。

必须满足：

- 压测请求带标识，例如 `X-Test-Run-Id`、`X-Load-Test`
- 测试账号隔离
- 测试数据可清理
- 第三方依赖明确真实调用还是 Mock
- 有一键停止压测方案
- 有网关限流、降级和回滚方案
- 有人实时观察监控

生产压测默认不推荐。除非用户明确具备流量标识、数据隔离、停止方案、实时监控和业务授权。

## 上线保障

压测通过不等于上线后一定没问题。上线前至少准备：

- 健康检查：`/health` 或 Spring Boot Actuator health
- 版本回滚：应用镜像、配置、数据库变更方案
- 外部可用性监控：首页、health、核心 API
- 错误追踪：Sentry 或同类平台
- 日志可查询：按 requestId/testRunId/userId 追踪
- 核心指标：错误率、p95、p99、CPU、内存、慢 SQL、Redis、MQ
- 发布观察窗口：30 分钟、2 小时、24 小时

中小团队的灰度替代方案：

- 先给内部账号或少量真实用户开放
- 用 feature flag 控制新功能
- 保留旧版本镜像随时回滚
- 避免一次性修改代码、数据库结构、配置和任务调度

## 告警建议

最小告警集合：

- `/health` 不可用
- 5 分钟错误率 > 1%
- 核心接口 p95 > 1s
- CPU > 80% 持续 5 分钟
- 内存 > 85%
- MySQL 慢 SQL 数量异常
- Redis 延迟异常或连接失败
- MQ 堆积超过阈值
- AI API 失败率或超时率升高

## 压测报告必须包含

- 测试目标
- 测试环境和机器配置
- 数据量
- 接口清单和业务链路
- 并发模型和流量比例
- 持续时间
- QPS、p95、p99、错误率
- CPU、内存、GC、慢 SQL、Redis、MQ
- 瓶颈判断
- 安全容量
- 是否建议上线
