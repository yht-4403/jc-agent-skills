# JC Rich Doc Publisher

把已经形成的内容发布成跨端清晰、视觉有重点、尽量原生可编辑的云文档。优先建立阅读层级，再选择平台组件；不要先堆组件再寻找内容。

## 工作模式

- **设计**：给出结构、视觉语义和平台组件方案，不执行外部写入。
- **发布**：创建新文档，写入后反向读取并校验。
- **更新**：先读取既有结构，只修改用户指定范围，保留无关内容。
- **审查**：只报告可读性、跨端、组件和降级问题；用户未要求修改时不写入。
- **接入**：检测腾讯文档 MCP，缺失或鉴权失败时提供官方最短接入路径；只配置时不创建测试文档。

## 首次使用

首次触发时，用一两句话说明：本 Skill 会优先保留原生可编辑性，按手机与电脑共同阅读设计，并在发布后反向校验。材料充分时说明后立即工作；材料不足时只索取平台、目标文档和正文等最小输入。后续轮次不要重复介绍。

## 资源路由

- 创建、重排或审查富文档时，读取 [core-design-system.md](references/core-design-system.md)。
- 内容包含流程、阶段、箭头、分支、循环或依赖时，读取 [native-arrow-patterns.md](references/native-arrow-patterns.md)。
- 目标是腾讯智能文档时，读取 [tencent-smartcanvas.md](references/tencent-smartcanvas.md)。
- 用户询问腾讯文档 MCP、当前没有腾讯文档工具或工具鉴权失败时，读取 [tencent-mcp-onboarding.md](references/tencent-mcp-onboarding.md)。已经连接成功时不要加载或重复配置。
- 更新既有文档、多人协作、涉及权限/评论/修订、同一任务有多个受众，或出现多个旧版本时，读取 [document-collaboration.md](references/document-collaboration.md)。
- 目标是飞书文档或飞书画板时，读取 [lark-doc.md](references/lark-doc.md)。

只读取当前平台和内容所需的 Reference，不要无条件加载全部文件。

## 默认工作流

1. **确认内容契约**：识别受众、阅读目的、必须保留的事实、真实与模拟边界、用户点名的样式偏好。
2. **确认协作目标**：创建时确认账号、位置和权限；更新时定位精确文档并先读取现状，识别用户手工修改和活动版本。
3. **建立阅读路径**：首屏先给结论或导航；每节先回答读者问题，再放证据、解释和动作。
4. **选择表达形态**：段落承载叙述，列表承载并列项，待办承载行动，高亮承载结论或风险，分栏承载短对比，原生箭头流程承载简单关系，Mermaid/SVG 只承载原生组件无法清楚表达的复杂关系。
5. **按跨端规则排版**：默认以手机端不失序为底线，同时保持电脑端信息密度。流程优先纵向，不让窄箭头栏在手机端与节点错位。
6. **执行平台写入**：优先使用目标平台原生组件。小改动定点更新；工具不可用时生成可继续发布的 MDX/XML/Markdown 源稿，并明确尚未写入。
7. **反向校验**：重新读取到文档末尾，确认开头、关键模块、图示、作品集或结尾均存在；检查不支持组件、丢图、重复标题、错序、空白占位、异常降级和权限。
8. **交付**：给出在线链接、主要读者、采用模式、权限和仍待补的真实材料；发生归档或回收站删除时列出精确目标并说明可恢复性。

## 表达选择

优先级不是固定组件配额，而是：

1. 原生段落、标题、列表和待办；
2. 原生高亮、分栏和文字标记；
3. 原生纵向箭头流程；
4. 平台可编辑画板或流程图；
5. Mermaid/SVG 渲染图；
6. 高清 PNG 兼容回退。

用户明确指定格式时，以用户要求优先。正式公文、法律、学术等体裁默认克制使用彩色组件，除非用户另有要求。

## 权限与依赖

- 写入云文档属于外部变更，只有用户要求创建、更新或发布时执行。
- 腾讯文档优先使用已配置的官方 MCP；飞书优先使用已配置的 `lark-cli` 或对应连接器。
- 腾讯文档缺少工具或鉴权时按 `tencent-mcp-onboarding.md` 检测、授权和验证；宿主没有安全凭据入口时不让用户在普通聊天中粘贴 Token。
- 检测到缺少工具、权限或授权时，按最小权限提供官方入口；用户拒绝时降级为本地源稿。
- 不输出、回显或保存 Token、密钥或私有候选人信息；真实人才资料对外发布前必须脱敏。
- 默认沿用现有权限或使用满足任务的最小权限；全员可编辑只有用户明确要求时设置。
- 不把作者机器上的绝对路径写成运行依赖。Reference 中的示例只说明结构，执行时重新发现可用工具。

## 质量门

- 首屏是否在短时间内说明结论、适用范围或阅读路径；
- 手机端是否保持正确顺序，没有窄栏、错位箭头或超宽图；
- 电脑端是否仍然有清楚层级，而不是一条过长文字流；
- 颜色是否保持信息蓝、建议绿、注意黄、风险红、中性灰的语义；
- 引用块是否只用于真实引用，而没有冒充高亮模块；
- 表格是否只承载真实行列数据，普通信息是否已改为段落、列表或分栏；
- 原生组件是否优先，复杂图是否保留可维护源文件；
- 发布后是否完成反向读取，而不是只信任写入成功响应；
- 更新是否保留用户在线修改，活动版本、权限和受众是否正确；
- 真实、推断、模拟和待确认内容是否清楚分开。

## 核心 Gotchas

- 不要为“视觉丰富”把每段都做成高亮块。
- 不要把横向四至七栏流程当作跨端默认；手机端会压缩或重排，箭头容易失序。
- 不要用 MDX 分栏伪装复杂拓扑；出现交叉连线、回路或条件树时切换图示。
- 不要把 Mermaid 代码块直接塞进不支持原生渲染的平台正文。
- 不要只保存 PNG；复杂图至少保留 Mermaid、SVG 或其他可维护源文件。
- 不要因一次小改动新建 V2/V3，也不要拿本地旧稿覆盖用户在线修改。
- 不要在普通聊天、命令输出、Skill 或文档中收集和复述真实 Token。
- 不要把平台返回“创建成功”等同于最终文档完整，必须读取验证。
- 不要复制平台全量 API 文档进本 Skill；平台语法变化时以实际工具 Schema 和官方 Skill 为准。

## 停止条件

缺少平台选择但不同平台会显著改变产物、目标文档无法定位、写权限缺失且授权未完成，或用户要求的原生能力当前平台不存在时，停止外部写入，说明限制并交付最小可用源稿或替代方案。
